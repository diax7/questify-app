2026-10-29, base main f716225. ONE coordinator-authorized, local TEST-ONLY candidate. No production
door, migration, adapter, dependency, transport or deployment changed. ADR-361 remains an investigation,
not an accepted replacement protocol; T-503 stays unchecked. Machine-readable observations, baseline

## Candidate and stop condition

The opt-in t503-auto-gate.int.test.ts loads t503-auto-probe.sql only into its disposable migrated DB.
It retains the actual complete_quest and current record_completion bodies, including real completion,
ledger, enrollment, XP/streak/bonus/trigger work. Test-only wrappers take shared G before those source
entrances. A BEFORE STATEMENT guard precedes tuple locking for the representative business tables;
an active-statement depth guard rejects premature immediate-constraint finalization. This is not a
complete writer inventory or a security/lifecycle certificate.

Each changed eligible enrollment maintains its own indexed projection row, marks the event dirty and
inserts one transaction-level pending row (ON CONFLICT does not add another callback). A deferred
constraint-trigger callback tries SET CONSTRAINTS ALL IMMEDIATE to drain business/FK work, seals the
business phase, then publishes events ordered by advisory-key hash and UUID. Publication writes the
snapshot/revision, all entry/exit facts and exact latest identities in the same transaction. No caller
publication helper is installed or needed for the passing ordinary completion.

**Fatal observation:** at a real COMMIT, a completion followed by a queued deferred business job fails
with "business entry after finalization". The pending marker was queued before that business job.
The callback's SET CONSTRAINTS ALL IMMEDIATE returned without running the already queued business
callback; E was acquired, then that callback ran and the new pre-source guard correctly rejected it.
Thus this candidate rejects a valid deferred-work transaction. The guard prevents the late business
lock rather than proving that the drain happened. It is NOT a PASS, and removing the guard would
restore the rejected late-business hazard. No attempt was made to rename/requeue triggers, move E,
weaken guards, tune performance or introduce another candidate after this failure.

The minimal session-local corroboration t503-auto-drain-repro.sql creates only temporary tables and
pg_temp functions. Observed notice order on PostgreSQL 17.11:

1. automatic callback: before SET CONSTRAINTS ALL IMMEDIATE
2. automatic callback: after SET CONSTRAINTS ALL IMMEDIATE
3. automatic callback: E acquired
4. business callback phase: finalizing

COMMIT raises 42501 in business_callback. Both temporary tables subsequently contain zero rows and
pg_locks confirms E released. This corroborates the ordering failure; it is NOT a substitute for the
unreached real-completion/ledger/projection/snapshot/fact rollback-injection proof. No assertion about
PostgreSQL's internal firing-list implementation is required to reject the observed protocol.

## Validation, harness debugging and recommendation

The 50k run reports 2 PASS / 1 RED, 11 registered / 8 unreached, 164.89 seconds. Preserve the red opt-in;
ordinary opt-out reports 11 skipped. Final API types, targeted oxlint/oxfmt and limits pass (318 existing,
zero new). After failure, only fail-stop/error reporting and the minimal diagnostic were added; the
candidate algorithm was not changed or retimed. These final harness additions are type/lint/opt-out
checked, not a second green real-source run. No full Vitest or duplicate 517-test security run occurred.

Two initial harness-only executions timed out while preloading 100,000 rows with per-row ranking_eligible.
They reached no candidate invariant/timing test. The bounded harness fix uses the existing canonical
set-based ranked_enrollments for initial preload only, with adequate setup timeout. Incremental actual
completion updates still call the unchanged eligibility predicate on their changed row. Their log hashes,
and the final run hash, are retained in JSON; no prior published fixture/result was changed.

**Recommendation: reject this automatic dirty-marker/SET-CONSTRAINTS callback candidate and stop.**
A further experiment needs separate coordinator authorization and a demonstrated after-all-deferred-
business boundary plus complete pre-row-lock source closure, not a promise that a callback drain is
transitive. No ADR acceptance, task tick, email/UI, next task, live service, push/deploy/EAS or mutation.
Approximate effort 25k agent tokens (estimate, not billing); CI minutes 0.
