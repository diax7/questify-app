# T-220 — Targeting by join answer or guest tag

Delivers FR-1708 (F-233). **Core bar** (it filters `record_completion` and `reserve_reward`, the points and prize
paths): one Opus plan review, one Opus code review, mutation on the new SQL-facing module. Migration **0037**.
Depends on T-212 (join fields and answers, guest list; migration 0028), T-201 (shop), T-105 (completion engine).

Dhia is away: the open choices are my recommendation, written as **Proposed** ADR-170 to ADR-173 and Q-136 to Q-139.

## What exists (no change)

- Join fields (`event_join_field`, at most 5, kinds `full_name … custom`) are **free text**; answers in `join_answer`
  (written only by the join definers). The guest list (`event_guest`) holds a phone or an email, no tag.
- Every completion runs through `record_completion` (player scan, operator My QR, the team's quest award); every
  reservation through `reserve_reward`. Players read quests through `member_event_quests`, the signed-out event page
  through `public_event_quests`, the shop through `event_shop` + `shop_rewards`, Home's goal through `shop_rewards`
  and `set_goal`.

## Rules

- **A targeting rule (ADR-170)** sits on a category or a reward: either *answer* (one join field and the chosen
  options of it) or *tag* (a set of guest tags). One rule per item; none means everyone. A player is in the audience
  when their answer to that field is one of the options, or one of their guest entries carries one of the tags.
- **Only choice fields can target (ADR-171).** Free-text answers ("Women", "women", "نساء") would match by luck. A
  `custom` field gains optional `options` (2 to 20, each `{id, ar, en}`); with options the app shows a picker and
  the join definers accept only an option id. The answer stores the option id; the players page and exports show its
  label. Changing options bumps the join card's version (T-111 note), so a stale card is refused as today.
- **Guest tags (ADR-172):** `event_guest.tag` (optional, 1 to 30 characters, trimmed, matched case-insensitively). The
  guest paste box gains "Tag these entries" applied to the whole paste; pasting a contact already on the list with a
  tag sets its tag (counted as `tagged`). A player's tags are those of every entry matching a verified phone or email.
- **Fail closed (ADR-173):** a field used by a rule cannot be deleted, nor an option in use removed (409
  `join_field_targeted`, naming the categories and rewards). A rule pointing at nothing matches nobody, never
  everybody. Rehearsal enrollments (T-211) see everything, so the team can test every quest and reward.
- **What a player outside the audience gets:** the category and its quests are not listed (app, Home, the public
  event page hides every targeted category); the reward is not in the shop, cannot be pinned (`set_goal` answers
  RN404) and a pinned one falls back as a sold-out pin does. Scanning a targeted quest's code answers 403
  `quest_not_open` with `reason: not_for_you` ("This quest is for another group of players."), so a person at a booth
  knows why; reserving answers 404 (the reward does not exist for them). The operator scanning their My QR and the
  team's quest award get the same refusal; a bulk award by quest only reaches completers, so it is unaffected.
- **Changes any time, effective at once:** a rule can be added, changed or removed while live (audited, ids only).
  Points already earned and reservations already made stay (the ledger is append-only; the desk hands over what was
  reserved). The cached phone copy refreshes on the next quests or shop read.
- **Who sets it:** the owner or an editor in scope (the quest and reward builders' rights).

## Data (migration 0037)

- `event_join_field.options jsonb NULL` (array, 2..20, unique ids `^[a-z0-9]{1,12}$`, labels 1..60), only on
  `custom`; the API's column grants widened for it. The join definers check a choice answer against the options.
- `event_guest.tag text NULL` (CHECK length 1..30, trimmed, no control characters); index `(event_id, lower(tag))`.
- `category` and `reward` gain `audience_kind text NULL CHECK IN ('answer','tag')`, `audience_field_id uuid NULL`,
  `audience_values text[] NULL` with shape CHECKs (answer ⇔ field set; 1..20 values; tag ⇒ no field) and FK
  `(audience_field_id, event_id) → event_join_field (id, event_id)` `ON DELETE RESTRICT`. Writes go through a
  definer `set_audience(kind 'category'|'reward', target, rule jsonb, request)` (team in scope, audited), never a
  column grant. A trigger on `event_join_field` refuses removing an option still named by a rule (`QT409`).
- `in_audience(enrollment, kind, field, values) RETURNS boolean` STABLE, internal (revoked from PUBLIC): true for no
  rule or a rehearsal enrollment; else the answer or tag match.
- Replaced to call it: `member_event_quests`, `public_event_quests` (targeted categories hidden), `shop_rewards`,
  `event_shop` counts, `set_goal`, `record_completion` (`QN403 DETAIL 'audience'`, checked after the enrollment and
  before the proof), `reserve_reward` (`RN404`). Lock order unchanged (the rule is read, not locked).
- Outsider + cross-tenant suites: `set_audience` and `in_audience` refused to the public role and another organizer;
  the new columns invisible to strangers.

## API

- `PUT …/events/{id}/join/fields`: a `custom` field takes `options?: [{id?, ar, en}]`; 409 `join_field_targeted`.
  `POST /v1/join` validates a choice answer (422 `invalid_join_answers`, field named). The card carries the options.
- `POST …/join/guests` takes `tag?`; the answer gains `tagged`; `GET …/join/guests` returns each entry's `tag` and the
  event's distinct tags with counts.
- `PUT …/events/{id}/categories/{categoryId}/audience` and `PUT …/rewards/{rewardId}/audience`: `{rule: null |
  {kind: "answer", fieldId, values} | {kind: "tag", values}}` → the rule and how many current members match. 422
  `invalid_audience` (a field without options, an unknown option, empty values). Category and reward reads return
  `audience`.
- Player reads unchanged in shape; `quest_not_open` gains `reason: not_for_you`.

## Screens

- **Dashboard:** the field editor gains "Answer by choosing from a list" with the options; the guest paste box gains a
  tag; each category and reward gets "Who sees it": Everyone / By an answer (field, then options as checkboxes) / By a
  guest tag (the event's tags as checkboxes), with "{count} players match now". Arabic and English, RTL.
- **App:** the join form shows a picker for a choice field; the quest refusal message. Nothing else changes: hidden
  items are simply not returned.

## Tests (test first)

- **DB:** a member with the matching answer sees the category and completes; another member does not see it and
  `record_completion` refuses (`audience`) for the player, the operator's My QR scan and the team's quest award;
  reward hidden from `shop_rewards`, `reserve_reward` RN404, `set_goal` RN404; tag match through phone and email
  entries, case-insensitive; no rule = everyone; a rehearsal enrollment sees all; deleting a targeted field and
  removing a used option refused; a rule change applies at the next read; earlier completions and reservations stay;
  the public page hides targeted categories; another organizer and an out-of-scope editor cannot set a rule; audit.
- **Routes:** every outcome; choice answers validated; the guest tag and `tagged`; the match count.
- **App unit:** the picker answer and the `not_for_you` message. **Browser:** setting a rule by answer and by tag on
  the dashboard (desktop and phone). Security suites; `expo export`; mutation on the new module.

## Out of scope

Rules combining several conditions (AND/OR), targeting single quests rather than categories (FR-1708 names categories
and rewards; Q-139), editing a player's answer after joining, targeting announcements or pushes (T-501's audience).
