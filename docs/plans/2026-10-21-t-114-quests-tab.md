# T-114 — The Quests tab

Delivers FR-221, FR-222, FR-230, FR-1742 (in part, see the scope note). Standard bar for the screens; the change to the
members' quest read is tenant isolation (Max), and completing an entry-code quest from the app touches the points
ledger through the existing `POST /v1/quests/{id}/complete` (no change to it).

## Scope note

- **Server today:** `GET /v1/events/{id}/quests` (T-113) gives an active member the categories and visible quests with
  `done` (completions) per quest. It has no points earned, which FR-230's collapsed summary needs.
- **Data the requirements name but the model lacks:** a quest's location ("where"), estimated time, difficulty, tips
  and steps (FR-221, FR-222). No task has added them yet: steps arrive with multi-step quests (T-3xx), estimated time is
  Q-101. FR-222's acceptance says sections not set are not shown, so the sheet shows what exists and hides the rest;
  the gap is recorded (Q-102), not invented.
- **Quest types shipped:** `scan_qr` and `enter_code` only. FR-1742's verification line exists for both; "Show My QR
  to staff" and NFC come with their types (T-205, T-3xx).
- **App today:** the Quests tab is a placeholder; Home's Go already opens `/event/{id}/quests?quest={questId}`.

## Decisions (tactical; for the CTO to challenge)

1. **Points earned per quest (FR-230):** migration 0022 replaces `member_event_quests` with one more column,
   `earned bigint`: the sum of this enrollment's ledger `score_delta` for the quest, so a points change by the organizer
   after a completion never misstates what the player earned. Same guard (active enrollment of an active player), same
   named columns, never `type_config`; dropped and created again (the return type changes), revoked from PUBLIC and
   granted to `questify_app` in the same migration. The route adds `earned` to each quest.
2. **A category's summary (FR-230):** points earned of the points available (each quest's points × its repeat cap),
   and quests finished (done to the cap, the T-113 rule) of the visible quests, with Western digits and grouping
   (`2,000 / 10,000`). Computed on the phone from the route's answer, in a pure function with tests.
3. **The accordion (FR-230):** every category starts open when the event has one category, else all collapsed except
   the one holding the quest named by `?quest=`; the open set is screen state only. Each header is a button with
   `accessibilityState.expanded`.
4. **A quest card (FR-221):** title, the type's action ("Scan a QR code", "Enter a code"), points, its state, and for a
   repeatable quest "2 of 3". States, one rule (`questState`, pure): `done` (finished to the cap), `not_live` (the
   event is not live), `not_yet` (opens later: shows when), `closed` (its window ended), else `open`. The event's
   status comes from Home's answer, read once by the tab (the `/home` route), so the server decides "live"; the quest
   windows use the phone's clock for display only, and the server rules on every completion.
5. **The details sheet (FR-222, FR-1742):** the description, the points, the window in the event's zone, the repeat
   progress, and the verification line with its action:
   - `scan_qr`: "Scan the quest's code" with a Scan button that opens the same "coming soon" sheet as the center
     button until T-115.
   - `enter_code`: "Type the code shown at the event" with a field (ASCII letters and digits, upper-cased, Arabic-Indic
     digits converted) and Submit → `POST /v1/quests/{id}/complete {proof: {type: "code", code}}` with a fresh
     Idempotency-Key per submission (the same key on a retry after a dropped connection). Success: "+10 points" and the
     tab reloads. Errors in the API's own words: 422 `invalid_code`, 429 with the wait, 403 `quest_not_open`, 409
     `already_completed`; a network failure keeps the typed code for retry.
   Only an `open` quest shows the action; other states say why.
6. **`?quest=` (from Home's Go):** opens that quest's sheet once, and expands its category; an unknown id is ignored.
7. **States of the tab:** loading; a network failure with retry (the last good copy stays); pending member (from the
   event's list in `EventContext`): "waiting for approval", no call; 403/404 `gone`: forget the event and go to Questify
   home (Home's rule); the empty state when no quest is visible (FR-221); refetch on focus and when the app returns to
   the front.
8. **Shared code:** the answer reader `readQuests` beside `home-api.ts`; the idempotency key from a small Math.random
   UUID helper shared with the install id (moved, not copied).

## Tests

- Database: `earned` is the ledger's sum for this player and quest only (another player's completion and a later points
  change do not move it); the guard and PUBLIC close stay (the T-113 cases run against the new function).
- HTTP: `earned` in the answer; the T-113 cases still pass.
- App (Vitest): `readQuests` (shape, bad shapes → network); `categorySummary` (the 2,000 / 10,000 example, repeat caps,
  empty category); `questState` for each state and boundary; the `?quest=` choice of the open category; the completion
  answer mapping (success, each error, network); the code normalizer (Arabic-Indic digits, spaces, case).
- Mutation on the new app modules and the changed API module.

## Revision 1 (after CTO plan review 1, 86/100): overrides the sections above where they differ

- **M1 and M2, option A: `/quests` stands on its own.**
  - The answer carries `event: {statusNow, timezone}`.
  - Each quest gets a server-computed `state` (`done | not_live | not_yet | closed | open`). `questState` sits in
    `apps/api/src/home/home.ts` beside `finished`; `isOpen` becomes `questState(...) === "open"`. It runs on the
    database's `now()` from `standingOf`, so Home's Up next and the tab cannot disagree.
  - A pending member gets 403 `membership_pending`, a new code, which the app shows as "waiting for approval". Only
    `not_enrolled` and 404 mean `gone`.
  - The tab makes one call and no longer reads EventContext for this; the phone only formats.
  - The T-113 HTTP case for a pending member and API.md change with it.
- **M3, a separate completion mapper**, fully tested, that never reaches `gone`:
  - `invalid_code`: try again;
  - `quest_not_open`: copy per `reason` (`event_not_live`, `hidden`, `not_started`, `ended`, FR-225);
  - `already_completed`: the limit is reached (FR-227);
  - `enrollment_inactive` and 404: close the sheet and reload the tab, whose own read decides `gone`;
  - 429: the wait from `retry-after`;
  - anything else: "couldn't complete, try again", keeping the code.
- **m1, the key's lifetime:** the key is reused only while the typed code is unchanged and the last attempt was a
  network failure. Any answer from the server, or an edit of the field, makes a new key. Tested.
- **m2, one normalizer:** `normalizeEntryCode` moves from `apps/api/src/completions/complete.ts` to `packages/shared`
  (replace, don't copy) and both sides use it. Submit waits for at least 4 characters.
- **m3, unknown types:** `type` stays a plain string. An unknown type's card shows its title and points, says "not
  available in this version of the app", and offers no action. Tested.
- **m4, `?quest=`:** handled once per value. The param is cleared when the sheet closes, and the sheet reads its
  quest by id from the latest data, closing if the quest is gone.
- **m5:** the staleness of `state` while the screen stays open is accepted (the server rules on every completion);
  the tab reloads on focus and when the app returns to the front.
- **n1:** `earned` is shown unclamped (it can pass the available points after a points cut; tested). API.md notes
  that category sums leave out hidden quests.
- **n3:** a category header's accessibility label includes its summary.
