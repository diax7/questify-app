# T-501c: the app's push (plan note)

Standard bar. The decisions are ADR-342 to ADR-351 (Accepted); the plan is "The app" in
`docs/plans/2026-10-28-t-501-push.md`. This note records only how the build is cut and where it fills in (ADR-352,
Q-321, Proposed). Delivers FR-1104, FR-1105, FR-1106, FR-1115 (on screen) and FR-1824's history (T-312b, merged).

## Dependencies

| Package | Range | Why |
|---|---|---|
| `expo-notifications` | `~57.0.23` (resolves 57.0.24, published 2026-10-22) | The SDK 57 list names `~57.0.23`. The native token, the permission prompt, Android channels, taps and the foreground handler. No JS-only way exists. |
| `expo-application` | `~57.0.3` (SDK 57 list) | `getIosPushNotificationServiceEnvironmentAsync()`: sandbox or production for the server's APNs host (ADR-344 (5)). |

Both new packages go through pnpm's one-day release delay; `strictDepBuilds` still passes (no install scripts).

## Cut

1. **Server, separate commit:** `GET /v1/me/notifications` items gain `refs` (ids only, `refIds`), because a tapped
   center row needs its quest id. `own_notifications` (0076) already returns `refs`; only the schema and `centerItem`
   change. A test on the route.
2. **Shared:** `notificationRoute(kind, eventId, refs)` (a fixed table; an unknown kind or a promotional kind answers
   `center`), the tap payload reader (`q` read where the platforms really put it), the app strings.
3. **App `src/push/`:**
   - `push-native.ts`, the only file that loads `expo-notifications` / `expo-application` / `expo-device`, and only when
     `requireOptionalNativeModule` finds every module the package imports at load (an older development build keeps
     working with push off). A unit test removes the modules; a scan test keeps the loads in this file.
   - `push-flow.ts`: platform-free logic over injected deps: permission states, when the explainer is due (undetermined,
     not snoozed 30 days), registration (`PUT /v1/me/push-device`; iOS lower-case; `development` → sandbox, `production`,
     `null` or a throw → production; on launch, token change, language change, else at most daily), unregister.
   - `push-api.ts`: the center, read, topics and device calls with zod-checked answers.
   - `PushHost` (root layout): channels, registration sync at launch and on foreground, token listener, foreground
     banner and unread refresh, taps (cold start and running) routed through the table.
   - `unread-store.ts`: the bell's count (from `GET /v1/me` `notifications.unread`, then from every center answer).
4. **Screens:** `/notifications` (the center, P16; the offers screen moves to `/settings/notifications` with the topic
   switches and push status), the bell on Questify Home and Event Home, Profile → Notifications, the explainer sheet on
   the join result screens, sign-out unregistering the device first.

## Where the build fills in (ADR-352)

1. **The explainer shows on the join result screens** (the join card, the invitation), not on Event Home. Event Home
   already shows the location sheet after a join; two sheets and two system prompts would stack. After "You're in" the
   push sheet appears; "Open the event" then leads to the location sheet as before.
2. **The route table names the kinds the plan's owed-push table lists** (`join_accepted`, `flash_quest`, …) as the
   contract for T-501d to T-501g; a unit test requires every kind in `PUSH_TEMPLATES` to have a route entry, so a slice
   that adds a kind must add its route (or `center`). Until then an unknown kind opens the center row (ADR-349 (4)).
3. **The payload is read from both places:** iOS direct APNs puts `q` in `trigger.payload` (`content.data` is only the
   `body` key of an Expo-service push, so it is empty); Android puts the flat keys in `content.data` and
   `trigger.remoteMessage.data`. The reader takes any of them; the RUNBOOK go-live line 6 confirms it on a phone.
4. **"Mark all as read"** on the center: the route exists (`{all: true}`), and a long unread list is otherwise 100
   taps.
5. **Not set in this slice:** Android's notification icon (a 96 px white-on-transparent asset from the brand deck) and
   `android.googleServicesFile` (Dhia's Firebase file; without it Android registration fails quietly and the center
   still works).
6. **A resumed app refreshes the profile** (`GET /v1/me`) once per foreground so the bell's count includes pushes that
   arrived while the app was in the background.

## Tests

Unit (Vitest, no React renderer in this app): the flow over fake deps, the native adapter with the modules removed and
present, the payload reader on every placement, the route table, the API functions, the unread store. Server: the route
test for `refs`. `hermes-runtime.test.ts` covers the new files. `npx expo export` for Android and iOS. Web e2e: no web
file changes. Phone checks stay owed (STATE).
