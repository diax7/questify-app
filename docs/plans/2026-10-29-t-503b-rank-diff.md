## Rank push (FR-613)

- Two personal kinds, `rank_top_ten` and `rank_top_ten_exit`: topic `rank`, membership `active`, TTL 5 minutes, fixed text
  with no rank number; both open the ranking tab (`routes.ts` already reserves the entry kind).
- `rank_top_snapshot` (one row per event: the ten enrollment ids, `taken_at`, the rehearsal erase stamp). A system door
  `rank_push_diff(event, ranking_on)` runs per live event under `pg_try_advisory_xact_lock` (the lease: a second runner
  or instance gets `busy`), reads the ten in the board's order and rule (`enrollment_ranking_idx` walk, `ranking_eligible`
  per row, stop at ten: one index range per event, not a scan of all members), compares, writes the snapshot and creates
  one `notice_create` per entry and per exit. No snapshot, a changed rehearsal erase stamp, or an event that is not live
  with the ranking on: baseline stored, no notices (an event that stops being live loses its snapshot, so a return starts
  again from a baseline). Cooldown: no `rank_top_ten*` notice for the member and event in the last 10 minutes (the notice
  table is the record; a dropped blip is not queued). The tick (`ranking/top-ten-tick.ts`) lists live events, reads the
  `ranking` switch through the settings service, and never overlaps itself; it touches neither the completion
  transaction nor the Redis copy. The board is read from PostgreSQL because a system seat has no reader and the Redis copy
  is rebuilt from this same rule.

## Organizer alerts (FR-1727)

- Seven types: `activated`, `stock_low`, `codes_low`, `new_flags`, `content_unpublished`, `support_access`, `size_limit`
  (80 and 100 are two facts under one switch). `organizer_alert_switch` holds one row per member and type (default ON,
  cascades with membership). Doors `own_alert_switches(org)` and `set_own_alert_switches(org, switches)` act only on the
  calling member (`app_staff_user_id()`); `GET` and `PUT /v1/organizers/:id/alerts/me`, a strict full boolean object.
- Outbox `organizer_alert` (ids only: organizer, event, staff user, type, once-only key; no address, no text). A producer
  calls `alert_enqueue`, which writes one row per active member whose event scope and switch allow it, at source time.
  Wired producers: `activated` (event draft to scheduled), `size_limit` (new `event_limit_alert`), `stock_low` and
  `codes_low` (a reward crossing into low: available at most max(1, ceil(10% of total)), so a total change alone never
  reopens an episode), `support_access` (`console.ticket_read` audit row, once per admin, event and day), `new_flags`
  (a cursor scan, so the completion transaction is untouched). `content_unpublished` has no source yet: owed to T-701/T-609.
- Sender (`organizer-alerts/worker.ts`): `alert_claim` re-checks active staff, membership, event scope and the switch
  at send time (else the row is skipped with the reason), leases 60 s, returns the current address into memory only; the
  mail is fixed bilingual text with ids only. Transport is the existing `EmailSender` type; production passes none, so rows are
  skipped as `transport_off` and nothing leaves the machine. A thrown send is `uncertain` and never retried (empty retry allowlist).
