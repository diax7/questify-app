## Today (read from the code)

- `apps/web/src/lib/forward.ts` forwards every `/v1/*`. It drops `authorization`, `x-device-id`, `x-app-version`, and
  passes `cookie` whole and every upstream `set-cookie`.
- Reachable now: `/v1/auth/code`, `/resend`, `/verify`, `/signup`, `/refresh`, `/logout`. verify, signup and refresh
  return `accessToken` and `refreshToken` in the body on the web origin. Every `access: "player"` route answers 401.
  Codes asked through the web skip the per-install limit (no `x-device-id`).
- After P2 every `player` route in `apps/api/test/security/routes.int.test.ts` is reachable with the cookie. The
  forwarder answers 404 to `/v1/operator/*` and `/v1/me/operator-events` for cookie requests (operator screens stay
  phone-only; Q-755).
- Only `players/guard.ts`, `players/devices.ts` and `push/routes.ts` read `authorization`. Server components send only
  the staff cookie.

## Why the forwarder sets the cookie, not the API

An API-set player cookie would make the player guard read cookies, put `checkOrigin` on every player write (63+ route
declarations) and give the native app a second credential channel. In the forwarder, the API's player contract stays
bearer only and the cookie is host-only to the web origin.

## The forwarder (`apps/web/src/lib/player-session.ts`, called from `forward.ts`)

Cookie: `__Host-qs_player=<access>.<refresh>` (two 43-character base64url tokens), `Path=/; HttpOnly; Secure;
SameSite=Strict; Max-Age=15552000` (180 days, set again on each rotation). The 365-day end is the API's (a refresh then
answers 401 and the cookie is cleared). Clearing: same attributes, `Max-Age=0`. A value not shaped like two tokens is no
cookie. An upstream `set-cookie` named `__Host-qs_player` is dropped.

Handled by the forwarder (always `cache-control: no-store` and the ADR-700 headers):

1. `POST /v1/auth/verify` and `/signup`: parse the JSON body (2 KiB at most), replace `device` with `{ "platform":
   "web" }` (no model or user agent, ADR-710), forward. On 200/201 with both tokens: set the cookie, answer `{ signedIn:
   true, expiresInSeconds, player }`. If a well-formed cookie is present, the forwarder first awaits `POST /v1/auth/logout`
   for it (normal timeout; a failure is only logged) and only then forwards verify or signup, so the orphan web family is
   ended before `issue_player_tokens` counts the 10 (0155:178-188) and no phone family is pushed out. Other answers (the `isNew`/`signupToken` step, 4xx, 429
   with Retry-After) pass through with no cookie. A 2xx without tokens answers 502 `api_unavailable`.
2. `POST /v1/auth/refresh`: the browser body is ignored. No cookie: 401 `unauthenticated`, no upstream call. Otherwise
   upstream `{ refreshToken }`. 200: new cookie and the step 1 body. 401: 401 `session_expired` and a cleared cookie.
   Timeout, 5xx or network: pass through, cookie untouched (the API's 60-second grace covers a lost answer).
3. `POST /v1/auth/logout`: the browser body is ignored; with a cookie, upstream `{ refreshToken }`. Always 204 with the
   cleared cookie, even when upstream fails (logged with method, path and reason only).
4. Every other `/v1` path: today's headers, plus `__Host-qs_player` removed from the forwarded `Cookie` (staff and
   device cookies stay); `Authorization: Bearer <access>` when the cookie is well-formed and the path is not
   `/v1/auth/*`, `/v1/staff/`, `/v1/admin/`, `/v1/device/` or an operator path; `x-device-id` only when a UUID; `x-app-version` only when `^[0-9]+(\.[0-9]+){0,2}$`. A browser-sent
   `Authorization` is never forwarded. Bodies stream unchanged.

- Cookie parsing: a `Cookie` header with `__Host-qs_player` more than once counts as no cookie and is cleared; every
  instance is stripped before forwarding.
- The forwarder's own upstream calls (the logout before a sign-in, refresh, logout) carry the client's
  `x-forwarded-for` and `user-agent`, so the address windows and the audit see the person, not the web server.

- Tokens out of bodies: only `players/routes.ts` `issuedBody` emits them, reached only through steps 1 and 2, which
  rebuild the body. An API source test fails when an `accessToken` or `refreshToken` property appears in another
  non-test file under `apps/api/src` (allowlist: `players/routes.ts`, `players/sign-in.ts`).
- Origin (CSRF): on POST, PUT, PATCH and DELETE, a request carrying the player cookie or targeting `/v1/auth/*` must send
  `Origin` equal to `WEB_ORIGIN`, else 403 `csrf_rejected` and nothing goes upstream. This stops login CSRF and sibling
  subdomains, which `SameSite` treats as same-site. GET and HEAD are not checked (they change nothing, V3.5.3; no CORS).
  Staff paths keep the API's `checkOrigin`. The web config reads the same origin under the API's name, `DASHBOARD_ORIGIN`
  (api config.ts:165), so the two never drift; it is required, in `apps/web/src/lib/config.ts`, `ops/cranl/*.json` and
  `playwright.config.ts`. No `access: "player"` GET writes anything (asserted on the route inventory), since GETs are not
  Origin-checked and a sibling subdomain is same-site.
- Device id caveat: a browser's install id lives in localStorage and can be rotated, so the per-install limit is not a
  control on the web (it never was against a scripted client, which can omit `x-device-id`, sign-in-limits.ts:65); the per-number (5 an hour, 10 a day), per-address and wrong-code limits hold. `x-app-version` is
  the web build's version; a `MIN_APP_VERSION` above it gives 426, and the app reloads once (Q-756, RUNBOOK).

## Refresh, reuse and clearing

Rotation and reuse stay in `rotate_player_refresh` (ADR-706, 712, 717). Reuse ends the family; the next refresh gets
401 `session_expired` and a cleared cookie. Web-specific risk: tabs share one cookie jar, so two refreshes within 60
seconds can store a revoked successor and the next refresh reads as reuse. Fix: one refresh at a time inside
`navigator.locks.request("questify.refresh")` (in-tab de-duplication where missing), and inside the lock retry the
failed request once before refreshing. Without `navigator.locks` the cross-tab race remains (accepted). A refresh answer
lost for more than 60 seconds reads as reuse and ends the family, as on the phone (RUNBOOK note).

## The app in cookie mode

- New `apps/app/src/api/cookie-session.ts` (pure, tested), wired by `app-session.web.ts`. No SecureStore: install id in
  AsyncStorage, base URL `location.origin`, `fetch` with `credentials: "same-origin"`. My QR is memory only on web.
- `Session.start(body: unknown): Promise<boolean>` in both modes: native accepts `isIssued`, web `signedIn === true`.
  `sign-in-api.ts` calls `start` in place of its own `isIssued` check.
- Web `request` never sends an access token. On 401: lock, retry once, then refresh; `session_expired` clears local
  items and notifies `onEnded` (not while signing out). `signedIn()` probes `GET /v1/me` (one refresh after a 401): ok
  or network is true; `session_expired` is true (the loader shows "session ended"); `unauthenticated` is false.
  `signOut` waits for a refresh in flight, posts `/v1/auth/logout`, drops My QR. Account deletion ends with `signOut`.

## The 10-device cap

Each browser sign-in is one family and one `player_sign_in_device` row with `platform = 'web'`; it counts in the 10, and
an 11th sign-in ends the oldest (ADR-717). Migration 0188 adds `'web'` to the 0155 CHECK; `deviceLabelBody.platform`
adds `"web"`; the devices list says "Web browser" / "متصفح الويب"; the data export lists it.

## Notes for P3

`SameSite=Strict` means a page reached from a QR code or an SMS link gets no player cookie on the document request;
`/play` never reads the cookie server-side. The `session_expired` code joins the shared `apiError` codes.
