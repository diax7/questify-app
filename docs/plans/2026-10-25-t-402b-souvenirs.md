## Product rules and immutable configuration (ADR-269)

Owners and editors within event limits manage up to100 souvenir rules per event through a dashboard Souvenirs
section. Draft creation/editing does not grant anything. Each rule has one new opaque item ID (never an event ID
or a reused level reward), kind, required bounded Arabic/English display names and a shipped visual key. Frame
choices reuse the14 shipped frames, character choices reuse the shipped chest, titles are bounded plain text.
Explain that equipped cosmetic names/art can be public; never copy the event name into a cosmetic automatically.
Private-event names belong only in the own locker source. Names follow existing organizer-content validation,
text-only rendering and safe error/log handling; no HTML, URLs or downloadable mechanics. Validate the same visual
allowlist in SQL and shared code. Future art remains data selecting a shipped renderer.

Activation is an explicit audited idempotent action. The confirmation states who qualifies, the frozen quest
targets/rank range, permanence and that already earned items cannot be recalled. Activation freezes item identity,
names/art, audience and target set; no silent recipient expansion after grants. Drafts can be edited/deleted.
An active rule can be stopped (future grants cease; existing items remain), but not edited or resumed. A replacement
is a new rule/item with its own explicit activation. Configurable limits/bounds use existing settings conventions;
no new top-level paid add-on is invented. Archived events cannot change or newly activate rules, while already
authorized pending grants can finish. Non-rank rules may activate during live or ended events; draft/scheduled
rules can be prepared/activated but do not award until real play is live. Rank rules activate only before results
confirmation. No general arbitrary-player grant endpoint is introduced.

Joined means approved active real membership (FR-1622's explicit 'everyone who joined'), not a claim that the app
proved physical presence. Deny pending/waitlisted/left/event-banned/platform-banned/deleted recipients. Organizer
team players and playable operators can receive joined/finisher souvenirs through their real player enrollment;
non-playable operators cannot receive finisher awards. Rank awards reuse ranking exclusion/team rules at freeze.
If a recipient leaves or is banned before delivery, skip; later legitimate reactivation triggers reevaluation.
An already earned cosmetic is never revoked by leaving, bans, reversals, rule stop, event archive or balance close.

Category/all-quest targets freeze at activation: visible non-flash quests, excluding live polls and quests whose
community unlock can no longer be reached (same target exclusions as category_done0055). A category must belong
to the event. Hidden categories are not automatically excluded: their discoverable quests can be targets; do not
return hidden target lists to unrelated players. Reject empty target sets. Explain exclusions and target count in
the confirmation. Later hide/delete/reparent/new quests do not rewrite the promise. Restrict physical deletion of
referenced targets; existing soft/config changes remain possible. Store the quest ID set with same-event FKs.

A souvenir is once per event rule across the event's lifetime, not once per daily/weekly reset. A target is done
after any real completion in any period (including a legitimate manual quest completion), a finished zero-score
quiz, or the existing exhausted-game terminal condition. Do not use current-period period_count during a delayed
worker run. Preserve quiz/game terminal semantics without granting on an open/pending submission, abandoned
single attempt with attempts remaining, or an issued but still playable round. Historical game exhaustion is
computed with game_attempts/game_left's actual bounds and terminal statuses, not just 'some failed round'; game
config locks already prevent changing attempt limits after a round exists. This lifetime interpretation and the
frozen targets are explicit Proposed choices and must be tested across local-midnight/week rollover.

## Eligibility, durable automatic work and grant locks (ADR-270)

All grant authority resides in an internal SQL evaluator, never the queue payload. It re-resolves the event, rule,
item and member from relational data, rejects stopped/draft rules and disallowed recipients, checks exact audience
evidence, inserts receipt+player_item atomically and returns only aggregate outcome. API/system callers cannot
supply earned_at, source, a substitute item or a trusted eligibility boolean. No new XP/ledger/reached row is paid.

Use narrow AFTER triggers to enqueue reevaluation after real enrollment approval/reactivation; quest_completion
insert; quiz completion including zero-score finish; game terminal transitions/exhaustion; and results confirmation.
These cover QR/NFC/My QR/typed/kiosk/manual/submission/passport/game/quiz doors through their actual shared DB
facts. No duplicate per-route grant logic. Triggers ignore rehearsal before writing work and use generation UPSERT;
they do not grant, scan all members, lock item/XP/player rows or call ensure_rehearsal_wiped. Target/config changes
cannot alter activated promises. A bounded activation scan covers existing attendees/completers; a periodic bounded
repair sweep covers missed work, upgrade history and lease recovery. No task depends only on an in-memory timer.

Keep queue claims and acknowledgments in **separate short transactions** from grants. A claim obtains a bounded
60s lease using SKIP LOCKED, records the observed generation and opaque lease token, and commits before evaluating any recipient. Evaluate one
recipient per transaction, processing applicable active rules in stable rule ID order; batch orchestration caps500
recipients and a2s tick budget, then resumes. Ack in a third transaction deletes/marks complete only the claimed
generation and lease token; a concurrent trigger increments generation and stays due. Renew a lease between bounded
batches if necessary; never acknowledge a reclaimed lease. Crash after a grant but before ack safely
replays uniqueness; crash after claim resumes when lease expires. Never hold a queue row while waiting for player,
enrollment, XP or item locks. In particular completion's queue trigger may run before XP, so deleting the queue
inside a grant transaction after taking XP would introduce a cycle. Tests must cross this exact schedule.

Grant lock order: read IDs without locks; lock active player **FOR SHARE**; lock its real enrollment FOR NO KEY
UPDATE; lock active rule FOR SHARE (stable ID order if several); lock player_xp FOR UPDATE; then receipt/item writes.
The player SHARE lock remains held until receipt/item commit. It conflicts with both NO KEY UPDATE (a normal admin
status UPDATE) and UPDATE (erasure/equip), while allowing FK KEY SHARE from XP/other legitimate writers. KEY SHARE
is insufficient:0005_harden_core.sql grants API UPDATE(status,deleted_at), and0038's player_status_guard permits
admin non-key updates; such a ban could commit after a final status read but before insertion. Use READ COMMITTED:
the locking SELECT must test status='active' against the row version obtained after any wait. If a ban committed
first, return ineligible and insert neither receipt nor item. If the evaluator obtained SHARE first, a ban waits
until grant commit; the item legitimately earned before the ban remains owned. Re-reading alone cannot replace
this transaction-long exclusion. Re-read enrollment/rule after waiting, including a completed erasure/ban/stop.
Do not call a rehearsal wipe
while holding player or enrollment locks. Real enrollment status/identity/phase checks reject rehearsals instead;
wipe only locks rehearsal members and has no souvenir rows to retain. Active rule edits/stops take rule FOR NO KEY
UPDATE and never player/enrollment/XP; event authorization/config locking uses FOR NO KEY UPDATE, compatible with
event FK KEY SHARE. Do not hold event FOR UPDATE waiting on a rule that a grant holds while inserting an event FK.
Confirmation's event lock only creates durable work after frozen places exist, never grants items in that transaction.
Before code GO, DB tests prove this order against actual latest completion/erase/equip/confirm/setter paths.

Run forced admin-ban/evaluator schedules as actual questify_app + app_is_admin context, not just owner-issued
UPDATE or a mocked ban: (1) ban holds the player row, evaluator waits, commit ban, evaluator refuses with0 receipts/

Use two primary actor connections and, where a real downstream lock blocker is needed, a third fixture connection;

claiming success. Permanent invalid configuration is refused at activation. Tick shutdown waits for current work;
multiple API instances remain safe. Document repair/resume in RUNBOOK; no new remote call or provider is involved.

## Final rank lifecycle (ADR-271)

Rank bounds are integers1–100 inclusive, rankFrom<=rankTo; independent souvenirs can overlap intentionally. Use
only event_result-confirmed result_place rows, not revealed ranks, Redis, today's board or a recomputed live query.
Extend result_depth to greatest(existing physical-prize depth,10,max active souvenir rank_to), retaining the100 cap
and existing rank_prizes toggle semantics for physical prizes. Souvenirs operate even when physical prizes are off.
The owner's existing expected places and preview must show exactly that new depth before confirmation; changed
places still yield results_changed, pending community payouts still block, and open quizzes still settle first.
No automatic confirmation/auto-reveal is introduced: after the event ends the rank rule reads 'Waiting for the owner
to confirm results', then confirmation atomically records recipients' rank evidence and enqueues the bounded scan.
Do not trigger off event_result INSERT alone before result_place insertion; enqueue at confirm_results's successful
tail, preserving replay handling. A repair scan recognizes already confirmed results after a crash/restart.

Creating/activating/editing rank rules takes the event lock compatible with the established confirmation barrier,
and checks event_result under that lock. The winner of rank activation versus confirmation fixes the depth; the
loser cannot add a range absent from the snapshot. Rank activation after confirmation is refused results_final,
including historical events with only10 frozen rows. Existing confirmed snapshots are never backfilled from current
scores and no vanished places are invented. Draft rank edits have no effect on depth. Stops before confirmation
can reduce preview depth; after confirmation they cannot rewrite result_place. Late bans/leaves/deletion skip that
recipient without promoting the next rank; already granted items remain. Prove behavior with ties, zero scores,
exclusions, rank100, prize toggle off, early stop and same-owner replay of confirmation/processing.
