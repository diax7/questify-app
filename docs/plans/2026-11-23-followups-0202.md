## 1. `reauth_at` only moves forward (T-599c review)

**Latest definitions** (none restated after 0155):
- `confirm_player_reauth` 0155:406-435, the write at 0155:428 (`SET reauth_at = now() ... RETURNING * INTO moved`).
- `confirm_staff_reauth` 0155:605-633, the write at 0155:627.
- `confirm_contact_change` 0155:786-846, the write at 0155:833-836 (the family's device row, ADR-715).
- The guard is on `staff_session` only: `staff_session_guard` 0155:96-109 raises `check_violation` (23514, a 500)
  when `reauth_at` moves backwards. `player_sign_in_device` has **no** guard trigger, so the two player writes never
  500; they can silently move `reauth_at` back (an older transaction's `now()` overwriting a newer confirm), which
  shortens the 10-minute fresh window by the gap. The review's "would 500" holds for 0155:627 only.

**How the 500 happens.** `now()` is the transaction's start. The staff confirm locks the session row, then the code;
two confirms of one code are already safe (the second waits on the row lock, then reads the code gone: `expired`).
The failing order: request A's transaction begins (its `now()` = t1); a second tab confirms code 1 at t2 > t1 and
commits; a new code 2 is started; A confirms code 2 and writes t1 < t2: 23514. This needs a transaction that
began before its code existed, so it is practically unreachable outside a test (plan review MINOR 3); the fix is
kept for the staff door, but the real race is `confirm_contact_change` crossed with a newer
`confirm_player_reauth`, which moved a device row's `reauth_at` back (test 3 is the main proof).

**Change** (the T-599c guard, "forward only, re-checked on the committed row", in its value form, because the confirm
must still return the row: a `WHERE reauth_at < now()` skip would leave `moved` NULL and answer `confirmed` with no
fresh end after the code was consumed):
- 0155:428 → `UPDATE player_sign_in_device SET reauth_at = greatest(reauth_at, now()) WHERE id = here.id RETURNING * INTO moved;`
- 0155:627 → `UPDATE staff_session SET reauth_at = greatest(reauth_at, now()) WHERE id = here.id RETURNING * INTO moved;`
- 0155:833 → `UPDATE player_sign_in_device d SET reauth_at = greatest(d.reauth_at, now()) FROM ...` (rest unchanged).
- `greatest` ignores NULL, so a first confirm still writes `now()`. Under READ COMMITTED a blocked UPDATE recomputes
  its SET list on the committed row version, so the newer value always wins. The audit row keeps its own time. No
  `clock_timestamp()` (it would not remove the need for `greatest` and would split the confirm's time from its audit).
- Rest of each body verbatim from 0155; lock order unchanged (device row or session row, then the code).

**Kiosk `paired_device` touch (0057:285-289, in `device_session`, never restated): no change.** Its SET is
`CASE WHEN p.last_seen_at < now() - interval '1 minute' THEN now() ELSE p.last_seen_at END`, evaluated on the
committed row, and `paired_device` has no backwards guard: it cannot 500, and at worst writes a time up to the gap
older than a concurrent touch's, which is never read finer than the minute. Recorded in the FOLLOWUPS line as checked.

**Tests** (`apps/api/test/db/signed-in-devices.int.test.ts`, the "races (ADR-712)" block, two `Client`s and the
`hold` / `pg_locks NOT granted` wait used by tests 13-16 and by `test/auth/sessions.int.test.ts` "lets an older
request's touch wait for a newer one still open"):
1. Staff, committed-first: an older transaction begins (BEGIN, request context, `SELECT now()` pins t1); 20 ms later
   another connection confirms code 1 and commits (t2); code 2 is started; the older transaction confirms code 2:
   `confirmed`, no 23514, `fresh_until` = t2 + 10 min, `reauth_at` = t2, one more `staff.reauth` audit row. Fails
   today with 23514.
2. Staff, lock-wait: the newer confirm of code 1 is held open; the older confirm of code 1 is seen waiting in
   `pg_locks`; after COMMIT it answers `expired` without an error, `reauth_at` = the newer time.
3. Player, committed-first, both doors: as 1 with `confirm_player_reauth`, and with the older transaction running
   `confirm_contact_change` after a newer `confirm_player_reauth` committed: `reauth_at` stays at the newer time
   (today it moves back; asserted by value).
4. Behaviour: the existing "a code typed on this family makes it fresh", "a contact change on this family makes it
   fresh" and the staff-session cases still pass (first confirm from NULL).
Outsider and cross-tenant: signatures and grants unchanged; `test/security` run as-is (the outsider list already names
the three doors).

0198:98-99, `WHEN (NEW.device_id IS NOT NULL)`), never restated. Today it calls `system_paid()` (0148:652, PL/pgSQL with a

**Change:** as 0198, reordered: keep the free `NEW.method = 'manual'` test first, then the PK read, then
`system_paid` only for a failed install:
```
IF NEW.method = 'manual' THEN RETURN NULL; END IF;
SELECT * INTO c FROM device_check d WHERE d.install_id = NEW.device_id AND d.verdict = 'failed';
IF NOT FOUND OR system_paid(NEW.method, NEW.idempotency_key) THEN RETURN NULL; END IF;
SELECT * INTO n FROM enrollment e WHERE e.id = NEW.enrollment_id;
PERFORM raise_integrity_flag(n, c);
```
Same outcome for every input. `system_paid` stays in a plain `IF` (rules.md, the per-row SET-function rule). Only the
function is replaced; the trigger is not dropped or re-created.
