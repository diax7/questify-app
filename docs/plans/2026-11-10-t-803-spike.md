# T-803 P0 spike: the player app as a phone web build (measured 2026-11-10)

Goal: measure what breaks when `apps/app` is exported for phone browsers with the same design. Plan:
`docs/plans/2026-11-10-t-803-player-web-build.md`. Nothing here ships; the only committed code is the dependencies and
the `app.json` web block.

## Dependencies added (`npx expo install`, Expo SDK 57)

| Package | Version | Note |
|---|---|---|
| `react-dom` | 19.2.3 | Same pin as `apps/web` and `react` |
| `react-native-web` | ^0.21.4 (0.21.4 installed) | Range chosen by `expo install` |
| `@expo/metro-runtime` | ~57.0.18 | |

`app.json`: `web: { output: "single", bundler: "metro" }` and `experiments.baseUrl: "/play"` (web only; the native
config is unchanged, `expo config` resolves). App typecheck and `npx vitest run apps/app` (157 files, 2063 tests) pass.

## Export

`npx expo export --platform web` passed on the first try: **no build errors, no code change, no stub needed**. Metro
resolves the `.web.js` builds of the Expo modules, and the ones without one (secure store, haptics, file system, NFC)
still bundle; they fail at run time instead (below). Output: `index.html`, one entry bundle of 4.55 MB (1.07 MB gzip),
four lazy chunks, 88 assets (every Baloo Bhaijaan 2 and Rubik weight, italics included: trim to the weights in use).

What got in the way of running it, and how I got past each:

1. `expo export --dev` keeps `/play` in the route (expo-router strips the base URL only in production), so every path
   is "Unmatched Route". Used the production export.
2. A release build refuses an `http` API (`apiBaseUrl`, MASVS-NETWORK). Served the export and a `/v1` forwarder over
   local HTTPS (self-signed) and set `EXPO_PUBLIC_API_URL=https://localhost:8090`. Same origin, so no CORS change.
3. **Every API call failed**, signed out too ("The terms could not be loaded"): `deviceId()` calls
   `SecureStore.deleteItemAsync`, and `expo-secure-store`'s web module is an empty object. For the measurement only I
   swapped in `sessionStorage` in `app-session.ts` (not committed: tokens in web storage break SECURITY.md; P2's cookie
   forwarder is the real fix).
4. A local API on a throw-away test database (`seedFullPlayer` plus a quiz quest, an SMS sender that writes codes to a
   file), started like `apps/web/e2e`. The 5-codes-an-hour limit per number is reached quickly in tests; the session
   was saved once and restored.

The helper scripts (static server, Playwright walker, fake-camera QR video, API launcher) were local and are deleted.

## Screens (Chromium, iPhone 13 and Pixel 7 profiles, English and Arabic)

Screenshots: `docs/evidence/t-803-spike/` (`en-*`, `ar-*`). Fonts, colours, cards, sheets, icons and Western digits
match the phone app in both languages.

| Screen | Result | What is wrong on web |
|---|---|---|
| Intro (language, 4 cards) | Works | `BackHandler is not supported on web` error from `IntroScreen.tsx` (harmless; guard it) |
| Questify home, signed out | Small fix | Tab bar: labels cut at the bottom edge; not mirrored in Arabic (Home stays left) |
| Sign-in (consent, number, code) | Works with the session swap | Needs P2 (no secure store on web); without it nothing loads |
| Event home | Works | Same tab bar issues |
| Quest list | Works | |
| Quiz (start, question, answer, result) | Works | |
| Rewards (shop, my rewards) | Small fix | Cancelling a held prize confirms with `Alert.alert`, which does nothing on react-native-web |
| Profile | Small fix | Language switch is dead (`Alert.alert` confirm); sign-out confirm likewise |
| Join scan, quest scan (camera) | Works | Decoder wasm is fetched from `fastly.jsdelivr.net` (self-host it) |
| Not reached | | Games, submissions, recap share, data export, operator screens (hidden on web per plan) |

RTL: the content of each screen already mirrors on web, because `Screen`, `Sheet` and `AppText` set `direction` and
`writingDirection` from the language rather than from `I18nManager`. Only the tab bar (outside `Screen`) stays LTR, and
`document.dir`/`lang` stay `""`/`en`. Fix: set `dir` and `lang` on `<html>` at start and give the tab bar the same
`direction`. A language change needs a page reload in place of `reloadAppAsync`.

`Alert.alert` is used 11 times in 8 files (profile, rewards, delete account, game, block button, home blocks, two
operator screens). One `confirm()` helper with a `.web.tsx` dialog in the brand style fixes all of them.

## Verdict

**Same design: feasible, yes.** Every screen reached renders as on the phone, in both languages, with only small,
contained fixes. Nothing needs a redesign. The draft plan's "hide the camera" is outdated: browser scanning works with
the same `CameraView` code, so `scan_qr`, `passport` and join-by-scan can stay on web. NFC stays phone-only.

Effort, about 4 to 5 worker days:

- P1 (tier B, about 2 days): `.web.ts` shims (secure store via P2, haptics, file system, NFC), `confirm()` helper for
  the 11 `Alert.alert` calls, tab bar direction and bottom inset, `<html dir lang>` and a reload on language change,
  `BackHandler` guard, self-hosted zxing wasm, `Platform.OS === "web"` in `deviceLabelOf` and `scan-quest.tsx`,
  operator screens hidden, font weights trimmed.
- P2 (tier A, about 1.5 to 2 days): the cookie session in the forwarder, as in the plan.
- P3 (tier B, about 1 day): hosting under `/play`, CSP and `Permissions-Policy` (camera and geolocation `self`), e2e.
