# T-102 — Event builder: create, edit, delete; lifecycle Draft to Archived

CTO: plan review 1 86/100; revision 2 94/100 (GO).

**Task (TASKS.md):** create, edit, delete an event with kind, time zone, event-day start, join methods; lifecycle states
Draft to Archived. Delivers FR-1001, 1002, 1003, 1728, 1714, 1715 (the event day, used later by T-216, T-304, T-405),
1017, 1608. Depends on T-101 (done). Done when: a draft event can be created and edited; its state moves Scheduled →
Live → Ended at the set times; every shown time is in the event's time zone. Quality bar: **Standard** for the builder;
the status rules are **Max** (they gate who can play and when).

## Scope note

- **Exists:** the `event` table (organizer, join code with a case-insensitive unique index, names AR/EN, status
  draft|scheduled|live|ended|archived, access public|unlisted|private, time zone, day start hour 0–23, starts/ends,
  config), its policies with the T-101 scope rules (a limited editor reads and edits only their events and cannot
  create one), `event_entitlement`, the organizer route scope (`member`/`owner`), audit.
- **Gap found:** the API role holds a full `UPDATE` grant on `event`, so any member could set `status` to `live`
  (FR-1017 says only Questify activates). This task closes it: **status is never written by the API role**; it moves
  only through definer functions.
- **Out of scope:** activation itself (T-210: Draft → Scheduled by a Questify admin after payment; until then a test
  helper and the owner connection activate); archiving at the end of the shop window (T-410 defines the window; until
  then Ended stays Ended); templates and duplicate (T-601); live-edit choices (T-604); join methods' behaviour (T-111 to
  T-112) — this task stores and validates them only.

## Behaviour

### Fields (migration 0009)

- New: `kind` (physical | virtual | workplace, default physical), `venue_ar`, `venue_en` (≤ 200 each; a physical event
  needs one before activation, checked in T-210's checklist, not here), `join_methods text[]` (subset of code, qr,
  link, public_list; at least one; default `{code, qr, link}`).
- Rules: `public_list` only when `access = 'public'` (CHECK); names ≤ 120; a time zone must be a real IANA zone
  (trigger against `pg_timezone_names`, and the API checks with `Intl.supportedValuesOf("timeZone")` first for a clear
  422); `ends_at > starts_at` (exists).
- **Join code:** generated by the API, 6 characters from an unambiguous alphabet (no 0, O, 1, I, L), retried on the
  unique index; never edited in this task (regeneration is a later concern).

### Grants (the status wall)

- `REVOKE UPDATE ON event FROM questify_app`; `GRANT UPDATE (name_ar, name_en, kind, venue_ar, venue_en, access,
  join_methods, timezone, day_start_hour, starts_at, ends_at, config, config_version)`. `status`, `organizer_id`,
  `join_code` and `id` are not writable by the API role.
- `INSERT` keeps working but a guard makes every new event `draft` (a trigger refuses any other status for
  `questify_app`).
- A guard trigger refuses changing `starts_at` once the event is live or later, and `ends_at` once ended (times are
  history then).
- Functions (definer, `search_path` pinned, EXECUTE to `questify_app` only, outsider-tested):
  - `end_event_early(event uuid, request uuid)`: owner of the event's organizer only (or admin); live → ended,
    `ends_at := now()`; audit `event.end`.
  - `advance_event_lifecycle()`: scheduled → live when `starts_at <= now()`; live → ended when `ends_at <= now()`;
    audit `event.lifecycle` as `system` per change; returns how many moved. Safe for anyone to call (it applies only
    the time rules), so it needs no caller check.
- `event_status_now(status, starts_at, ends_at)`: an immutable-in-shape SQL helper that answers what the status is at
  `now()` even before the tick moved it (scheduled past its start reads as live). The completion engine (T-105) and the
  event pages use it, so a minute of tick lag never lets a scan in early or late.

### The tick

- An in-process interval in the API (every 30 s, jittered, `unref`), calling `advance_event_lifecycle()` in its own
  transaction; errors are logged (`event.lifecycle_failed`, error name only) and never stop the server; stopped on
  close. Several API instances calling it at once are harmless (the updates are idempotent and row-locked).
  **Decision for the CTO:** this vs pg-boss now. Recommendation: the interval — pg-boss arrives with notifications
  (T-501), where queues are needed; one idempotent periodic statement does not need a queue.

### API (organizer scope)

- `GET /v1/organizers/:id/events` (`member`): the events the caller may see (the database applies the limit), newest
  first, with `statusNow`.
- `POST /v1/organizers/:id/events` (`member`, **Idempotency-Key**): create a draft → `201 {event}`. A limited editor
  → `403 scope_limited` (the database refuses; the API answers it plainly).
- `GET /v1/organizers/:id/events/:eventId` (`member`) → the event, or 404 (also outside an editor's limit).
- `PATCH /v1/organizers/:id/events/:eventId` (`member`) → partial update of the writable fields; validation as above;
  a change of `starts_at` after start, or `ends_at` after end → `409 event_times_locked`.
- `DELETE /v1/organizers/:id/events/:eventId` (`member`) → only a **draft** (`409 event_not_draft` otherwise); the
  dashboard confirms first (FR-1003). Audit `event.delete` with the event's name lengths only? No — names are not
  personal data; the audit `before` keeps `name_ar`/`name_en` for the record.
- `POST /v1/organizers/:id/events/:eventId/end` (`owner`) `{ confirm: true }` → `end_event_early` → 204; not live →
  `409 event_not_live`.
- Audit `event.create`, `event.update` (before/after of changed fields), `event.delete`, `event.end`.

### Times in the event's zone (FR-1728)

- `packages/shared/src/time/event-time.ts`: `formatEventTime(iso, timeZone, language)` → e.g. "Thu 23 Oct, 09:00
  (Riyadh time)" / "الخميس 23 أكتوبر، 09:00 (بتوقيت الرياض)", Western digits; zone label from a small map of common
  Gulf zones (Riyadh, Dubai, Kuwait, Doha, Bahrain, Muscat, Cairo) with the IANA name as the fallback.
  `eventDayOf(instant, timeZone, dayStartHour)` → the event day (`YYYY-MM-DD`) for FR-1714/1715: an instant before the
  day-start hour belongs to the previous day. Property tests over random instants and zones (DST zones included).
- The dashboard's date inputs are in the event's zone: the form sends local date-time plus zone; the API converts with
  the zone (no browser-zone guessing). `toInstant(localDateTime, timeZone)` in shared, tested around DST gaps.

### Web

- `/[lang]/organizers/:id/events`: list (name in the page's language with the other as fallback, status badge from
  `statusNow`, times in the event's zone), "New event" (hidden for a limited editor).
- `/[lang]/organizers/:id/events/new` and `/[lang]/organizers/:id/events/:eventId`: one form — kind, names AR/EN,
  venue AR/EN, dates (local to the chosen zone), time zone (common zones first, then all), event-day start hour,
  access, join methods (public list only when public). Delete (draft only) with a confirmation screen naming what is
  removed; "End now" for the owner when live, with a confirmation. Messages AR/EN.
- Home: each organizer card links to its events.

## Revision 2 (after CTO review 1, 86/100) — these override the sections above where they differ

- **M1, one status-aware guard** `BEFORE UPDATE OF starts_at, ends_at, timezone, day_start_hour` for `questify_app`,
  judged on `event_status_now(OLD…)`: draft → anything (CHECKs apply); scheduled → the new times must keep it
  scheduled (`starts_at > now()`); live → `starts_at`, `timezone`, `day_start_hour` locked and `ends_at` may only move
  later (shortening is `end_event_early`, owner only); ended/archived → all four locked. API answer `409
  event_times_locked`. Tests per branch, including an editor shortening a live event and the lag window (stored
  `scheduled`, `starts_at` past).
- **M2, draft-only delete in the database:** `event_delete` = `(member in scope AND status = 'draft') OR admin`. The
  API's 409 stays for a clear answer; a DB test proves a raw delete of a scheduled event touches 0 rows.
- **M3, `isTimeZone` as built (review 2, accepted):** an IANA shape with each part capitalised (`UTC` or
  `Area/Location…`), resolvable by the runtime, and not a case variant of what it resolves to; aliases that name the
  same clock are accepted (`Asia/Kolkata`, `US/Pacific`). **Not** `resolvedOptions().timeZone === name`: Node's ICU
  maps current names to legacy ones (`Asia/Kolkata` → `Asia/Calcutta`, `Europe/Kyiv` → `Europe/Kiev`), and
  `Intl.supportedValuesOf` lists only the legacy names (and no UTC), so equality would refuse valid zones. The cache
  fills only after acceptance (bounded). The API stores the name exactly as sent, never the runtime's resolved name.
  The pg trigger against `pg_timezone_names` stays the backstop. Tests: refused `asia/riyadh`, `ASIA/RIYADH`, `+03:00`,
  `EST`, `Asia/Nowhere`; accepted `Asia/Kolkata`, `America/Argentina/Buenos_Aires`, `Europe/Kyiv`, `US/Pacific`.
- **M4, join code:** upper case, 6 characters from the 31-character unambiguous alphabet, `INSERT … ON CONFLICT DO
  NOTHING RETURNING id` in a bounded loop (5); tested by seeding a code and stubbing the generator.
- Minor 1: INSERT by column grant (no `status`, `config_version`, `created_at`, `id`), not a trigger; `config` and
  `config_version` stay updatable (settings/store.ts).
- Minor 2: `end_event_early` requires `event_status_now(...) = 'live'`, `app_is_owner()`, `FOR UPDATE`.
- Minor 3: `event_status_now` is `STABLE`; it is the only source of the rule (no TypeScript copy); the API returns
  `statusNow` from SQL.
- Minor 4: the `event.delete` audit row is written before the delete (the audit policy needs the event); `before`
  keeps the names.
- Minor 5: deleting an event removes its id from editor limits that keep at least one event; an editor whose only event
  it was keeps the dangling id (sees nothing) rather than an empty or NULL limit.
- Minor 6: the merged access/join methods are validated in the API → 422 naming `joinMethods`, never a raw 500.
- Minor 7: the tick chains `setTimeout`, runs with no organizer context, is a `buildApp` option tests leave off, and
  `advance_event_lifecycle` does scheduled→live then live→ended in one call (CTEs feeding the audit rows); repeated
  `event.lifecycle_failed` gets a RUNBOOK line.
- Minor 8: a draft shows "Questify activates this event after payment" (AR/EN) beside its badge (FR-1017).
- Minor 9: QUALITY_BASELINE mutation scope gains the lifecycle functions' callers and the time helpers.
- Minor 10: the time helpers on Hermes go to OPEN_QUESTIONS until checked on a device (before T-113).
- API inputs: `starts_at`/`ends_at` are required on create, as `YYYY-MM-DDTHH:mm` (no `Z`, no offset), read in the zone
  of the same body or the stored zone; responses carry the instant (UTC ISO) and the zone; a PATCH cannot null them; a
  zone change without times keeps the instants. A limited editor gets `403 scope_limited` up front from the hook's
  membership, with the database as backstop.

## Build notes (Phases 2 and 3)

- Phase 2 code review: 92, GO. Folded in: `update` and `remove` lock the row on read (`readEvent(…, lock)`), so an edit
  is never built on a stale read and a draft cannot be activated between the check and the delete (the earlier
  rollback-carrying `Refusal` became dead code and was removed); the venue is in the audit view; the tick logs the
  SQLSTATE; API tests for the scheduled and ended guard branches and the stored-row 422s.
- Two bugs found by the tests and fixed: `toInstant` accepted impossible dates (30 February rolled into March; it now
  reads the date back), and `updateEvent` wrote back millisecond-precision times, which the guard saw as a change on an
  event whose times carry microseconds (an event ended early could not be renamed; a time sent back unchanged now keeps
  the stored value).
- Web: `organizerPage` (session and membership checks) and `OrganizerShell` (top bar, organizer name, error state) are
  shared by the team page and the three event pages. The edit form sends only what changed; a new zone or start sends
  the zone and both times, a new end alone sends only the end, so a live event's start never reaches its lock. One
  Idempotency-Key per distinct body: a retried request replays, a corrected one is new.
- Deviation: "New event" shows for every member. The session's memberships do not carry the editor limit, and a
  limited editor who tries gets the API's own explanation (`scope_limited`). Hiding it needs the limit in `/me`; worth
  doing if editors find it confusing.
