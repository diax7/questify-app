**Answer (ADR-234):** two kinds of tag. A **basic tag** (any NTAG21x sticker, the cheapest kind) holds a signed Questify
URL: it is exactly as strong as the printed quest QR (it can be copied), and the server flags a tap whose tag id is not
the one registered at writing (ADR-041: the system flags, people decide). A **secure tag** (NTAG 424 DNA, several times the price of a basic
one) signs every tap with a counter (AES-CMAC, SUN); the server verifies it with that tag's own keys and accepts each
counter once, so a copied or shared tap is **refused**. Basic tags ship in T-308, secure tags in T-308b. The quest's
QR is always on when NFC is (phones without NFC, a tag torn off). Both tags are written from staff mode on a phone;
the web dashboard never writes tags (F-105).

## Basic tags (T-308; ADR-234)

### What a tag holds

- One NDEF URI record: `{DASHBOARD_ORIGIN}/t/{token}`, `token` a signed code of a new purpose **0x06 `tag`** (the tag's
  id and its version, its own derived key, `createTagCodeKey` in `qr.ts`). 50 characters; with `https://questify.nafes.com/t/`
  it is about 80 bytes, which fits an NTAG213 (144 bytes). Nothing personal, nothing secret; the quest is found on the
  server, so a tag can be **moved to another quest of the same event** on the dashboard without rewriting it.
- A phone without the app (or a camera-less tap on iOS) opens the bilingual landing page `/[lang]/t/[token]` ("Tap this
  tag inside the Questify app, from the scanner"), as `/q/`. Opening the app straight from a lock-screen tap needs
  universal links and App Links, which wait with the join links (Q-070); noted in TASKS.

### Data (migration 0056)

- `nfc_tag (id uuid PK, organizer_id, event_id, quest_id, kind text CHECK (kind = 'plain'), uid bytea CHECK (length 4
  to 10), label text (0 to 40), locked boolean, version integer ≥ 1, status active|revoked, written_by → staff_assignment
  (SET NULL), written_at, revoked_at, revoked_by)`. Composite key `(quest_id, event_id)` → `quest (id, event_id)`
  RESTRICT (a single quest with tags is not deleted; the builder maps it to `409 tags_in_use`, Revoke first). At most 50 tags a
  quest and 2,000 an event (`NT409 limit_reached`). Unique `(event_id, uid) WHERE status = 'active'`: one active
  registration per physical tag (a rewrite of a registered tag revokes the old row in the same call). RLS forced,
  PUBLIC revoked, no grant: written only by its definers. Not deleted by the rehearsal wipe (a tag on a wall is
  organizer data). Deleting the event: RESTRICT would fail inside the event's own cascade, so the event-delete trigger
  deletes the event's `nfc_tap` and `nfc_tag` rows first, as `event_delete_goals` does (CTO 4).
- `nfc_tap (completion_id bigint PK → quest_completion ON DELETE CASCADE, organizer_id, event_id, tag_id → nfc_tag,
  uid_ok boolean NOT NULL, created_at)`: one row per tap that paid. CASCADE so the rehearsal wipe and account erasure
  remove it with its completion with no restatement (`wipe_rehearsal`, `erase_rows` unchanged; tested). T-308b adds its
  counter here. Closed table.
- `quest_verification_known` widened: `'nfc'` allowed on `scan_qr` only, and **only with `quest_qr`** (`NOT ('nfc' = ANY
  (verification)) OR 'quest_qr' = ANY (verification)`): the QR backup can never be switched off (FR-313). Column grant
  unchanged. `location` and `challenge` stay as they are (Q-199 asks about `location`).
- `quest_completion_method_check` widened with `'nfc'`. `flag_kind_check` widened with `'nfc_copy'`; index
  `flag_nfc_open ON flag (enrollment_id, kind) WHERE kind = 'nfc_copy' AND status = 'open'`.
- Shared registry (`packages/shared/src/quests/registry.ts`): `scan_qr.verifications` gains `nfc`; the builder refuses
  `nfc` without `quest_qr` (`422 invalid_quest {field: verification}`, the table is the second wall).

### Writing a tag (FR-312)

Staff mode, an operator of the event with `write_nfc` (an owner or editor writes only when also assigned as an operator),
the event not closed, the quest `scan_qr` with `nfc` on:

1. **Prepare** `POST /v1/operator/events/{eventId}/quests/{questId}/nfc-tags/prepare` → `{tagId, url}`: a fresh tag
   id and its signed URL (version 1). **Nothing is stored** (stateless, as an unsaved QR): an unconfirmed token opens
   as `unknown_tag`. At most 60 prepares and 60 confirms a minute per operator (CTO 8).
2. The app (`NfcTech.Ndef`; on iOS `[NfcTech.Ndef, NfcTech.MifareIOS]`, so Core NFC hands over the tag's id, CTO 2):
   reads the tag first. A tag already holding a Questify `/t/` URL of an active tag answers
   "This tag is already {quest}" (from step 3's refusal) and is not overwritten unless the operator confirms "Rewrite";
   a read-only tag answers "This tag is locked". It writes the URI record, reads it back, optionally locks it
   (`makeReadOnly`, the switch "Lock the tag" is **on** by default: a locked tag cannot be rewritten by a passer-by,
   and cannot be reused), and reads the tag id. Under the switch: "Locking is permanent: the tag can never be
   rewritten. A tag written for the wrong quest is moved on the dashboard" (CTO 7).
3. **Confirm** `POST …/nfc-tags {code, uid, label?, locked}`, **Idempotency-Key** → `201 {tagId, questId, replaced}`:
   `code` is the prepared token, opened again with `verifyTagCode` (a bare id is never taken, CTO 5);
   `register_nfc_tag` (definer) checks the operator, ability, quest and limits under the quest row's `FOR NO KEY UPDATE`
   (counts stay exact), revokes an active tag with the same `uid` in this event (`revoked_by` = the operator, audited
   `nfc_tag.revoke` with that tag's label and quest; `replaced` answers its label and quest, CTO 6),
   inserts the row, audits `nfc_tag.write` (operator, quest, label; never the uid in the audit text). A replay answers
   the first row. A uid already active in **another** event of the organizer is allowed (a tag is per event).
4. Success: "Tag ready for {quest}" with the label, and "It replaces {label} ({quest})" when `replaced` is set (CTO 6). Write failures (tag moved away, too small, not NDEF formatted,
   a write that read back wrong) are answered on the phone, nothing is stored, the operator taps again.

### Tapping a tag (FR-313, FR-621)

- **App**: the scanner (FR-621) reads NFC beside the camera. Android: reader mode (`NfcTech.Ndef`) while the scanner is
  open, so the tag never opens the browser there. iOS: a "Tap NFC tag" button in the scanner opens the system sheet
  (iOS has no silent foreground reading); the quest sheet's action "Tap the NFC tag" (FR-1742) opens the same.
  The app accepts only `/t/` URLs read from a tag, never a typed or shared link (as the live-camera rule, FR-303).
  On a phone without NFC (`NfcManager.isSupported()` false) the NFC button and hint are hidden and the quest shows its
  QR action only.
- **The tag id on iOS (CTO 2)**: the iOS read asks for `[NfcTech.Ndef, NfcTech.MifareIOS]` (NTAG21x is a MIFARE
  Ultralight family tag, whose `identifier` Core NFC exposes); "the iPhone sends the tag id" is a **gate** of the
  on-phone test. If it proves unreadable, the app sends `uid: null, uidReason: "platform"` from iOS only, the tap row
  stores `uid_ok = NULL` (not checked) and nothing is flagged. A future universal-link or background read (Q-070)
  never carries a tag id either: it sends `uidReason: "background"`, also `NULL`, never `uid_missing`.
- **API** `POST /v1/taps {code, uid: hex | null, uidReason?: "platform" | "background", position?}`, player, **Idempotency-Key**, optional `X-Device-Id` → the completion
  answer (`completionId, points, occurrence, score, balance, replayed, rank, levelUp, bonus, boost`) **plus `questId`**.
  `verifyTagCode` (strict, constant-time, as `verifyQuestCode`): `not_questify` and `forged` answer `422 invalid_proof`
  (forged logged apart, never the token text), counted by the wrong-proof throttle like a forged QR. Taps share the
  completion route's per-player and per-device limits (CTO 8).
- **Database** `tap_quest(tag uuid, tag_version integer, seen_uid bytea, request_key text, device uuid, reading jsonb)`,
  granted, `app_player_id()` required:
  1. reads the tag row (no lock) **whatever its status**; no row → `NT404 unknown_tag`;
  2. **replay first (CTO 1)**: if this player already has a completion under `request_key` in the tag's event, it calls
     `record_completion` with **that completion's** `quest_id` (not the tag's current one), which replays it; so a retry
     after a Revoke answers the paid tap instead of `unknown_tag`, and a retry after a Move answers it instead of
     `QK422`. Only otherwise: revoked or another version → `NT404 unknown_tag` (one answer, so an outsider learns
     nothing about other tags or tenants);
  3. calls `record_completion(tag.quest_id, me, 'nfc', NULL, NULL, request_key, device, NULL, NULL, NULL, tag.event_id,
     reading)`, which runs the wipe first, takes the enrollment lock, **re-reads the quest after the wipe**, replays a
     retry, runs `quest_open_check` and every cap (one door, no copy of its rules);
  4. on a fresh completion (not `replayed`): inserts `nfc_tap (completion, tag, uid_ok)` with `uid_ok = (seen_uid =
     tag.uid)`, or `NULL` for a `platform`/`background` reason; **and pays** (ADR-041: flags only). The tag's **copy
     count** (taps with `uid_ok = false`) is the main signal, on the Tags panel (CTO 9). The account gets an `nfc_copy`
     flag only from its **second** mismatch in the event (evidence `{taps: [{completion, tag, reason: uid_mismatch |
     uid_missing}]}`, newest 50), so one bad read never flags a player.
- `record_completion` restated (from 0055:255, one line in the method check): `(quest_row.type = 'scan_qr' AND
  proof_method = 'nfc' AND 'nfc' = ANY (quest_row.verification))`; `nfc` is boosted like a scan (`now`). Only
  `tap_quest` passes `nfc`; `complete_quest` keeps refusing it (`QV422 wrong_method`), so the method cannot be claimed
  without a tag row.
- A tap that read the tag just before a Revoke committed still pays (the tap's `nfc_tap` key takes `KEY SHARE` on the
  tag row, the revoke's `UPDATE status` takes `FOR NO KEY UPDATE`: no conflict, no wait). Accepted and tested.
- **The UID is told by the phone**: it catches a tag copied onto another blank sticker, a shared link opened outside a
  tap and a modified app that forgets it; it cannot stop a modified app that sends the right id. That is the honest
  ceiling of a basic tag, the same as a photographed QR (the dashboard says so: "Basic tag: can be copied like a
  printed QR"). Secure tags are the answer (T-308b).

## Store compliance

- **Apple**: NFC tag reading needs no special approval; the entitlement (NDEF, TAG) and `NFCReaderUsageDescription` in
  Arabic and English; the ISO 7816 select identifier is NXP's NDEF application id (no payment AIDs, 2.5.1 private APIs
  untouched). Reading is user-started (the sheet). The App Review demo event gets an NFC quest whose QR works for the
  reviewer (no tag needed; the review notes say "NFC is optional; every NFC quest also has its QR").
- **Google Play**: `android.permission.NFC` is a normal permission, no declaration form; `required="false"` keeps the
  app on phones without NFC. Data safety and Apple's privacy answers are unchanged: the tag id is the sticker's, not the
  player's, and is kept only beside the completion (`nfc_tap.uid_ok`, a boolean) and on the tag row.
- Configuration never downloads a feature: the quest's method is data, the reading code ships in the binary
  (STORE_COMPLIANCE gate, rules.md 7).

## T-308b — secure tags (split, ADR-235; design for its worker)

NTAG 424 DNA with Secure Unique NFC (SUN, NXP's Secure Dynamic Messaging). Built after Dhia answers Q-198; finished on
a phone once he has the tags.

### What a secure tag holds and how a tap is checked (ADR-236)

- The NDEF URL `{DASHBOARD_ORIGIN}/t/{token}?e={32 hex}&c={16 hex}`: the same 0x06 token (the tag's id) in the static
  part, then the mirrors the tag fills on every read: `e` = PICCData (tag byte 0xC7, the 7-byte UID, the 3-byte read
  counter) encrypted with AES-128-CBC (zero IV) under the tag's **meta-read key**; `c` = the SUN MAC: AES-CMAC with a
  session key `CMAC(fileReadKey, 3CC3 0001 0080 || UID || counter)`, over the empty input, its odd bytes (AN12196 §3).
  Encrypting the UID and counter keeps them off the URL, so a tag cannot be tracked across events.
- **Keys** per tag, **derived, never stored**: `key_n = HMAC-SHA256(NFC_SECRET, "questify/nfc/v1/{n}/{tagId}/{keyVersion}")[0..16]`
  for the master key (0), the file-read key (1), the meta-read key (2) and the unused keys 3 and 4 (all changed from
  the factory zero keys). A database dump holds no key; a tag's keys never leave the API process, never reach a phone,
  a log, an error, an audit row or a test snapshot (pino redaction gains `NFC_SECRET`; a test greps the logs). `NFC_SECRET`
  is a new secret (32+ characters, its own value, backed up apart from the database; the API refuses to start
  without it once T-308b ships). Rotating it re-personalises every secure tag (`key_version`), which the
  dashboard can do tag by tag.
- **Our own AES-CMAC** in `apps/api/src/nfc/cmac.ts` on `node:crypto` AES-128 (RFC 4493, about 40 lines), tested with
  RFC 4493's four vectors and AN12196's SUN example; no new dependency.
- **Replay (ADR-236)**: `nfc_tap.counter integer` (0 to 16,777,215), unique `(tag_id, counter)`; `nfc_tag.max_counter`.
  `tap_quest` (restated) for a secure tag: the API has decrypted and checked `e` and `c` and passes the counter;
  after `record_completion` (so the order stays rehearsal row → enrollment → tag), it takes the tag row `FOR NO KEY
  UPDATE` (enough: no key changes, CTO 10)
  and accepts the counter only if it was never used **and** is above `max_counter - 20` (the window lets taps that
  reach the server out of order at a busy station all pay); otherwise `NT409 tap_used` / `tap_stale` and the whole
  transaction (completion included) rolls back. Then `max_counter = greatest(max_counter, counter)`. A secure tag tapped
  with no `e`/`c`, a UID inside `e` that is not the registered one, or a bad MAC: `422 invalid_proof` (logged apart as
  forged). Result: **one physical tap pays at most one player once**; a copied tag cannot make a new signature; a
  harvested tap (read with another NFC app and sent on) is used once and dies after 20 newer taps. The tag still
  cannot tell who held the phone (Q-200).
- **Counter gaps (CTO 10)**: each accepted tap stores `gap` = counter minus the previous highest minus 1 (reads that
  never paid). Large gaps on a tag are shown on the Tags panel (harvested reads); a tap accepted 5 or more below the
  highest raises `nfc_copy` for the account (reason `stale_tap`), paid as every flag.
- **Keys only for the caller's tags (CTO 3)**: personalisation and re-personalisation derive a tag's keys only when
  its row is in the caller's event, or is revoked within the caller's organizer; any other tag (another tenant's, or
  an unknown token on a tag that is not factory-new) answers `unknown_tag`, so no one can take over another
  organizer's tag. Cross-tenant test: an operator of organizer B on organizer A's tag gets `unknown_tag` and no
  authentication step.
- **Kinds**: `nfc_tag.kind` widens to `'plain' | 'secure'`, with `key_version`, `max_counter`. The dashboard shows
  "Secure tag" and the counter; a quest can mix both kinds.

### Personalisation from staff mode, the phone as a relay (ADR-236)

- `POST /v1/operator/events/{eventId}/quests/{questId}/nfc-tags/secure` → `{tagId, apdu, state}` and `POST
  …/secure/step {state, response}` → `{apdu, state}` | `{done: {tagId}}`. The API runs the NTAG 424 DNA
  personalisation as a state machine (AN12196 §5): ISOSelect `D2760000850101`; AuthenticateEV2First with key 0
  (factory zero key; a tag that is already ours authenticates with its derived key, found by reading its token first);
  GetCardUID (encrypted); WriteData of the NDEF template with the URL and zeroed mirrors; ChangeFileSettings (SDM on:
  encrypted PICC data with key 2, MAC with key 1, the offsets of `e` and `c`, file read free, writes and changes by key
  0); ChangeKey 1 to 4, then key 0 last; a final ISOReadBinary of the NDEF that the API verifies as a real tap before
  `register_nfc_tag` stores the row with the UID. The phone only forwards bytes (`isoDepHandler.transceive`).
- `state` is sealed by the API (AES-256-GCM, a key derived from `NFC_SECRET` for `relay`): tag id, operator, quest,
  step, session keys, command counter, TI, UID, expiry 90 s. Nothing is stored between steps (no Redis, no table), a
  state cannot be replayed into another operator's session, and a lost tag mid-way leaves either a factory tag or one
  of ours (re-run with "Rewrite"; the key-0 change is last so the tag is never left with an unknown master key).
- **Interrupted personalisation (CTO 11)**: on a re-run each key slot is tried with the factory key, then with the
  derived one, so a tag stopped between two ChangeKey steps (some keys ours, some factory) finishes; tested with a
  tag stopped after each step.
- About ten round trips, each a few milliseconds on the server; Core NFC's 60-second session limit and the 90-second
  state expiry bound it. Tests drive the state machine with AN12196's published personalisation values (fixed RndA).

## Proposed decisions and questions

- **ADR-234** NFC tags: two kinds. A basic tag (any NTAG21x) holds a signed Questify URL of its own (purpose 0x06, the
  tag id; the quest is looked up on the server, so a tag can be moved), is as strong as the printed QR, and a tap whose
  tag id differs from the one registered at writing is flagged and paid (ADR-041). A secure tag (NTAG 424 DNA, SUN)
  signs every tap and is verified on the server; a copied or reused tap is refused. NFC is offered on scan quests only,
  always with the quest QR on (phones without NFC); written from staff mode on a phone, never from the web; a locked tag
  by default. Answers Q-071; amends ADR-040's "Not chosen: secure NFC tags" (Q-198).
- **ADR-235** T-308 is split: T-308 builds basic tags end to end; T-308b builds secure tags and their personalisation,
  after Q-198, finished on a phone once tags are bought.
- **ADR-236** Secure tags: keys per tag derived from `NFC_SECRET` and the tag id (never stored, never on a phone,
  never logged); personalisation with the phone as a byte relay and a sealed, 90-second state; our own AES-CMAC (RFC
  4493); encrypted UID and counter in the URL; each counter accepted once and only above the tag's highest minus 20.
- **ADR-237** The NFC library is `react-native-nfc-manager` v4 (Expo config plugin, development build) with no second
  NFC or crypto module (`react-native-ntag-424` rejected: one author, a second native crypto module, keys in the app).
  The Android NFC feature is declared not required.
- **Q-198** Secure tags (NTAG 424 DNA, several times the price of a basic sticker; written from staff mode) refuse copied and reused taps.
  ADR-040 had left them out; may T-308b build them? If yes, buy a pack (10 or more) for testing.
- **Q-199** Basic tags: a tag that seems copied is flagged and still pays (flags only, as everywhere else), and NFC is
  offered only on scan quests, always with their QR. Agree, or refuse copied basic tags, or allow NFC on location
  quests too?
- **Q-200** Secure tags: each tap pays one player once; a tap read with another app and passed on still pays once and
  stops working after 20 newer taps on that tag. Agree with 20?
