# T-509: Cheers (plan note)

Tier B (ADR-355): a cheer pays no points, touches no sign-in or tenant-isolation logic and shows no player. The owner's doors run
behind `award_event_of`; the player's door reads only the caller's own enrollment. Delivers FR-1841 (F-343). Migration **0090** (new,
undeployed; CranL runs through 0088, 0089 is deploying). Choices: **ADR-377 / Q-344 (Proposed)**.

## What exists and what this adds

- The `cheers` feature key was already in the registry (`gated: false`), so the event and the platform switches compose as for every other
  feature; `feature_enabled(ev, 'cheers')` in the database reads both. T-509 puts the event's switch on the **Big screen page** (the
  event menu is full), beside the owner's moment controls, through the existing `PUT …/cheers` switch route.
- **A cheers moment** is one row per event (`cheers_moment`): started by the owner for 1 to 30 minutes, replaced by the next start (which also
  clears the last moment's cheers), ended by Stop or by time. It needs the big-screen add-on, a live event and the Cheers switches on.
- **A cheer** is an append-only row (`cheer`: event, enrollment, reaction, time). The database counts a player's cheers in the last 60 seconds
  under a per-player advisory lock, so the limit (30 a minute) holds under any number of taps at once and across servers.
- **The big screen:** a live moment makes `big_screen_running` return `['cheers']` alone (the owner chose it; the finale and the picked scenes
  come back when it ends). `screen_cheers()` answers the end, the five counts and the newest 40 cheers as sequence number and reaction only; the
  page floats the ones it has not shown (polling at 3 seconds, ADR-365; no stream).
- **The app:** the live read (`GET /v1/events/{id}/live`, ADR-221) carries `cheers: {endsAt} | null`. It is read apart from `live_state`: one
  cached event-level question (`event_has_cheers`, 3 seconds, as `event_has_live`), then the per-player door `member_cheers` only while the event
  has a moment. The Home card shows five emoji buttons, a countdown and the rest after a 429.

## Care points

- No free text anywhere: the body is one of five names; the database's CHECK and door refuse anything else.
- A stranger, a removed member, a team seat and a device all get the same refusal; `member_cheers` answers null to them.
- Nothing on the screen or in a team door names a player; the cheer rows go with the enrollment (deletion, rehearsal wipe) and the event.
- Turning the switch off, removing the add-on or the event ending ends the moment at once (`cheers_live_until` is asked by every reader).
- A tap is not idempotent on purpose: it pays nothing and the limit bounds a retry storm.

## Not in this task

- A live counter in the app (the wireframe review said "may"); art for the reactions (the platform's emoji stand in, Q-344).
- A per-event limit or length setting; the limit is 30 a minute for every event.

## Mutation globs

None required (not tier A).
