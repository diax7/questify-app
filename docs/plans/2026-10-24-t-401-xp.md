# T-401 — Questify XP ledger and levels

Delivers FR-414, FR-415, FR-416, FR-706, FR-1602 (the XP half, owed by T-207) and FR-407's level-up beat; FR-721
partly (the level-up is recorded; the item itself is T-402's, see ADR-182). **Core bar** (a ledger): one Opus plan
review, one Opus code review, mutation on GitHub. Migration **0039**. Depends on T-105 (done).

Dhia is away: the open choices are my recommendation, written as **Proposed** ADR-179 to ADR-182 and Q-145 to Q-148.

## The shape (ADR-179): XP follows the event ledger by trigger, in its own rows

Every writer of a quest credit (`record_completion`: the player's scan, an operator's My QR scan, the team's quest
award) and every removal (`remove_award`) already goes through one `INSERT INTO ledger_entry`. So XP is written by an
`AFTER INSERT` trigger on `ledger_entry`, not by each writer: no path can pay event points and forget XP, and later
writers get it for free.

- `kind = 'quest'`, not `rehearsal`: one credit per (player, quest), ever. `INSERT … ON CONFLICT DO NOTHING` on a
  unique key, so a repeat, a refresh, a race between two scans or a retry gives nothing (FR-414; "Done when": a repeat
  gives no second XP).
- `kind = 'removal'` reversing a quest entry that paid XP: one reversal row (unique on the reversed credit). The quest
  stays used (ADR-152), so it never pays XP again (FR-1602, the T-207 note).
- Any other kind (`award`, `welcome`, `redeem*`, `handover`): no XP. Spending never touches XP (FR-415): no XP column
  is ever read by a shop path, and no XP price exists.

## Tables (deny by default; no write grant to the API role)

| Table | Columns | Notes |
|---|---|---|
| `player_xp` | `player_id` PK → `player`, `xp` bigint ≥ 0, `level` smallint ≥ 1, `updated_at` | The running total and its level (a cache of `xp_entry`). Made for every player by a trigger on `player` insert; backfilled for existing players. SELECT for the API role only through definers |
| `xp_entry` | `id`, `player_id` → `player_xp`, `delta` (≠ 0), `source` (`quest`, `removal`), `ledger_entry_id` → `ledger_entry` RESTRICT, `reverses` → `xp_entry` NULL, `quest_id`, `created_at` | Append-only for every role (the 0012 trigger pattern). Unique (player_id, quest_id) WHERE source = 'quest'; unique (reverses) WHERE source = 'removal'. CHECK: quest → delta > 0, reverses NULL; removal → delta < 0, reverses set |
| `level_reached` | `player_id` → `player_xp`, `level`, `xp_entry_id`, `reached_at`; PK (player_id, level) | The first time each level was reached; never removed. T-402 grants one item per row (FR-721: two levels at once → two rows → two items) |
| `xp_level` | `level` smallint PK (1–30), `xp_from` bigint | The curve, seeded (ADR-180). Readable; written only by a Questify admin (T-709 edits it, FR-1403) |
| `level_title` | `level_from` smallint PK, `name_ar`, `name_en` | Titles per range (FR-706), seeded (ADR-181) |

The XP per quest is `platform_setting` key `xp` `{"questXp": 100}` (seeded), read in SQL with the same fallback. It is
**not** in `features`/`tuning`, so the public config never carries it (the amount stays hidden, FR-414). T-709 edits it.

## The trigger (`grant_quest_xp`, SECURITY DEFINER, ≤100 lines)

1. Skip unless `kind IN ('quest', 'removal')` and not `rehearsal`; find the player from the enrollment.
2. Quest: insert the credit (`questXp`) ON CONFLICT DO NOTHING; nothing inserted → done.
   Removal: find the credit whose `ledger_entry_id = NEW.reverses`; none → done; insert `-delta` ON CONFLICT DO NOTHING.
3. `UPDATE player_xp SET xp = xp + delta, level = xp_level_of(xp + delta)`; insert `level_reached` for every level
   from the old level + 1 to the new one, ON CONFLICT DO NOTHING. A drop recalculates the level; the rows (and so the
   items) stay (FR-1602).

**Lock order.** The writers lock the enrollment, then the trigger updates `player_xp`. `erase_player` locks `player`
FOR UPDATE, then enrollments; it never touches `player_xp`. `xp_entry` and `level_reached` point at `player_xp`, not
at `player`, so their foreign-key checks never wait on the player row: no cycle with a deletion. Two completions in
two events serialize on the one `player_xp` row. A deleted account keeps its XP rows on the tombstone (no personal
data; ADR-175's table gains a row).

## Backfill (in the migration)

`player_xp` for every player; one credit per (player, quest) from the earliest non-rehearsal `quest` entry; a reversal
for each of those removed; totals, levels and `level_reached` from the result (reached_at = now). Tested on a seeded DB.

## Reading it (API, app)

- `GET /v1/me` gains `questify: {xp, level, levelFrom, nextLevelAt (null at the top), title: {ar, en}}` via a definer
  `own_level()`. PATCH answers the same.
- `POST /v1/quests/{id}/complete` gains `levelUp: {level, title} | null`: the highest `level_reached` written by this
  credit (so a replay answers the same). The XP amount itself is never sent (hidden, FR-414; Q-146).
- Operator scans and the team's quest award pay XP too; the player sees the new level on their next profile load.
- App: Profile shows the level, the title (Arabic or English) and an XP bar from `levelFrom` to `nextLevelAt`; the
  scan result plays a **medium** level-up celebration after the points (FR-407; Reduce Motion respected). Strings in
  `messages.ts` (Arabic checked with `ux-araby`), RTL bar, Western digits. "The next level's reward" (FR-416) shows
  once T-402 has items; until then the bar shows the next level only (Q-147).

## Tests (test first)

- **Database** (`apps/api/test/db/xp.int.test.ts`): first completion pays `questXp`; a repeat (repeat_cap 3), a
  replay with the same key, and two concurrent scans pay once; an award, a welcome and a redeem pay none; a rehearsal
  completion pays none; a removal reverses exactly once and the quest never pays again; a drop across a level keeps
  `level_reached`; a jump of two levels writes two rows; an operator scan and a manual quest completion pay; XP in two
  events sums into one level; `questXp` changed by an admin applies to the next credit; erase_player racing a
  completion (no deadlock, both orders); append-only (UPDATE/DELETE refused for the owner role); backfill.
- **Security**: outsider and cross-tenant suites list the new tables and definers (no grant; an organizer reads no XP).
- **Route/unit**: `/v1/me` and the completion `levelUp`; the shared level helper; the app's Profile bar and the
  celebration choice. Browser: none (no web screen). `expo export`.
- Mutation (GitHub): the new `src` modules only (`apps/api/src/xp/**`).

## Proposed decisions and questions

- **ADR-179** XP by trigger on the event ledger, one credit per (player, quest), reversals by removal; own tables.
- **ADR-180** 100 XP per quest; 30 levels, level n from `50·(n−1)·(n+2)` XP (L2 200, L5 1,400, L10 5,400, L30 46,400):
  about one level per two quests at first, a full event of ~20 quests reaches level 5. Q-145.
- **ADR-181** Titles per five levels: مستكشف Explorer, مقتفي الأثر Pathfinder, مغامر Adventurer, صائد الكنوز Treasure
  Hunter, بطل Champion, أسطورة Legend. Q-148.
- **ADR-182** XP on repeats and difficulty-based XP are not built now (ADR-083: later switches); FR-721's item and
  ADR-046's level-up gems wait for T-402/T-404, which read `level_reached`. Q-147.
- **Q-145** the amount and the curve; **Q-146** never show the XP gained per quest, only the bar and level-ups;
  **Q-147** the bar without a reward until T-402; **Q-148** the title names.
