# T-302 — Vote and quiz quests

Delivers FR-207 (vote), FR-208 (points for each right answer), FR-209 (one try, the right answer after answering),
FR-210 (a timer per question) and FR-1629 (vote options are the organizer's own; moved here from T-301). **Core bar**
(both types pay through the completion engine and the ledger): one Opus plan review, one Opus code review, mutation on
GitHub. Migration **0041**. Depends on T-105 (done) and reuses T-301's open checks and payment path.

Dhia is away: the open choices are my recommendation, written as **Proposed** ADR-190 to ADR-195 and Q-156 to Q-159.

## Scope (ADR-190)

- **Vote options are text only for now.** Organizer images need a Questify bucket (Q-149, the same block as T-301b);
  the option shape keeps room for an image key later. FR-1629 holds by construction: options exist only in the quest's
  config, written by the builder from the organizer's typed text; no route takes a submission id, and no definer that
  serves options reads `submission` (`own_submissions` and `event_submissions` stay the only readers).
- **"Enter-a-code variants": no new work.** FR-211 shipped with T-105; where the code is shown (slide, speaker, push) is
  the quest's existing `hint`. A typed-answer quiz question is not in v1 (Q-156).
- **Results to players are not in T-302.** The team sees vote counts; showing results to players (after voting, at
  close, never) is F-100's live poll (T-306), which builds on this vote type (ADR-195).

## Config (shared registry, `QUEST_TYPES`; the database holds the same rules in CHECKs)

| Type | `type_config` | Rules |
|---|---|---|
| `vote` | `{options: [{id, text: {ar?, en?}}]}` | 2 to 10 options; each id a short unique string made by the dashboard; text 1 to 120 characters in at least one language (FR-1008). `repeat_cap = 1`. Points are `quest.points`, paid on voting |
| `quiz` | `{questions: [{id, text: {ar?, en?}, choices: [{id, text}], right}], timerSeconds}` | 1 to 20 questions; 2 to 6 choices each, exactly one right (`right` names a choice id); question text up to 300, choice text up to 120; `timerSeconds` null or 5 to 300 (one timer for every question, FR-210). `repeat_cap = 1`. `quest.points` is the points **per right answer** (ADR-191) |

`quest_type_known` widens to `vote` and `quiz`; `quest_completion.method` gains `vote` and `quiz`. Players never read
`type_config` (the member quest list does not return it); options and questions reach them only through the definers
below, which never return `right` before the player has answered or the question has closed.

**Edits after the first vote or attempt (ADR-194):** text may change (a typo fix); the ids, the number and order of
options, questions and choices, the right answers, the timer and the points are locked. The builder refuses with
`quest_locked` (checked in `src/quests/builder.ts` and in SQL, the `has_completions` pattern T-301 widened).

## The quiz (ADR-191 to ADR-193)

- **One attempt per player and quiz.** `quiz_start` creates it (or answers the open one: resuming is allowed) after
  `quest_open_check` (active member, live phase, visible, open window, audience, an operator who may play). The points
  per right answer are frozen on the attempt at start (as ADR-184 froze a submission's points).
- **The server serves one question at a time** (`quiz_next`): the first unanswered one, in order. Serving stamps
  `served_at`; the question's deadline is `served_at + timerSeconds + grace` (grace 2 s for the network, a tuning number,
  Q-157). A player cannot see question k+1 before question k is answered or closed. Between questions there is no clock:
  the player may read the right answer and go on when ready.
- **One try (FR-209):** `quiz_answer(quest, question, choice)` locks the attempt; the question must be the one served;
  a second answer to it is `409 already_answered` (the same choice again replays the first answer). It answers `right`
  and `rightChoiceId` at once. Past the deadline the answer is refused (`409 question_closed`) and the question counts
  as closed with no points; `quiz_next` closes an overdue question the same way before serving the next (FR-210), and
  the closed question's right answer is then shown.
- **Payment at the end (ADR-193):** when the last question is answered or closed, the attempt finishes in the same
  transaction: right answers × the frozen points, as **one** `quest_completion` (method `quiz`, key `quiz:<attempt id>`,
  reserved like `sub:`) and one `quest` ledger entry, through `pay_completion` (T-301's `pay_submission` body made
  general, so score, balance, XP and the shop window follow one path). **No right answers: no completion and no entry**
  (FR-208); the attempt is `finished` with 0 and the quest shows as done (`member_event_quests.done` also counts a
  finished attempt).
- **An abandoned attempt** is finished by `finish_due_quizzes(size)` in the lifecycle tick once the quest closes or the
  event leaves `live`: it pays the right answers already given, with the approval's re-checks (player and enrollment
  active, event live or ended, results not final; else `void`, no points) and the balance only while the shop is open
  (FR-1710). Its completions skip burst flags (`raise_completion_flags`, as a reviewer's approvals) and mark the ranking
  for repair. Until then the app offers "Resume quiz".

## The vote

`vote_quest(target, option, request_key)`: `quest_open_check`, the option must be in the config, one vote per player and
quest (`409 already_voted`), then the completion (method `vote`, `quest.points`) and the vote row in one transaction.
A replayed key answers the first result.

## Tables (deny by default: no API grant; reads and writes through definers; tenant foreign keys, RESTRICT)

| Table | Columns | Notes |
|---|---|---|
| `quest_vote` | `organizer_id`, `event_id`, `enrollment_id`, `quest_id`, `option_id`, `completion_id`, `created_at` | PK (enrollment_id, quest_id) |
| `quiz_attempt` | `id` bigint, `organizer_id`, `event_id`, `enrollment_id`, `quest_id`, `status` (`open`, `finished`, `void`), `points_each`, `right_count`, `completion_id` null, `started_at`, `finished_at`, `idempotency_key` | unique (enrollment_id, quest_id); `completion_id` set ↔ finished with right_count > 0 |
| `quiz_answer` | `attempt_id`, `question_id`, `choice_id` (null: closed unanswered), `right`, `served_at`, `answered_at` | PK (attempt_id, question_id) |

Account deletion (`erase_rows`) deletes the player's `quest_vote` and `quiz_answer` rows (choices are personal data in
the store forms; vote counts drop, ADR-195); attempts stay for the ledger's sake. The rehearsal wipe deletes all three
for rehearsal accounts before `quest_completion`, and counts them.

## Functions (each REVOKEd from PUBLIC; only entry points granted to `questify_app`; each calls `ensure_rehearsal_wiped`)

Player: `vote_quest`, `member_vote(quest)` (options and my choice), `quiz_start`, `quiz_next`, `quiz_answer`,
`member_quiz(quest)` (status, total, answered questions with their right answers, right count, points, the served
question with `secondsLeft`). Team (owners and editors in scope; operators not): `quest_vote_counts(event, quest)`.
System: `finish_due_quizzes(size)`. Internal: `pay_completion`, `finish_quiz`, `quiz_config_locked`.

## API (API.md)

`GET /v1/quests/{id}/vote`, `POST /v1/quests/{id}/vote {optionId}` (Idempotency-Key; answers like a completion:
`{completionId, points, score, balance, levelUp, rank, replayed}`). `GET /v1/quests/{id}/quiz`, `POST …/quiz/start`,
`POST …/quiz/next`, `POST …/quiz/answer {questionId, choiceId}` (each Idempotency-Key; the answer that finishes the
quiz carries `completionId`, `points`, `levelUp`, `rank`). Team: `GET /v1/organizers/{org}/events/{id}/quests/{qid}/votes`.
The routes call `ranking.afterCompletion` when a completion was paid. Refusals: 403 `quest_not_open` /
`enrollment_inactive` / `operator_play_off`, 404, 409 `already_voted` / `already_answered` / `question_closed` /
`already_completed`, 422 `not_vote_quest` / `not_quiz_quest` / `unknown_option` / `idempotency_key_reused`. Every
string in `messages.ts` (Arabic via `ux-araby`), RTL checked, Western digits.

## Proposed decisions and questions

- **ADR-190** Scope: text vote options now (images with the bucket, Q-149); no new enter-code work; results to players
  in T-306. Q-158.
- **ADR-191** Quiz shape: multiple choice, one attempt, points per right answer frozen at start, questions served one at
  a time. Q-156.
- **ADR-192** The timer runs on the server from serving, with a 2-second grace, and only while a question is open. Q-157.
- **ADR-193** One payment at the end; zero right pays nothing; an abandoned attempt is paid at the quest's close with the
  approval's re-checks. Q-159.
- **ADR-194** After the first vote or attempt, only text may change.
- **ADR-195** Vote counts for the team only; votes and quiz answers are deleted with the account. Q-158.
