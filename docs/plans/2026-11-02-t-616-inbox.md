# T-616 - Owner reports: the Inbox (plan note, tier B)

Delivers FR-1825 (F-327). Decisions: ADR-401 and Q-368 (Proposed). Migration 0110. No change to points, sign-in or tenant
isolation: one read-only counts door behind the same `award_event_of` check as the control room.

## What it builds

One dashboard page, **Inbox** (`/organizers/{o}/events/{e}/inbox`, Run group), that composes what already exists; no second
ticket, flag or request store.

- **Counts by kind** as equal tiles, each number a link to the list it counts: questions, problems, prize problems and player
  reports (the Help desk's Open tab filtered by the same kind, so a count and its list always match), with Questify (the
  escalated ones), join requests (only for an event that takes requests or holds some), submissions and flagged activity.
- **Reported players** and **oldest prize problems** cards: the five oldest open requests of that kind (the Help desk's own read,
  `GET …/tickets?status=open&kind=…&limit=5`), "View more" to the Help desk list past five, a line that says nothing is waiting
  when there are none. Reply, Solved and Escalate stay on the Help desk; each row links there.
- **Join requests** card: the existing panel (Accept, Decline, Accept all) as a card of five, "View more" to the Players page.
- The Help desk opens on a tab and a kind from its address (`?status=open&kind=prize`), which is what a count links to.
- The control room's Inbox counter links here instead of the Help desk.

## The one new read

`event_inbox(event)` (migration 0110): a jsonb of counts, `SECURITY DEFINER`, opening with `award_event_of` (AN404), PUBLIC holds
no EXECUTE. Counts only; the API checks the answer against a strict schema. Two indexes make the walks index only:
`ticket_event_open_idx (event_id, queue, kind) WHERE status = 'open'` and `flag_event_open_idx (event_id) WHERE status = 'open'`.
Join requests use `enrollment_requests_idx` (0036), submissions `submission_queue_idx` (0040).

## Personal data

Nothing the owner cannot already read on the Help desk and the Players page: a sender's and a reported player's @username, the
request's text cut to one line, the time. No full name (T-615): the existing reads give usernames, and this page adds no read of
the name. No contact detail.

## Measured (50,000-player event, 12,000-player neighbour, 16,000 tickets, 6,000 open flags, 4,000 pending submissions, 2,000 requests)

Before the two indexes the ticket and flag counts were sequential scans (6.6 and 5.6 ms, and growing with the platform) and the
function took 30 to 40 ms. With them every count is an index scan: tickets 2.1 ms, requests 0.8 ms, submissions 1.4 ms, flags
1.5 ms; `event_inbox` 13 to 17 ms warm. Nothing is cached.
