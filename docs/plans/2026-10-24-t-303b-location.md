# T-303b — Location check-in quests with the QR fallback, the prompt's timing, far-from-venue and impossible-speed flags

Delivers FR-215, FR-216, FR-1744 (F-86) and FR-331, FR-332 (F-114). Split from T-303 by ADR-196; FR-331 and FR-332
moved here from T-209 by ADR-153. **Core bar**: it changes the completion payer (`record_completion`) and its player
door (`complete_quest`), and it handles personal data (location): one Opus plan review, one Opus code review, mutation
on GitHub. Migration **0048** (0042 to 0047 are undeployed but belong to finished tasks; this task adds its own file).
Depends on T-303 (`play_quest`, the type pattern), T-209 (`flag`, `raise_completion_flags`, `flag_detail`).

Dhia is away: the open choices are my recommendation, written as **Proposed** ADR-206 to ADR-208 and Q-170 to Q-172.

**CTO plan review 2026-10-24: 82/100, findings folded in** (the position kept in its own closed table, not on
`quest_completion`, which the API role and organizers read; `location` added to 0046's two refresh triggers; a bad
position never blocks a QR or code scan; one "Continue" button that always leads to the system prompt; what a
check-in proves stated plainly; a per-quest check-in limit instead of the shared wrong-code buckets; the database log
guard covers every parameter-logging setting; no phantom redact paths; server-receipt times and the speed evidence
defined; the Arabic purpose string and Expo's localized InfoPlist strings).

**What a check-in proves** (ADR-206): only that **the phone claimed to be here**. Latitude, longitude, age, accuracy
and the mocked mark are all reported by the client; a rooted phone or a tampered request can claim any point. The
speed flag on quest pins (which needs no phone position) is the stronger guard, and the far-from-venue flag catches
only careless fakes. For prizes that matter, the organizer should use the QR at the spot (or a staff-confirmed
challenge). The quest builder says so beside the type.

Fixed points: location is optional and never the price of points (ADR-015, STORE_COMPLIANCE rule 3, Apple 5.1.2(i));
read only while the app is open, never in the background (ADR-072); personal data stays in Saudi Arabia and out of
logs, errors and push text (hard rule 3); flags never block play (FR-329).

## Data minimization first (ADR-206)

- **No coordinates are stored anywhere.** The phone's position reaches the database only as a function argument;
  SQL turns it into rounded distances (10 m) and keeps those, plus the reported accuracy and Android's "mocked" mark.
  The organizer's flag page needs "how far, how sure", never the point on a map.
- **Its own closed table** (CTO 1): `quest_completion` cannot hold it, since 0012:116 grants the API role SELECT on
  the whole table and the policy at 0012:118 lets the organizer's team read every column. `completion_position
  (completion_id bigint PRIMARY KEY REFERENCES quest_completion (id) ON DELETE CASCADE, organizer_id, event_id,
  enrollment_id, accuracy_m integer NOT NULL, mocked boolean NOT NULL, venue_distance_m integer, created_at)`, tenant
  FKs as `quest_completion`; RLS enabled and forced, `REVOKE ALL … FROM PUBLIC`, **no grant to `questify_app`**, no
  policy: only the definers below write or read it. The cascade removes it with its completion (the rehearsal wipe);
  erasure deletes the player's rows.
- **No parameter logging in the database** (CTO 7): Postgres writes bound parameters to its log when
  `log_parameter_max_length` (statements logged by `log_statement` or `log_min_duration_statement`; default -1, all)
  or `log_parameter_max_length_on_error` (default 0) allow it. A DB test asserts `log_parameter_max_length_on_error =
  0` and either `log_parameter_max_length = 0` or (`log_statement = 'none'` and `log_min_duration_statement = -1`),
  so a later change is noticed. Both are superuser settings: before the switch goes on, the coordinator confirms
  CranL's values (`SHOW …` on the CranL database) and records them in the RUNBOOK; if CranL logs statements with
  parameters, the switch stays off until it is changed.
- The phone sends a position only with a request that uses it: a location check-in, and the player's own QR scan or
  typed code (the moments a far-from-venue reading means something). No periodic upload, no track, no background.
- In the API the position is a body field (never a header or query, which proxies log). The server's request log
  writes method and URL only (`app.ts:119` serializer) and never bodies, so no redact path is added (CTO 8). Instead a
  route test sends a malformed and an out-of-area position and asserts that neither the error answer nor the zod
  issue text nor the logged error contains the numbers (zod messages are mapped to field names only).

  `venue_radius_m integer NOT NULL DEFAULT 1000 CHECK (venue_radius_m BETWEEN 100 AND 20000)`; added to the event
  builder's column grants (0009:41-44). Optional for every kind; no activation rule (an event without a pin simply

- `quest.place_lat`, `place_lng` (same type and checks), `place_radius_m integer CHECK (BETWEEN 20 AND 2000)`; all

  (`quest_place_types`), and **required** for `location`. Added to the quest builder's column grants. Later T-506
  (maps) may read it; nothing here draws a map.
- Deny by default: the pins are the organizer's data on tables already closed to `PUBLIC`; the player's position
  lives only in `completion_position` (above), closed to every role but its definers.

## The location quest type (FR-215, FR-216)

- `quest_type_known` gains `location`; `quest_verification_known` gains `type <> 'location' OR verification =
  ARRAY['quest_qr']` and `location` joins the "may have a verification" list; `quest_verification_default` gives it
  `['quest_qr']`. So **every location quest has its QR at the spot**, by the database's own check (FR-216): the QR
  is printed and rotated exactly as a `scan_qr` quest's (every `'scan_qr'` test in the QR print and rotate paths
  becomes "uses the quest QR", read from the shared registry's `usesQuestQr`).
- Shared registry (`packages/shared/src/quests/registry.ts`): `location: {usesQuestQr: true, verifications:
  ["quest_qr"], oneTry: false, config: strictObject({})}`; `location` joins `REFRESHING_QUEST_TYPES` (a daily
  check-in at a spot behaves like a daily scan). Repeat caps as `scan_qr`.
- **The database's refresh rule too** (CTO 2): `quest_refresh_type` (0046:73) and `category_refresh_type` (0046:89)
  hard-code `('scan_qr', 'enter_code', 'challenge')`; both are made again (`CREATE OR REPLACE`, same lock) with
  `location` added and the message "only scan, code, challenge and location quests…". A DB test puts a location quest
  in a daily category and switches a category holding one to daily; both pass, and a survey still fails.
- **The builder's note** (CTO 5): beside the type, "A check-in trusts the phone's reported position. For prizes that
  matter, ask players to scan the QR at the spot." in both languages.
- **Platform switch** `locationQuests` (`level: "platform"`, ADR-208): off until Dhia has updated the App Store privacy
  label and Play's Data safety form (ADR-073's blocking step). Off: the builder refuses the type (`QF403
  location_off`, the share pattern of 0042:398), existing location quests still complete by QR, the app never asks
  for or reads location, so no far-from-venue flag can arise. The speed flag needs no location reading and works
  either way.

## Completing a location quest

- `complete_quest` (latest 0030:295) is dropped and made again with a 7th parameter `reading jsonb DEFAULT NULL` and
  accepts `proof_method IN ('qr', 'code', 'location')`; `REVOKE ALL … FROM PUBLIC` and `GRANT EXECUTE … TO
  questify_app` on the new signature in the same statement group (deny by default; the outsider suite lists it).
- `record_completion` (latest 0047:327; its 0046 period counting and 0047 `lock_quest_items` before the insert copied
  unchanged) is dropped and made again with a 12th parameter `reading jsonb DEFAULT NULL`, `REVOKE ALL … FROM
  PUBLIC` repeated. Every existing caller passes 11 arguments and keeps working (PL/pgSQL resolves the call at run
  time); only `complete_quest` passes a reading. A DB test calls each existing payer once after the migration.
- `position_of(reading jsonb)` (internal, IMMUTABLE, `REVOKE ALL … FROM PUBLIC`): `{lat, lng, accuracyM, ageS,
  mocked?}` → a record, or NULL when the shape is bad (out of range, accuracy not 0 < a ≤ 10000, age not 0 ≤ s ≤
  86400, extra keys) or the fix is older than 120 s. It never raises: **a bad position never blocks a QR or code
  scan** (CTO 3). Only `proof_method = 'location'` turns a NULL into a refusal (`QV422 bad_position` for a bad shape,
  `stale` for an old fix, `no_position` when absent). `distance_m(lat1, lng1, lat2, lng2)` (haversine on a 6371008 m sphere, IMMUTABLE, revoked). No PostGIS:
  a dependency for one formula is not worth it.
- The proof gate gains `(quest_row.type = 'location' AND proof_method = 'location')`, and `qr` widens to `type IN
  ('scan_qr', 'location')`. For `location`, before any count is read:
  - no reading → `QV422 no_position`; `ageS > 120` → `stale`; `accuracyM > 500` → `imprecise`;
  - `distance > place_radius_m + least(accuracyM, place_radius_m)` → `QV422 not_here`, DETAIL the distance rounded
    to 10 m (the player's own number: "you are about 140 m away"). The accuracy allowance is capped at the radius, so
    a coarse fix never passes a far player.
  - A mocked reading inside the area pays (flags never block play) and raises a flag (below). ADR-206, Q-170.
- With a usable reading (any proof) `record_completion` inserts one `completion_position` row right after the
  completion: accuracy and, when the event has a venue pin and is not virtual, `venue_distance_m` (rounded to 10 m),
  and the mocked mark. A bad, stale or absent reading stores nothing and the scan pays as today. A replay ignores the
  reading and answers the first completion.
- In the API (CTO 3): for `qr` and `code` the optional `position` is parsed leniently (an invalid one is dropped to
  `null` before the database, never a 400); only `proof.type = "location"` validates it strictly (`422
  location_refused {reason: bad_position}`).
- Rate limit (CTO 6): refused check-ins do **not** use the wrong-code buckets (`complete.ts:186-206`, which guard
  typed codes); a new per-player-and-quest bucket allows 10 refused check-ins per 10 minutes (`429
  too_many_attempts`), enough for a player walking towards the spot, too few to map the radius by script.

## The flags (FR-331, FR-332; ADR-207)

- `flag.kind` gains `far_from_venue` and `impossible_speed`; `CREATE UNIQUE INDEX flag_location_open ON flag
  (enrollment_id, kind) WHERE kind IN ('far_from_venue', 'impossible_speed') AND status = 'open'` (one open case per
  account and kind, as `flag_burst_open`). Evidence keeps T-209's shape `{"completions": [ids]}`, the newest 50.
- `flag_tuning()` is dropped and made again with the new numbers (OUT parameters changed): `far_margin_m 1000`,
  `speed_mps 15` (54 km/h), `speed_min_gap_m 300`, beside `burst_count`, `burst_window`. Console numbers in T-703.
- **Far from the venue** is raised by a new `raise_position_flags()` (definer, `REVOKE ALL … FROM PUBLIC`), AFTER
  INSERT on `completion_position`: the position row is written after the completion, so `raise_completion_flags`
  cannot see it. Only when the event is not virtual (FR-1744) and the completion is not manual or system-paid:
  `NEW.mocked` OR `NEW.venue_distance_m - NEW.accuracy_m > venue_radius_m + far_margin_m`. Upsert the open case
  (`ON CONFLICT (enrollment_id, kind) WHERE … DO UPDATE` the evidence and `last_seen_at`, the burst pattern). A
  refused location (no reading, so no row) can never match: no flag.
- `raise_completion_flags` (latest 0041:860) keeps its first lines (manual and system-paid completions raise nothing)
  and the two T-209 detectors unchanged, then, only when the event is not virtual:
  - **Impossible speed**: when NEW's quest has a place, find the player's latest earlier counted completion (not
    manual, not system-paid) at a quest with a place; `gap = distance(places) - r1 - r2`; flag when `gap >=
    speed_min_gap_m` and `gap / greatest(seconds, 1) > speed_mps`, with both completion ids. Uses quest pins only, so
    it needs no phone location and works with location refused. An operator's station scan counts (the player stood
    at that station).
  - Both read only the player's own rows, under the enrollment lock every payer already holds (record_completion's
    FOR NO KEY UPDATE, pay_completion's callers); no new lock and no lock order change (0047: enrollment, items,
    redemption; the trigger runs after `lock_quest_items`).
- `flag_detail` (latest 0047:800, same output, `CREATE OR REPLACE`): the completions branch adds, per completion,
  `distanceM`, `accuracyM`, `mocked` (far) and, for speed, the quest place's distance and the seconds between the
  pair (`gapM`, `seconds`). Never a coordinate. Definitions (CTO 9): `distanceM`, `accuracyM`, `mocked` come from
  the completion's `completion_position` row (NULL when none); `gapM` and `seconds` are computed **per completion
  against the same player's previous counted completion at a placed quest** (edge-to-edge distance of the two places,
  seconds between their `created_at`), NULL for the first. `created_at` is the server's receipt time, so a retry
  delayed by a bad connection can bunch two scans; the reviewer sees the seconds and decides (Q-171).
- **Erasure** (`erase_rows`, latest 0047:1240): beside `device_id = NULL`, deletes the player's `completion_position`
  rows. **Rehearsal**: the wipe deletes completions (the positions cascade) and flags; its JSON is unchanged.
  Retention past the event is Q-075's (the distances follow the event's data); written into Q-171.

## The app (FR-1744)

- `expo-location` (Expo's own module, the SDK 57 version from `npx expo install`; justified: no other way to read
  location), its config plugin with `locationWhenInUsePermission` only, no "Always" string, no background mode;
  `ACCESS_BACKGROUND_LOCATION` added to `blockedPermissions`. Purpose string, worded for both uses (ADR-072):
  - EN: "Questify uses your location while the app is open to check you in at quest spots and to keep the game fair
    at your event. You can always scan the QR code instead."
  - AR: "يستخدم Questify موقعك أثناء فتح التطبيق لتسجيل حضورك في أماكن المهام وللحفاظ على عدالة اللعب في فعاليتك.
    يمكنك دائمًا مسح رمز QR بدلًا من ذلك."
  - How Expo localizes it (context7, Expo app config `locales`): the plugin's `locationWhenInUsePermission` holds the
    English text; the key `NSLocationWhenInUseUsageDescription` goes under `ios` in `apps/app/locales/en.json` and

    Checked on a build by reading the generated `ar.lproj/InfoPlist.strings`.
  - STORE_COMPLIANCE's row (line 353, the pre-ADR-072 "only when you start a location quest" wording, both languages)
    was replaced with these texts in this plan's commit; PD-09's row is updated in the build.
- **When it asks** (ADR-208, CTO 4): never at launch. Apple rejects a pre-permission screen with a "Not now" exit or
  an "Allow"-worded button under 5.1.1(iv) ("the user should always proceed to the permission request after the
  message"; Apple Developer Forums, 2026; HIG Privacy: one button, clearly leading to the system dialog). So the app's
  explanation sheet has **one button, "Continue"**, that always opens the system prompt; no close, no "Not now". It is
  shown when the player taps "Check in" on a location quest, or once per install right after joining an in-person
  (`physical` or `workplace`) event that has a venue pin. After a denial, the quest sheet shows "Scan the QR at this
  spot" and a link to the system settings; Android may ask again from the "Check in" tap (the OS decides). Nothing
  else in the app changes (FR-216's second case).
- **Reading**: on a check-in, `getCurrentPositionAsync` (high accuracy, 8 s timeout; on timeout the sheet offers the
  QR). On a QR scan or typed code, the last known position no older than 120 s, never a fresh fix: a scan is never
  delayed by location. Approximate-only permission (iOS reduced accuracy, Android coarse) works for the flags; a
  check-in then answers `imprecise` and the sheet says "Turn on precise location or scan the QR".
- The location quest sheet: the title, points, "Check in here" button, the QR option always visible beside it, the
  answers `not_here` ("You're about 140 m from the spot"), `stale`, `imprecise`, `no_position`. Strings in
  `messages.ts` (Arabic via `ux-araby`), RTL checked, Western digits. Virtual events: no prompt ever.

## API (API.md)

- `POST /v1/quests/{id}/complete`: `proof` gains `{type: "location", position}`; `qr` and `code` accept an optional
  `position`. `position: {lat, lng, accuracyM, ageS, mocked?}`. New answers: `422 location_refused {reason:

  sent to players.
- Flags: `kind` gains `far_from_venue | impossible_speed`; the detail's completion lines gain `distanceM`,
  `accuracyM`, `mocked`, `gapM`, `seconds`.

## Proposed decisions and questions

- **ADR-206** Location check-in: a `location` quest has a required place (pin and radius) and always its own quest QR
  (DB check, FR-216). A check-in proves only that the phone claimed to be there (every value is client-reported); the
  speed flag on quest pins is the stronger guard, and for prizes that matter the organizer uses the QR. It passes when
  the fix (no older than 2 minutes, accuracy 500 m or better) is within the radius plus its accuracy, the allowance
  capped at the radius; a mocked fix inside pays and is flagged. No coordinates are stored: only rounded distances,
  accuracy and the mocked mark, in a table no API role can read, erased with the account. The position travels only
  with a check-in, a QR scan or a typed code, in the body; a bad one never blocks a scan. Q-170.
- **ADR-207** Location flags: `far_from_venue` (the fix, less its accuracy, beyond the venue radius plus 1 km, or a
  mocked fix; raised when the position row is written) and `impossible_speed` (two completions at placed quests more
  than 300 m apart, edge to edge, faster than 15 m/s, by server receipt time; raised by `raise_completion_flags`), one
  open case per account and kind, never in a virtual event, never from a manual award; the numbers live in
  `flag_tuning` until T-703. Q-171.
- **ADR-208** Asking and the switch: never at launch; one explanation sheet with a single "Continue" button that
  always opens the system prompt, shown on tapping "Check in" or once right after joining an in-person event with a
  venue pin. A platform switch `locationQuests` stays off until the store privacy answers are updated (ADR-073) and
  CranL's parameter logging is confirmed off; off, nothing reads location and existing location quests complete by QR.
  Q-172.

## Build notes (2026-10-23)

- `position_of` returns the numbers of any well-shaped reading, age included; the callers judge the age, so a check-in
  answers `bad_position` and `stale` apart (CTO build note 1). A stored reading must also be at most 2 minutes old.
- The check-in limit is reserved before the database is asked, under the player's advisory lock, as `reserve()` does
  for typed codes; a check-in not refused for its position gives it back. A parallel-requests test covers it (CTO 2).
- The location numbers live in their own `location_tuning()`; 0031's `flag_tuning` is untouched (coordinator).
- `not_here`'s distance travels in the error's HINT; the API maps it to `distanceM`.
- Home's event carries `locationPrompt` (in-person with a venue pin); the app explains once only when Home is opened
  from a join (`?joined=1`), never at launch. The platform switch is read from the event's composed config.
- Older builds: see ADR-208's amendment; this build offers the QR for any unknown type that keeps one.
