# T-106 — Ranking: a live sorted ranking per event, ties, exclusions, the on/off switch, rebuild from the ledger

Delivers FR-606, FR-607, FR-609, FR-318 (with FR-1014), and FR-1612 in part (the switch exists; the big-screen scene
list that hides it is T-6xx). Depends on T-105 (the ledger). Core quality (rankings decide rank prizes): Max.
ADR-118 (Accepted 2026-10-20): Redis now.

## Scope note

- **Builds:** the ranking order (score, then who reached that score first), a Redis sorted set per event kept current
  after each completion and rebuilt from PostgreSQL, a PostgreSQL fallback with the same order when Redis is down or
  the set is being rebuilt, `GET /v1/events/{id}/ranking` (top 10 plus the caller's own row, ADR-052), exclusions
  (banned or removed players, banned accounts, the organizer's own team), the `ranking` feature switch and an owner
  route plus dashboard switch to turn it off and on.
- **Not built here:** the exclusion list of phones and email domains and the ban flows (T-208, which depends on this and
  calls `removeFromRanking`); operators' exclusion (with the operator tasks); today's ranking (FR-1611, F-61, Should);
  the big-screen scene list (FR-1612's hiding, with the big screen); rank prizes (T-6xx); live push of rank changes
  (`/stream`, later); the Event Home ranking card (T-113).
- **Reuse:** the ledger and its trigger (0012), `withEvent`-style owner checks, the settings service's
  `saveEventSwitches` (T-007, never wired to a route), the lifecycle tick pattern, the route inventory and the
  outsider and cross-tenant suites.

## Decisions (tactical; for the CTO to challenge)

1. **Order:** score descending, then the ledger entry that last changed the score, ascending ("reached that score
   first", FR-606). Ledger ids are assigned under the enrollment's lock, so for one player they increase in commit
   order, and across players they follow insertion order. No clock is involved (a transaction's `now()` is its start
   time and could reorder commits). New column `enrollment.score_version bigint` (the id of that ledger entry), set by
   `apply_ledger_entry` when `score_delta <> 0`; backfilled from the ledger. Exactly one holder per rank, always.
2. **Who is ranked (FR-609, FR-318/1014):** an enrollment is ranked when its score is above 0, the enrollment is
   `active`, the player is `active`, and the player is not on the organizer's team: no `player_contact.email` equals the
   email of a staff user who is a member (owner or editor) of the event's organizer. A team member who plays by phone
   is caught by T-208's exclusion list (recorded there). One SQL function, `ranking_eligible(enrollment)`, holds this
   rule for every reader.
3. **Redis layout (ADR-118):** per event, `rank:{event}` is a sorted set whose score is the points and whose member is
   `{inverted version, 19 digits}:{enrollment id}`. Equal points sort by member, so the lowest version (reached first)
   comes first in reverse order; ranks need no float packing and points keep their full range. A hash
   `rank:{event}:member` maps enrollment to its current member, and `rank:{event}:built` marks a complete set. One Lua
   script upserts only when the new version is higher than the stored one, so late or repeated writes cannot move a
   player back.
4. **Writes:** after `complete_quest` commits, the API reads the enrollment's score, version and eligibility in one
   query and runs the upsert (or a removal when no longer eligible). Redis gets 250 ms; a failure or timeout never fails
   the completion: the event is added to `rank:dirty` (or, when Redis itself is down, the next read finds no `built`
   marker) and the repair tick rebuilds it within 5 seconds (the Done-when).
5. **Rebuild:** read every ranked enrollment of the event from PostgreSQL (one definer function), write it into
   `rank:{event}:next`, then `RENAME` over the live key and set `built`, so readers never see a half-built set. Taken
   under a Redis lock per event (`SET NX PX`), so two copies of the API do not rebuild at once. Triggered by: a read
   that finds no `built` marker, the tick for `rank:dirty` events (every 2 seconds), and a runbook command.
6. **Reads:** `GET /v1/events/{id}/ranking` (player route; the caller must hold an active enrollment in the event; the
   `ranking` feature must be on for the event, else 404 `ranking_off`): top 10 and the caller's own row
   `{rank, username, score, isMe}`, plus `total` (ranked players). Usernames come from a definer
   (`ranking_rows(event, enrollment ids)`) that returns only ranked rows of that event, because a player cannot read
   other players' rows directly. Each row is re-checked for eligibility as it is read; a stale member found ineligible
   is removed from Redis and the event marked dirty, so a ban shows at once. **Fallback:** when Redis fails or the set
   is not built, the same answer comes from PostgreSQL (`ranking_top` and `ranking_position` definers using the same
   order and an index on `(event_id, score DESC, score_version)` for ranked rows). Never a 500 because of Redis.
7. **The switch (FR-607):** a new registry feature `ranking` (not gated, on by default). `PUT
   /v1/organizers/{org}/events/{event}/features {ranking: boolean}` for the **owner** only (FR-607 says the owner;
   editors get 403), audited through the existing `saveEventSwitches`; the dashboard's event page gets a switch with
   both languages. Turning it off hides the ranking from players (the route answers 404 `ranking_off`); the sorted set
   keeps updating, so turning it back on shows current ranks at once.
8. **Configuration:** `REDIS_URL` required in production; optional in development and tests (the fallback serves). The
   client is `redis` (node-redis 6.3.0, the official package, ADR-118), with a connect timeout of 2 s, a command
   timeout of 250 ms, and no offline queue (a down Redis fails fast to the fallback).
9. **CI:** a Redis service container in the one job (`redis:8-alpine`, pinned by digest as compose.yaml already is);
   `TEST_REDIS_URL` for tests. zizmor before committing the workflow change.
10. **Deny by default:** the new definers are `SECURITY DEFINER SET search_path = public, pg_temp`, `REVOKE ALL FROM
    PUBLIC`, `GRANT EXECUTE TO questify_app`; `ranking_rows`, `ranking_top` and `ranking_position` refuse unless the
    caller (`app_player_id()`) holds an active enrollment in the event, or the caller is a member of its organizer
    in scope, or an admin; the rebuild list is for the system context only (no player, no staff: the worker). Outsider
    and cross-tenant suites cover them.

## Tests

- Database: order and ties (equal scores ranked by who reached first, one holder per rank); `score_version` set only
  when the score changes and backfilled; eligibility (banned enrollment, banned player, removed, left, team member by
  email, score 0); each definer refuses another event's player and an outsider; the search-path test covers them.
- Ranking module against a real Redis: upsert ordering, a late write with an older version ignored, removal, rebuild
  swaps atomically and gives the same order as PostgreSQL (the Done-when: delete the key, rebuild, compare), the
  rebuild lock, the fallback when Redis is stopped (a client pointed at a closed port) gives the same answer.
- HTTP: the ranking route (top 10 plus own row, own row when outside the top 10, ties, a banned player gone at once,
  the team member absent, not enrolled 403, ranking off 404, Redis down still 200), the feature route (owner only,
  audit), the completion flow updating the ranking within the request and the repair tick within 5 seconds after a
  Redis write failure.
- Web: the switch on the event page (e2e, both languages).
- Mutation scope: the new ranking module and routes.

## Revision 1 (after CTO plan review 1, 82/100) — overrides the sections above where they differ

- **Keys** use Redis hash tags so multi-key scripts stay valid in cluster mode: `rank:{<event>}` (the sorted set),
  `rank:{<event>}:member` (enrollment → stored version, 19 fixed-width digits, or `x` + 19 digits for a removal
  tombstone), `rank:{<event>}:built`, and while a rebuild runs `rank:{<event>}:next`, `rank:{<event>}:next:member`,
  `rank:{<event>}:building` (TTL = the lock's). Every key of an event carries one TTL of 30 days, refreshed on write
  (rebuildable data; an ended event's keys expire). Versions are compared in Lua as fixed-width strings; the inverted
  member text is built in Node with BigInt (n1).
- **M3, removal tombstones:** removing a member deletes it from the set and writes `x{version}` into the member hash
  (the enrollment's current version). The upsert script refuses any version not higher than the stored one, tombstones
  included, so a late upsert from before a ban cannot bring the player back. Unbanning (T-208) marks a repair, and the
  rebuild rewrites the hash.
- **M1, rebuild under writes:** a rebuild (under the lock) 1) clears the event's repair mark, 2) sets `building`,
  3) reads PostgreSQL, 4) writes each entry into `next` through the same versioned upsert, 5) swaps in one script:
  `next` and `next:member` over the live keys (or, with no ranked players, deletes the live keys: m1), sets `built`,
  deletes `building`. While `building` exists, every upsert and removal is applied to both the live and the `next` keys
  by the same script, so a write that commits after the read lands in `next` and wins by version; nothing is lost.
- **M2, a durable repair mark in PostgreSQL:** table `ranking_repair (event_id PK, marked_at)`, forced RLS, no grants;
  written by `mark_ranking_repair(event)` (definer, for the API when a Redis write fails) and by triggers on every
  eligibility change: `enrollment.status`, `player.status` (the player's events), `player_contact.email` (the player's
  events), `organizer_member` insert and delete (the organizer's live events). The repair tick (every 2 s) claims
  marked events and rebuilds them; a failed rebuild marks again. A backstop rebuilds every **live** event every 5
  minutes, bounding any staleness a lost signal leaves (a crash between commit and upsert). `removeFromRanking` (the
  immediate removal) stays for T-208, but correctness does not depend on it.
- **M4, the switch route:** `PUT /v1/organizers/{org}/events/{event}/ranking {enabled: boolean}`, owner only (FR-607),
  through a new `saveEventSwitch(actor, event, key, value)` that merges one key into the stored switches inside the
  locked transaction (the existing `saveEventSwitches` replaces the whole map). Test: polls off, toggle ranking, polls
  still off.
- **m2, eviction:** the RUNBOOK requires `maxmemory-policy noeviction`; at start the API reads it (`CONFIG GET`) and
  logs a warning when it is something else or cannot be read. CranL's TLS (`rediss://`) is a deploy check in the
  RUNBOOK.
- **m3:** after a completion commits, the API reads `ranking_entry_of(completion)` (a definer in the system context:
  event, enrollment, points, version, ranked) on its own connection: one extra round trip, no rewrite of
  `complete_quest`.
- **m4:** `ranking_eligible` is a plain `LANGUAGE sql STABLE` function (inlinable), executable by no one but the
  owner; the team check is an anti-join.
- **m5:** a top-10 member found ineligible at read time is removed (tombstoned), the event marked for repair, and that
  request is answered from the PostgreSQL fallback.
- **m6:** the completion answer gains `rank` (the player's place after the upsert, `null` when not ranked or Redis
  failed); API.md says so.
- **m7:** node-redis 6.3.0 (2026-09-30, the current stable) checked from the installed package's typings (context7 was
  unreachable): `commandOptions.timeout`, `disableOfflineQueue`, `socket.connectTimeout`, `reconnectStrategy`; a test
  proves a down Redis rejects at once.
- **m8:** the rebuild lock is `SET NX PX 30000` with a random token, released by a compare-and-delete script; two
  rebuilds after an expired lock are harmless because both go through the versioned rule (a comment says so).
- **m9:** `ranking_position(event)` finds the caller's own enrollment from `app_player_id()`; `ranking_rows` is called
  only with ids read from Redis, never ids from a client (ADR-052; a comment says so).
- **m10:** a caller who is not ranked (0 points, or excluded) gets `me: null`; tested.
- **n2:** the migration notes that the order relies on the ledger identity's default `CACHE 1`. **n3:** the old index is
  dropped. **n4:** readers are the event's active players only (staff and admin readers come with the dashboard or big
  screen, T-504).
- **ARCHITECTURE** line on "the last known ranking during a rebuild" is updated: the exact PostgreSQL order is served.
- **Tests added:** a rebuild under concurrent upserts equals PostgreSQL; a late upsert after a removal is refused; a
  Redis write timeout while Redis lives is repaired within 5 s; a new team member disappears after the repair tick; an
  empty event rebuilds; toggling ranking keeps the other switches.

## Build notes

- **Phase 1 review (2026-10-21): 92 GO.** Folded in: `mark_ranking_repair` callable only by the system or a player of
  the event (with a test); the comment on inlining corrected.
- **Fallback cost at 20,000 ranked players** (local PostgreSQL 17, 3 runs, warm): per-row eligibility made
  `ranking_position` and `ranking_entries` take 1.7 s each, so the rule now also exists in set form
  (`ranked_enrollments(event)`: one anti-join on `organizer_team_players`), with a test that both forms agree on every
  row, and the reader check is computed once per call. After: `ranking_position` 48–60 ms (the Redis-down path only),
  `ranking_top` 13 ms, `ranking_rows` (10 ids) 25 ms, `ranking_entries` (a rebuild's read) 105–130 ms.
- **For later tasks:** a change of `staff_user.email` sends no repair signal (no route changes it today; the task that
  adds one adds the trigger, and the 5-minute backstop bounds it meanwhile). Rank prizes (T-6xx) decide winners from
  PostgreSQL (`ranking_entries` order), never from Redis, so ended events need no repair.
