# T-804 - Load test at 20,000 completions a minute per event, ten events at once (plan note, tier B)

Quality gate for NFR-002, NFR-003, NFR-005 and NFR-025, and the sign-in rush named in T-804's note. Design in ADR-660;
how to run it in the RUNBOOK, "Load test". Results in STATE.md and T-804's line.

- **Where:** `ops/load/` (orchestrator, drivers, the schedule, statistics and report, with unit tests) and
  `apps/api/test/load/` (the load API and the seeding script, test code that imports the API's modules, bundled by the
  run with the API's esbuild).
- **What runs:** the product's app in its own process with production's pool of 10, Redis options, background ticks and
  request logs; SMS, email and push stubbed. Local PostgreSQL and Redis only; a throw-away database dropped in `finally`.
- **Seed:** set-based SQL, 10 organizers with one live event each, 20 scan quests and one probe quest per event, 2,500
  players per event with a phone and an enrollment; sessions from `issue_player_tokens` in one statement.
- **Measure:** open schedule (latency from each request's due time), 60 s after a 10 s warm-up; statuses; ranking
  freshness through a probe player per event; the database's written rows against the answers; PostgreSQL time per
  function; API, PostgreSQL and client CPU. Rush: stepped rates of new phones through `POST /v1/auth/code`.
- **If the PC cannot reach the target:** record the highest sustained rate and the bottleneck, tick nothing, and name the
  rerun step.
- **Checks:** unit tests for percentiles, the schedule and the verdict; lint, types, `lint:limits`, `format:check`. No
  app code changes, so no full suite.
