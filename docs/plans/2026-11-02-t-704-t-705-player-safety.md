## 2. Common rules for every admin action (all three builds)

- Route under `/v1/admin/` (404 to non-admins), door re-checks `app_admin_id()`, row lock on the target, `Idempotency-Key`
  on every write. **(review)** Reads that answer personal data (player search, contact reveal) are POST routes **without**
  an Idempotency-Key and outside the in-memory idempotency store: the store would keep full contacts in memory and a
  replay would hand a contact out again without a fresh audit entry. Each call is a new read with its own audit entry
  (and, for a reveal, its own D2 row).
- **Reason required:** `reasonCode` from a fixed list per action (bilingual labels) **plus** a note 10-300 characters,
  cleaned (control and direction characters refused, as T-702). The note is internal unless stated.
- **Audited** in `audit_log`, actor admin, **ids and codes only** (player id, action id, event id, reason code). Notes and
  usernames live in the new `player_admin_action` row (D2), which erasure deletes; the audit log, which survives
  erasure, never holds a contact, a username or free text about a player.
- **Rate-limited per admin** (`holdBack`, new `BUCKETS`, names `^[a-z_]{1,32}$`): search 30/min, record and ledger reads
  120/min, contact reveal 20/hour, rename and reset 30/hour, ban and lift 20/hour, queue actions 120/hour, word edits
  60/hour, flags list 60/min.
- **Personal data:** contacts masked everywhere (`+9665•••••12`, `a•••@gmail.com`) unless revealed (section 3). No
  birth year, no join answers, no full name. Phone and email searches go in a **POST body**, never the query string,
  so no access log or proxy log holds them. Errors echo no input.
- **Deny by default (rules.md rule 2):** every new table RLS forced with no grant; every new function `REVOKE ALL FROM
  PUBLIC` in the same group, EXECUTE to `questify_app` for doors only; definers pin `search_path = public, pg_temp`;
  audited reads are VOLATILE. Outsider and cross-tenant suites extended for each new object.

**D2 `player_admin_action`:** id, player_id, admin_id, kind (`rename|reset_sign_in|ban|lift_ban|contact_reveal`),
reason_code, note, created_at, plus `from_username`/`to_username` for renames. Append-only by trigger (the 0016
pattern, deletable only inside erasure with `app.erasure`). It is the record's "Questify actions" section.

## 3. T-704 - player tools (migration 0118)

**Find a player** - `POST /v1/admin/players/search {by: username|phone|email, q}` -> door `console_player_search`.
Username: folded prefix, at least 3 characters, 20 results. Phone: normalized to E.164 (`normalize.ts`), exact match.
Email: lowercased, exact match. No wildcard on contacts (no enumeration). Tombstones are never returned (no username,
no contact). Result rows: id, username, avatar, status, created_at, masked contacts. Audit `console.players_search`
with `by`, count and the ids shown, never `q`.

**Read-only record** (FR-1774) - `GET /v1/admin/players/:playerId` -> `console_player_record`, one audit
`console.player_read` (player id, sections). Sections: profile (username, avatar, status, created, level and XP),
masked contacts, username history (FR-1702, with `admin` rows marked), events (event and organizer name, enrollment
status, score, joined, event ban), flags naming the player's enrollments (kind, state, event; T-209 rows), report
tickets naming the player (count and state per event; the text stays the team's), active session count, Questify
actions (D2), marketing consent (existing route), and **(review)** when the contacts last changed (the newest
`player.contact_change` audit entry of T-108, with its channel and kind, never the value), so support sees a recent
contact swap before acting on a "this is my account" request. No edit controls on any of it. A tombstone record says "Deleted" and
offers nothing (FR-1776: no restore action exists, tested). Points record: `GET .../ledger?eventId&cursor` ->
`console_player_ledger` (kind, points, quest or reward name, time, actor **kind** only; ledger notes not shown), 50 a
page, audited `console.player_ledger_read`. Every look is logged (task's Done when).

**Contact reveal** - `POST .../contact {reasonCode, note}` -> `console_player_contact` returns the full phone and email,
writes a D2 row (`contact_reveal`) and audit `console.player_contact_read`. Needed only to answer a verified support or
legal request; T-708 reuses it.

**Change username** (FR-1775) - `POST .../username {username, reasonCode, note}` -> `admin_rename_player(target, name,
reason_code, note, request)`. Rules (D3):
- Same character CHECK, folding, uniqueness and word lists as players (`username_taken`, `username_blocked` answered).
- Not bound by the player's change window, and does not use it up: the player may choose a new name at once (still
  checked). `username_history.reason` gains `admin`; `rename_player`'s window keeps counting `rename` rows only.
- **The old name is retired** (D4): new table `username_retired (fold text PRIMARY KEY, retired_at)`, no player id,
  written with `ON CONFLICT DO NOTHING` **(review)** so a name retired twice (two players over time) is one row;
  `username_blocked` is restated to also refuse a retired fold, so neither the renamed player nor anyone else takes an
  offensive name back. Sign-up and rename pick this up without being restated. The console's word-list page can
  un-retire (T-705).
- Target must be `active` or `banned` (a tombstone has no name). Lock the player row `FOR UPDATE` (races the player's own
  `rename_player`, which locks the same row).
- **The player is told:** a personal notice through T-501's center, new kind `username_changed`, fixed bilingual
  template with no name and no reason ("Questify changed your username because it broke the rules. You can choose a
  new one in your profile."). Push text carries no personal data (rule 3).
- Abuse: reason required, 30/hour per admin, every rename in D2 and audited; the ranking cache picks the new name up on
  its next read (names are read through `ranking_rows`, not cached; verify).

**Reset sign-in** (D5) - `POST .../reset-sign-in {reasonCode, note}` -> `admin_reset_player_sign_in`. The admin never
sees, sets, sends or relays a code, a contact or a token. One transaction:
1. lock the player row `FOR NO KEY UPDATE` **(review)**: it never waits for a token insert's foreign-key check (`FOR KEY
   SHARE` on the player), so a sign-in or a refresh holding its own rows can always finish;
2. delete the player's live `player_login_challenge` rows (by their contacts), `player_contact_challenge` and
   `player_deletion_challenge` rows, first, so a sign-in that already holds its challenge finishes before the next step
   reads the sessions;
3. revoke every refresh token with **one UPDATE by player id** **(review)**, then every access token the same way, and
   delete the player's push devices (and their queued sends) so a lost phone stops receiving pushes;
4. set `player.tokens_valid_after = clock_timestamp()`, taken last (section "Race (D6)");
5. the API, in the same transaction and the admin seat, reads the player's contacts, computes
   `contactThrottleKey` for each and deletes their `playerCodeContact` and `playerFailContact` rows; address and
   install buckets are never cleared (SMS-pumping stays bounded). **(review) Why the failure counter is cleared too:**
   the usual reason for a reset is a player locked out by wrong codes (theirs, or a stranger's guesses at their number);
   keeping `playerFailContact` would leave them locked out for up to a day after support acted. The guesses it allows
   again are bounded: 3 tries per code, the per-address failure window stays, and a reset costs an admin a reason, an
   audit entry and one of 30 an hour;
6. D2 row and audit `player.reset_sign_in` (ids, count of ended families).
The only way back in is a fresh one-time code sent to a contact already on the account: that is the re-verification.
**No takeover path:** no route sets or changes a contact for a player, nothing returns a code, and reset only removes
access. A person who lost every contact cannot be helped into the account (documented; they start a new account).
**Race (D6), restated after the review.** The first draft had every token issuer take the player row `FOR SHARE`; the
review found the deadlock in it (a rotation holds its refresh row and waits for the player, the reset holds the player
and waits for the refresh row). Instead, a cutoff: `player.tokens_valid_after` (no grant). `player_session_owner`
accepts an access token only when `session.created_at > tokens_valid_after`, and `rotate_player_refresh` refuses
(`invalid`, family revoked) a refresh row with `created_at <= tokens_valid_after`. No issuer takes a new lock. Rows are
stamped with their transaction's start (`now()`), and the cutoff is taken with `clock_timestamp()` after the reset's
deletes and revokes, so:
- a sign-in or rotation that **started before** the cutoff issues rows dated before it: refused at their first use,
  whether it committed before or after the reset (a rotation that held its refresh row while the reset waited on it
  leaves a successor the UPDATE could not see; the cutoff kills it);
- one that **started after** the cutoff either waits on a row the reset already changed (the challenge it deleted, the
  refresh row it revoked) and then finds it gone or revoked, or proves a fresh code sent after the reset began, which is
  the way back in.
Tested in both orders for sign-in and refresh, with the second transaction held on a lock (no sleeps, no flake); and
two resets at once. T-705's ban uses the same cutoff.

**Merge accounts: dropped from v1 (D7, Dhia agreed 2026-11-02).** Under the append-only rule a merge cannot move rows: `ledger_entry`,
`xp_entry`, `gem_entry`, `audit_log`, `username_history`, `achievement_earned`, frozen `final_rank`/`result_place` are
append-only or frozen, and enrollments are unique per (player, event) with completions unique per (enrollment, quest).
The only legal form is compensating entries (debit one account, credit the other), which cannot carry completions,
achievements, items, streaks or results, and double-counts anyone who played one event on both accounts (a rank-prize
abuse path). That is not "points, items and history combined" (FR-1775's acceptance) and is a new ledger kind on the
core. Supported path instead: the player deletes the unwanted account in Settings (T-217, its points are forfeited),
then adds its phone or email to the kept account with Change contact (T-108). Same call as organizer merge (Q-375).

**Console web (T-704):** menu "Players": search (one box, a By select), result rows, the record page with sections,
the ledger table with event filter, Reveal contact (reason dialog), Change username and Reset sign-in (confirmation
screens per ADR-063 with reason code and note). Arabic and English, RTL, Western digits, phone and computer layouts.

## 4. T-705 - ban, block, word lists

**Platform ban** (FR-1416, FR-1417, FR-1606; D8) - `POST /v1/admin/players/:playerId/ban {reasonCode, note}` and
`.../lift-ban {note}` -> `admin_ban_player`, `admin_lift_ban`. Never automatic: only these doors set or clear `banned`
(source grep test plus a catalog test that no trigger or job writes `player.status = 'banned'`).
- **Reason the player sees (D9):** a code from `cheating | abuse | spam | prize_fraud | terms`, shown in fixed Arabic and
  English text; the admin's note is internal. Stored as `player.ban_action_id` (FK to the D2 row; no API grant).
- **Ban, one transaction:** lock `FOR UPDATE`; refuse `already_banned` and tombstones; `status = 'banned'`; the reset
  steps 2-3 of section 3; queue `ranking_repair` for each event where the player has an active enrollment (the 0019
  pattern) so cached boards drop them; D2 row; audit `player.ban`. Enrollments, event bans, ledger and history are
  untouched; lifting restores exactly what was there (`status = 'active'`, `ban_action_id = NULL`, ranking repair again,
  audit `player.lift_ban`; the player signs in normally).
- **Database wall (D10):** a station scan of a screenshot QR or a hand award must not pay a banned player. A BEFORE
  INSERT guard on `ledger_entry`, `xp_entry` and `gem_entry` raises PB423 when the player is not `active`, except the
  refund and removal kinds (`redeem_return`, `removal`; the builder lists the equivalents for XP and gems). Same shape as
  T-701's `ledger_suspension_guard`. Live reservations are left to expire (their refunds pass the guard).
  **(review, BLOCKER) The guard alone would roll back a whole batch for one banned member,** so before the guard ships:
  - every **multi-player** ledger writer skips players who are not `active` and locks each paid player's row `FOR SHARE`
    first, as the souvenir writer does (`0064_event_souvenirs.sql:491`): the adjust batch (`0098_live_points.sql:406`),
    the group and bulk awards (`0093_session_points.sql:858`), the community payout (`0114_console_foundation.sql:647`),
    and every other writer that pays more than one player in a statement (the builder lists them with a catalog search
    for `INSERT INTO ledger_entry|xp_entry|gem_entry` over a set, and names each in the migration header);
  - the guard itself reads the player `FOR SHARE`, so a ban (which takes the row `FOR NO KEY UPDATE`) and a payment are
    one after the other: a payment that started first commits before the ban, one that started after is refused;
  - PB423 is mapped once, globally, in the API's error mapping (a scan, an award, an approval, a handover and a desk sale
    each answer one clear "this player can't receive points" error, never a 500);
  - tests: a batch (adjust, group award, community payout) with one banned member pays every other member and skips the
    banned one; a station scan, a hand award, a submission approval, a handover and a desk sale of a banned player each
    answer the clear error; ban vs payment race in both orders.
- **Questify-wide boards:** verify `questify_ranking`, `xp_board` and the public profile leave banned players out;
  add the filter where missing. **What the player sees:** `POST /v1/players/sign-in/verify`'s `account_banned` (after the right code only) gains
  `{reason: <code>, appealEmail}`; the app's ban screen shows "Your account is banned" with the reason text and the
  appeal address as a mail link. A signed-in phone gets 401 on its next call, its refresh is refused, and the next
  sign-in shows the screen.
- **Appeal address (D11, Dhia agreed 2026-11-02):** configuration data: `platform_setting` gains `moderation
  {appealEmail}` (T-703 edits it later), seeded with `MAIL_FROM` as Q-376 did. Appeals arrive as plain email; no appeal
  table.
- **No ban email (D12, Dhia agreed 2026-11-02):** mail is off (ADR-360), the screen meets FR-1417/FR-1606, and an email
  would carry the reason abroad. If wanted later: a fixed template under Questify's name, reason code and appeal address
  only.
- **(review) Erasure clears `ban_action_id`** before it deletes the player's D2 rows (the foreign key would otherwise
  stop the erasure of a banned player, who may still delete the account under PDPL).

**Block a player** (FR-1415; D13) - `player_block (blocker_id, blocked_id, created_at, PRIMARY KEY (blocker_id,
blocked_id), CHECK (blocker_id <> blocked_id))`, both FK to player. Doors bound to `app_player_id()`:
`block_player(username)`, `unblock_player(username)`, `own_blocks()` (current username and avatar). Routes
`GET|POST /v1/me/blocks`, `DELETE /v1/me/blocks/:username`. At most 500 per player (blocker row locked), 60 changes an
hour, idempotent, tombstones and unknown names answer the same `not_found`. **(review)** The username in the DELETE
path would land in the access log: the logger's URL serializer redacts that path segment (as the join code is not
logged in full), or the route becomes `POST /v1/me/blocks/remove {username}`; the builder picks one and tests that no
log line holds the name.
- **Effect:** every player-facing read that names another player masks a player the viewer blocked: the row keeps its
  place and points but returns `hidden: true` with no username, **no full name (review)** and no avatar (the app shows
  "Hidden player"), so ranks stay true and the top 10 keeps 10 rows. Reads to restate: event ranking (top, around me,
  today), `questify_ranking` and the XP boards, community contributor lists, the public profile (a blocked player's
  profile answers `not_found`). **(review)** The review named these reads, each restated or allowlisted with a reason:
  `public_player_profile` (`0065:425`), `screen_finale`, the 0109 ranking reads, `results.ts:558`, `ranking/display.ts`,
  `submissions.ts:265`, `rewards/quest-items.ts`.
  Meet quests refuse a meeting in **either** direction between a blocked pair with the existing generic
  `not_for_them`. Report a player stays possible.
- **Invisible to the blocked player:** no read returns "blocked by"; a test compares the blocked player's every read
  before and after the block.
- **Gate test (review: widened):** a catalog test over the **source** (`prosrc`) of every function the API's role can
  execute that mentions `username` or `public_full_name` (not only functions whose result has a `username` column: most
  reads return jsonb): each is in the masked list or an allowlist with a reason (staff reads, own profile). Plus a
  TypeScript file allowlist in the style of `apps/api/src/full-name-guard.test.ts` for API files that read a username or
  full name outside those functions. A later player-name read fails until it decides.
- **App:** Block and Unblock on the public profile and the ranking row's sheet, Settings "Blocked players" with
  Unblock. The big screen is unchanged (not per viewer).

**Word lists** (FR-1779) - console page "Word lists": search, language and match filters, 50 a page, Add (word, match,
language), Remove; and "Retired usernames" (D4) with Un-retire. Doors `console_words`, `admin_word_add`,

  event's log shows it; the actor is shown as Questify (ADR-409's marker).

  suspension. **Note to add on T-301b, T-504b, T-506b, T-507b:** each upload kind adds itself to `content_hold`.

**Platform flags** (FR-1404) - console "Flags": open flags across events grouped by event (count, oldest, kinds), linked
to the console event page; read-only (the team resolves, or support), audited `console.flags_read`.
