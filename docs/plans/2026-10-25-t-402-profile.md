### Guaranteed level grants and backfill

`AFTER INSERT ON level_reached` calls an internal definer to insert that level's mapped `player_item` ON CONFLICT
DO NOTHING, copying reached_at. It never takes a player row lock, never raises a duplicate grant and never grants to
an API-supplied identity. Missing mapping is an invariant violation which fails the transaction; catalog invariants
are proven in migration and tests, and future curve administration must add its mapping in the same transaction.
This is deliberate atomicity: no paid XP without its promised item. An invariant error contains no PII.

Install the new tables, trigger, replacement erasure function and backfill in one migration transaction, with these
barriers **first, before any DDL/foreign-key lock or backfill**:

```sql
LOCK TABLE player IN EXCLUSIVE MODE;
LOCK TABLE player_xp IN SHARE ROW EXCLUSIVE MODE;
LOCK TABLE level_reached IN SHARE ROW EXCLUSIVE MODE;
```

The first barrier drains an erasure already using old code: `erase_player` (0038) first takes player FOR UPDATE,
which holds ROW SHARE on the player table through transaction end. EXCLUSIVE conflicts with that table lock, so the
migration cannot pass until the entire old erasure commits/rolls back. A new erasure cannot pass its initial player
row lock until migration commit, then invokes the replaced `erase_rows` (latest body 0059, preserving ticket cleanup).
A SHARE ROW EXCLUSIVE barrier on player is insufficient because it permits ROW SHARE. Keep player schema unchanged
in this migration; the existing avatar column grant is revoked, not altered.

Lock player before XP and reached: never hold an XP/reached barrier while waiting for an erasure that holds player
and may wait for XP through a concurrent completion. Lock XP before reached: drain an XP writer before preventing
its reached insert, and acquire the referenced-table lock before creating inventory FKs. Old completions acquire no
new player lock after their XP write. Install all schema/seed mappings, the new reached trigger and new erasure
cleanup before backfill; no transaction can enter an old erasure after that install while the player barrier holds.
Use bounded migration lock waits; a timeout rolls the entire transaction back, then deployment can retry. Do not
skip or weaken the barrier to complete a deploy. The brief barrier applies only at migration, not normal reads/play.

Backfill every preexisting reached row of a non-deleted player (including currently platform-banned players), including
levels above their present level after a reversal. Exclude deleted tombstones, including any erasure just drained by
the barrier. ON CONFLICT makes a repeated backfill harmless. Test multi-event simultaneous credits, multi-level jumps
and repeat XP/removal behavior. No grants are removed by an XP drop, event end or rehearsal wipe.

**Lock semantics verified read-only, 2026-10-25:** two connections to an idle local Postgres fixture, with no row/data
changes: player SELECT WHERE false FOR UPDATE made another connection's EXCLUSIVE NOWAIT fail 55P03; the inverse
order made the SELECT hit lock_timeout (55P03). The three migration barriers acquired in the stated order. Both
transactions rolled back. This confirms the table-lock premise, not the full upgrade race; the implementation must
also prove the actual pre-0063 erasure/backfill schedules below.

**Lock order:** completion already holds enrollment(s), then player_xp, then inserts level_reached and ownership;
the new grant never locks player or equipment. Equipment edits take active player FOR UPDATE first, then its equipment,
then read owned rows; they never explicitly lock an enrollment or XP row (the equipment FK implicitly takes compatible KEY SHARE on player_xp). Acknowledge takes active player FOR KEY SHARE, then
owned rows in stable item-id order, and never enrollment/XP/equipment. Erasure already holds player then enrollments;
after all existing reservation operations, take player_xp FOR UPDATE before deleting equipment then ownership.
This waits for any in-flight grant and prevents a grant surviving deletion. New ownership FKs target player_xp,
not player, so the XP trigger cannot deadlock on erasure's player lock. Prove crossed orders on two connections.

## API contracts

Every new route has `config.access: player`, caller identity from the session, strict body/query schemas and no
client-controlled player id on own operations. Request/rate-limit storage uses existing infrastructure.

- `GET /v1/me` adds `equipment: {character: Item|null, frame: Item|null, title: Item|null}` and
  `questify.nextReward: Item|null` (NULL at top). Existing `avatar`, masked identifiers, legal/help and XP fields
  stay owner-only. No arbitrary catalog fields are serialized. `Item = {id,kind,name:{ar,en},visualKey:string|null}`.
- `GET /v1/me/locker?cursor=&limit=` returns `{items:[{item:Item,earnedAt,source:{kind:'level',level},seen}],
  nextCursor}`. Default 30, max 100, stable tuple cursor `(earned_at,item_id)`, own rows only. Starter choices are
  rendered separately from the fixed six. No unequippable remote catalog exposed as owned.
- `PATCH /v1/me` extends existing strict schema with nullable `characterId`, `frameId`, `titleId`; omission keeps
  the slot, NULL clears it. Reject avatar + characterId together (400). At least one field, bounded IDs/body.
  Rename and all equipment/legacy avatar changes use **one** caller transaction; validate every requested owned
  item and kind before any update. Existing username filter/switch/rate limits and history remain enforced.
  Unowned, nonexistent or wrong-kind item → identical 422 `item_not_owned` without leaking ownership. Any refusal
  rolls back username and every slot. Pure equipment replacement is idempotent; reapplying identical values is a
  no-op and does not alter username history. Keep username cooldown failures and response shape.
- `POST /v1/me/locker/seen` body `{itemIds:[...]}` (1–100, bounded unique IDs) →204; marks only the caller's rows.
  Repeating is harmless, foreign/nonexistent IDs affect nothing. The profile/locker shows unseen grants with their
  names; acknowledge only after the notification is actually shown. Offline/failed acknowledgment keeps the notice
  retryable. This covers grants from operator scans and background-approved play as well as direct completions.
- `GET /v1/players/{username}` returns an explicit **different** DTO `{username,character,frame,title,level}` only.
  Username resolves active/non-deleted player internally, no exposed internal player/enrollment UUID or searchable
  player directory. Missing, renamed-away, deleted and platform-banned targets return the same 404. Signed-out and
  staff-only sessions cannot call it. Apply existing per-player rate limiter: 60 profile reads/minute, 429 standard
  Retry-After. No cache shared between own/public DTOs; use Cache-Control: private, no-store on both profile reads.
  `character` is a safe starter visual or earned Item. Public `level = {number,title:{ar,en}}` includes its automatic
  level-range title from player_xp/level_title, separately from the equipped cosmetic `title`; never XP or grant dates.

Public response **never** contains contacts (even masked), birth year, real name, city/interests, event history,
join answers, XP amount/bar, locker, item source/event, help counts, legal, username history or settings. Never reuse
`readMe` then remove fields. Public profile is intentionally Questify-wide, so no shared event membership is required;
organizer/staff interfaces gain no cross-event player lookup. ADR-032/FR-702's allowlist wins over event name display.
FR-1415's per-player block implementation is still T-705; it must also filter this new public-profile definer and
ranking entry points when that table is built. Do not silently substitute event enrollment bans for platform status,
and do not claim this task delivers blocking. Record the integration requirement on T-705.

`levelReached` adds `items: Item[]` to the existing `levelUp` result, all newly reached levels for that completion,
ordered by level, preserving its highest-level/title fields. Read the actual grants, not the current mappings.
Same completion replay returns the same list. Extend quizzes/games/typed code/scan parsers and copy through this
shared helper; XP drop and re-climb has no new row, no new item notice/celebration. Owner unseen notices also cover
earned items without a synchronous completion response. Notices carry item names, no XP gained amount.
