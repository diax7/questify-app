# T-810b - Close the ASVS L2 code gaps (plan, tier A: sign-in, tenant isolation, admin powers)

Source: `docs/security/ASVS_L2.md` "Gaps and what to do" rows 1 to 8 and the answered Q-660 (row 9) and Q-662
(row 11). Decisions: ADR-700 to ADR-706 (Proposed); questions Q-670 to Q-673. Migrations 0152 to 0154 (new, none
deployed). TASKS.md lists Q-660 and Q-662 together as item (9); this plan numbers them 9 and 10.

**Done when** (TASKS.md): each item has its test, the sheet's rows move to Met, and the mutation targets are the
changed core files.

**Split and order.** Item 8 (reward code key id and re-seal) moves to **T-810c** (Q-673): it touches the config, the
seal format, every place a code is opened, the upload's duplicate check and a new operator command, and nothing is
at risk until a leak forces a rotation. Item 7 needs a release tag the coordinator pushes (Q-672); it is built here
but only proves itself on the first tagged deploy. The rest is one build in this order, one commit each:
6, 1, 2 (HTTP layer, no schema), 4 (0152), 3 (0153), 9 and 10 (0154 and SECURITY.md), 5, 7.

Every migration starts with `SET LOCAL lock_timeout = '10s'`, restates `REVOKE ALL ... FROM PUBLIC` next to every
function it creates or replaces, and grants nothing new. After each schema change the security suites
(`apps/api/test/security/*`) and `test/db/rehearsal.int.test.ts` run.

## 1. Security headers on every API answer (V3.4.1, V3.4.3, V3.4.4, V3.4.6; ADR-700)

**Change.**
- `packages/shared/src/http/api-security-headers.ts` (new): one constant, `API_SECURITY_HEADERS`:
  `Strict-Transport-Security: max-age=31536000; includeSubDomains`, `X-Content-Type-Options: nosniff`,
  `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`. The API answers JSON and file downloads
  only (no HTML), so `default-src 'none'` breaks nothing.
- `apps/api/src/conventions.ts`: a second `onSend` hook (separate from the idempotency one, registered first) sets
  the three headers on every reply. `onSend` runs for handler answers, thrown errors, the not-found handler,
  idempotent replays and 426/400 from `onRequest`, which `onRequest` alone would not guarantee.
  `privacy/data-export.ts` keeps its own `nosniff` (same value).
- `apps/web/src/lib/forward.ts`: the forwarder sets the same three headers itself on **every** answer it returns,
  its own 404/413/502/504 included, rather than adding them to the pass-through allowlist (ADR-700: the web host's
  answer does not depend on the API sending them, and an API answer cannot weaken them).

**Migration and grants.** None.

**Rollout.** Header-only. HSTS on the API host: the app talks to it over HTTPS already; the 1-year `includeSubDomains`
matches the web pages (same parent domain, already sent). No preload.

**Tests.**
- `apps/api/src/conventions.test.ts`: the three headers on a 200, a thrown `HttpError` (400), a Fastify 4xx
  (bad JSON), the not-found handler, a 426 from `onRequest`, a 500, and an idempotent replay.
- `apps/web/src/lib/forward.test.ts`: an upstream that sends none of them, and one that sends weaker values
  (`frame-ancestors *`): the answer carries the constant's values; the forwarder's own 404 and 502 carry them too.
- `apps/web/src/lib/security-headers.test.ts`: assert `Strict-Transport-Security` in `PAGE_HEADERS` and on a kiosk
  path (today no test does).
- **Outsider:** `apps/api/test/security/routes.int.test.ts`: an anonymous request to every public route and to one
  route of each guarded kind (refused 401/404) carries the three headers.

## 2. Outside calls never follow a redirect (V15.3.2; ADR-701)

**Change.** `redirect: "error"` in the `fetch` init of `players/sms.ts`, `auth/breached.ts`,
`auth/email/resend.ts`, `auth/email/gmail.ts`, `auth/google-token.ts` (also FCM's and APNs' token requests, which go
through `google-token.ts`). The FCM and APNs sends use the raw HTTP/2 client (`push/h2.ts`), which never follows a
redirect (a 3xx is an answer, mapped to a failure by status): noted in the sheet, no change. Node's fetch then
throws a `TypeError` on a 3xx, which each client already maps to its network-failure path (SMS: `unreachable` and
the safe retry; breached: the check's fallback; email: failed send; Google token: `unreachable`). The web's
server-side calls to the API (`lib/event-card.ts`, `event-terms.ts`, `event-rules.ts`, `legal-api.ts`,
`staff-api.ts`) get `redirect: "error"` too; `forward.ts` keeps `"manual"` (it passes the API's own answer through).

A source guard, `apps/api/src/outbound-redirect.test.ts`: every `fetch(` call under `apps/api/src` and the five web
files above passes `redirect: "error"` (a parsed check with the TypeScript compiler API, not a regex), so a new client
cannot forget it (CLAUDE.md: a repeated finding becomes an automatic check).

**Migration and grants.** None.

**Rollout.** None. If a provider ever moves its endpoint behind a redirect, the send fails loudly (its existing
alert) instead of following it.

**Tests.** Per client, in its own test file: the init passed to the injected `fetch` has `redirect: "error"`, and a
thrown redirect `TypeError` lands on the client's failure result (never a success, never a retry loop beyond the
existing bound). **Outsider (attacker's seat: a hostile or hijacked provider):** one test with two local
`node:http` servers, the first answering `302 Location: <second>`; `sendSms` and `createGoogleTokenSource` pointed at
the first fail, and the second server records **zero** requests (no secret, body or bearer reached it).

## 3. A 128-bit random invitation link (V11.5.1; ADR-702, Q-670)

**Today.** `invitation_recipient.link uuid DEFAULT gen_random_uuid()` (0073): 122 random bits. The token in the SMS
is the 16 bytes in base64url (22 characters, `invitation-campaigns/message.ts`).

**Change (migration 0153).** Keep the column and the whole token path; change only where its 16 bytes come from:

```sql
ALTER TABLE invitation_recipient ALTER COLUMN link SET DEFAULT
  encode(substring(sha256(uuid_send(gen_random_uuid()) || uuid_send(gen_random_uuid())) FROM 1 FOR 16), 'hex')::uuid;
```

128 bits taken from 244 bits of the server's strong random source (pgcrypto is not installed and is not added for
this; Postgres stores any 128 bits in a `uuid` and never checks the version). `invitationToken` and
`readInvitationToken` accept any 16 bytes already, so nothing in TypeScript changes. **Why not 256 bits** (the task
text): a 32-byte token is 43 characters, 21 more in a message held to 3 SMS parts, so every event name would be cut
about 21 characters shorter; ASVS asks for 128 bits, which this meets. Q-670 lets the coordinator choose 256 instead.

**Grants.** No new table, function or grant. `invitation_recipient` stays RLS-forced with no grant; `invitation_open`
stays granted to `questify_app` only.

**Rollout.**
- **Links already sent** (`sending`, `sent`, `unknown`): untouched, same column, keep opening until their rows are
  purged 90 days after the campaign finished (`invitation_purge`). No dual path, nothing to remove later.
- **Rows queued but not yet sent** get a new link in the migration
  (`UPDATE invitation_recipient SET link = <same expression> WHERE state = 'queued'`): nobody has seen them. Bounded by
  the queue (staging and production queues are empty or small; the worker counts first and records it).
- Old API instances during the deploy read the same column: no skew.

**Tests.** `test/db/invitation-campaigns.int.test.ts`: (a) 2,000 filled rows: the version nibble and variant bits
vary (not all `4` and `8..b`), all links distinct; (b) a row inserted with a v4 link before the migration's default
(explicit value) still opens through `invitation_open`; (c) a queued row's link changed by the migration's update
expression, a sent row's not (run the statement in the test). **Outsider:**
`test/invitations/routes.int.test.ts`: an anonymous `POST /v1/public/invitation-open` with a random well-formed token
answers the empty result and counts against the address bucket; `questify_app` still cannot `SELECT` from
`invitation_recipient` and `anon`/PUBLIC cannot execute `invitation_open` (outsider suite list unchanged, re-run).

## 4. The backslash in the player search prefix (V1.2.4, V1.2.9)

**Today.** `event_players` (0032, the live definition) escapes `%` and `_` but its backslash step is
`replace(…, '\', '\')`, a no-op; `0118`'s console search does it right (`'\\'`). No other live function builds a LIKE
pattern from input (checked: `LIKE` with a non-literal pattern appears only in 0019/0031/0032 `event_players` and 0118).

**Change (migration 0152).** `CREATE OR REPLACE FUNCTION event_players(uuid, uuid, integer, text)` with 0032's body
and `replace(…, '\', '\\')`; same signature, so no drop. Restate
`REVOKE ALL ... FROM PUBLIC; GRANT EXECUTE ... TO questify_app;`.

**Grants.** Unchanged: granted to `questify_app` only, organizer and event scope checked inside (`app_organizer_id()`,
`in_event_scope`).

**Rollout.** None (search results only).

**Tests.** `test/db/` next to the existing `event_players` cases: usernames `a_b`, `a%b`, `axb`; prefixes `a_`, `a%`
and `a\` match only the literal (today `a\` would escape the appended `%` and match nothing, or match unexpectedly); a
prefix of 30+ characters is cut as before. **Outsider / cross-tenant:** `cross-tenant.int.test.ts` already proves
organizer B's member gets nothing for A's event; add the `%` prefix case (a pattern that matches everything still
returns nothing across tenants).

## 5. One `authz.denied` log line for refused access (V16.3.2; ADR-703, Q-671)

**Change.**
- `apps/api/src/http-error.ts`: `HttpError` gains an optional `denied` flag. `auth/http-errors.ts` adds
  `hiddenNotFound()`: the same envelope and status as `notFound()` (the caller cannot tell), with `denied: true`.
- Replace `notFound()` with `hiddenNotFound()` only where a 404 hides access, not absence: the organizer hook's
  `principalOf` (no membership and no support seat), the console hook and the `activation/routes.ts` sites commented
  "forbidden and not_found", and the device and player guards where they answer 404 for another tenant's object. The
  worker lists every site in the commit.
- `conventions.ts` error handler: for an `HttpError` with status 403, or with `denied`, one
  `request.log.warn({ event: "authz.denied", method, route, status, code, actorKind, actorId })`: `route` is the
  pattern (`request.routeOptions.url`, never the filled path or query), `actorKind` is `staff`, `player`, `device` or
  `anonymous` from `request.principalId`'s prefix, `actorId` the id (pseudonymous; no contact, body or header). The
  request id comes from the logger's child.
- A direct `reply.code(403)` that bypasses the handler is converted to a thrown error (the worker greps; today all 403s
  come from the `http-errors.ts` factories).

**Not covered, by design (Q-671):** a 404 from a definer for an object that row-level security hides is
indistinguishable from "absent" inside the database; logging every authenticated 404 would flood the log with typos and
expired links. The hook-level hides above are the ones that mean "someone tried another tenant's door".

**Migration and grants.** None.

**Rollout.** New log lines only; no alert yet (the monitoring app reads logs; a rule is added if a pattern is wanted).

**Tests.** `conventions.test.ts`: a 403, a hidden 404 and a plain 404 (only the first two log); the line's exact
key set (no extra key, no path with ids, no query). **Outsider / cross-tenant:**
`test/security/cross-tenant.int.test.ts`: organizer B's member calls an organizer-A route and a console route: 404,
the same body as an unknown id, and exactly one `authz.denied` line with B's id and the route pattern (log captured
from the Fastify instance). A player calling another player's object answers as before with no line (Q-671 boundary,
asserted so the choice is visible).

## 7. An SBOM kept with each release (V15.1.2; ADR-704, Q-672)

**Today.** `pnpm sbom:generate` (CycloneDX, prod, lockfile only) exists; nothing runs it. A "release" here is a CranL
deploy or a store build, both started by hand by the coordinator; there are no tags.

**Change.** `.github/workflows/sbom.yml`: `on: push: tags: ["release-*"]`, one job on `ubuntu-24.04`,
`timeout-minutes: 5`, top-level `permissions: {}` and the job's `contents: write` only; checkout pinned by SHA with
`persist-credentials: false`; pnpm and Node setup pinned; `pnpm sbom:generate`; `gh release create <tag> sbom.cdx.json
--notes "SBOM for <sha>"`. A Release asset is kept for the life of the repo and does not count against Actions storage
(an artifact would expire and would). Comment in the file: about 1 minute a release, about 10 minutes a month. RUNBOOK
"Database and deploy": tag the deployed commit `release-YYYYMMDD-N` and push the tag, for every CranL deploy and every
store build. No PR trigger, no secrets beyond the job's `GITHUB_TOKEN`.

**Migration and grants.** None.

**Rollout.** The first tag is the next deploy's. Older deploys have no SBOM (the sheet says so).

**Tests.** Run `pnpm sbom:generate` locally and check the file is valid CycloneDX JSON with the API's, web's and app's
production dependencies; `actionlint` and `zizmor` on the new workflow (both clean). **Outsider's seat:** zizmor's
checks (no `pull_request_target`, no injection from the tag name: the tag is passed through `env`, never interpolated
into `run`), and a check in `scripts/` that the workflow is the only one with `contents: write`.

## 8. Reward code key id and re-seal (V11.2.2; moved to T-810c, ADR-705, Q-673)

Outline for T-810c (its own plan and review):
- **Format.** New seals are `0x51 0x02 keyId ‖ iv ‖ tag ‖ ciphertext` (3-byte header; the length CHECK of 0025, 29 to
  1,024 bytes, still holds, so no migration). Opening reads the header and uses that key; a value without a valid
  header, or whose header open fails, is opened as the legacy format under key 1 (a legacy IV that starts with the
  header bytes therefore still opens). GCM's tag makes a wrong key a refusal, never a wrong code.
- **Config.** `REWARD_CODE_SECRET` stays the current key with `REWARD_CODE_KEY_ID` (default 1);
  `REWARD_CODE_PREVIOUS_SECRETS` (`id:secret,...`) is optional and read only to open and re-seal.
- **Duplicates.** While a previous key is loaded the upload checks the marks under every key, so a code uploaded
  during a rotation cannot duplicate an old one.
- **Re-seal command.** `node reward-codes.cjs reseal`, run with the migration owner's connection like `migrate.cjs`
  (no new door, nothing granted to `questify_app`): batches of 500 by id, each row compare-and-set on its old cipher,
  every row including redeemed ones (players see their code again), new cipher and mark under the current key; a mark
  conflict is reported by row id and skipped; ends with counts, never a code. Then the previous secret is removed.
- **Tests.** Round trips across formats and keys, legacy-header collision, a wrong key refused, re-seal idempotent and
  resumable, conflicts reported, a concurrent redemption during re-seal; outsider: `questify_app` still cannot read
  `reward_code` directly.

## 9. A player refresh family ends 365 days after its sign-in (V7.3.2, V7.1.1; Q-660 answered, ADR-706)

**Today.** `issue_player_tokens` gives every refresh token `now() + 180 days`, and each rotation issues a new one, so a
family has no end. Used and revoked rows are deleted 7 days later (`sweep_player_sign_in`, 0020), so the sign-in time
cannot be read back from the rows.

**Change (migration 0154).**
- `ALTER TABLE player_refresh ADD COLUMN family_started_at timestamptz` ; backfill per family with the earliest
  surviving `created_at`; then `SET NOT NULL` and `DEFAULT now()`.
- `CREATE OR REPLACE FUNCTION issue_player_tokens(uuid, bytea, bytea, uuid)` (same signature, so its eight callers in
  0013 to 0144 are untouched): the family's start is `coalesce((SELECT min(family_started_at) FROM player_refresh WHERE
  family = new_family), now())`; the new row gets it and `expires_at = least(now() + 180 days, start + 365 days)`.
  `rotate_player_refresh` already answers `invalid` for an expired token, so it needs no change; the 60-second retry
  grace and the theft detection are unchanged. Restate `REVOKE ALL ON FUNCTION issue_player_tokens(...) FROM PUBLIC`
  (it stays ungranted: called only by definers).
- Cap live rows in the same migration: `UPDATE player_refresh SET expires_at = least(expires_at, family_started_at +
  365 days) WHERE revoked_at IS NULL`.
- SRS amendment to FR-123: "until they sign out, or 365 days after they signed in on that phone"; SECURITY.md
  "Authentication": the reason (low-value accounts holding event points, never money; a lost phone ends with sign-out,
  the 10-family limit or a ban; one fresh code a year is the NIST SP 800-63B AAL1 allowance of 30 days stretched for a
  game, recorded as a deviation).

**Grants.** No new function; `player_refresh` stays RLS-forced with no grant; `issue_player_tokens` stays revoked from
PUBLIC and ungranted.

**Rollout.**
- **Families older than 365 days at deploy cannot exist in the rows**: a live row expires 180 days after it was made
  and older rows are swept, so the oldest surviving row of a live family is at most about 187 days old. The backfill
  therefore starts every existing family at its earliest surviving row: **nobody is signed out by the deploy**, and
  every existing session ends at most 365 days after that row (in practice 6 to 12 months after the deploy).
- Logic is all in SQL, so API instances of the old and new release behave the same during the deploy.
- The app already treats `invalid` on refresh as "sign in again" (sign-in screen, no error); no new copy.

**Tests.** `test/db/` next to the existing sign-in cases, the clock moved by updating the row's `family_started_at`
(superuser in the test): (a) a fresh sign-in's row ends at 180 days; (b) at 300 days a rotation's new row ends at
`start + 365`, not `now + 180`; (c) at 365 days a rotation answers `invalid` and the family's access tokens end; (d) a
rotation keeps `family_started_at`; the retry grace keeps it; (e) the sweep deleting older rows does not move the
start; (f) the backfill on a family whose first rows were swept. HTTP: `POST /v1/auth/refresh` with an ended family
answers 401 `invalid`. **Outsider:** the outsider suite still shows `player_refresh` with no grant to anyone and
`issue_player_tokens` executable by nobody but its owner (re-run; the list-style guards catch the new column only if
a grant appears).

## Risks

- Item 5 needs a judgement per `notFound()` site (hide vs absence); a missed site leaves a denial unlogged, a wrong one
  logs noise. The commit lists every site for the review.
- Item 1's `onSend` hook must run on every path, including the idempotency replay and errors thrown before routing;
  the test list covers each.
- Item 3's queued-row update rewrites every unsent recipient in one statement; large queues would hold the table
  briefly (count first; batch if over 50,000).
- Item 9 shortens FR-123 for every player: a one-year re-sign-in will surprise some players; accepted with Q-660.
- Item 7 depends on the coordinator tagging every release (Q-672); without the tag no SBOM is made.
