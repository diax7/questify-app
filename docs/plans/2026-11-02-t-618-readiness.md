# T-618 - Go-live readiness checklist (plan note, tier B)

Delivers FR-1845 (F-347). Decisions: ADR-403 and Q-370 (Proposed). Migration 0112. No change to points, sign-in or tenant
isolation: two read-only doors that answer flags and counts, one of them behind the same `award_event_of` check as the control
room and the Inbox, the other behind `app_admin_id()` like the usage doors. The checklist writes nothing, activates nothing and
blocks nothing.

## What it builds

- **The checklist** (`packages/shared/src/readiness`): the database answers facts, `evaluateReadiness` turns them into items, so
  the owner and the console always read the same list. Each item is `done`, `warning` or `blocking`, with a line (a state, plus a
  number where it has one). Items that do not apply to the event are not listed (a prize desk without item or experience rewards,
  operators without a station, a big screen without the add-on, devices without a kiosk-only quest, a rehearsal after go-live).
- **Status meaning:** blocking = players cannot use the event as it is (no dates or dates passed, no activation asked or declined,
  no playable quest, no prize desk place for an item reward, no operator for an operator-only quest, a guest list nobody is on);
  warning = it works but should be looked at; done. "The checklist blocks nothing" (FR-1845) means it never stops a request for
  activation or an activation; a blocking item is advice with a stronger word.
- **Owner:** a card on the event Overview (draft and scheduled events only) and at the end of the guided setup: a line of
  three counts (needed, to check, ready; the layout check allows no box inside a card), then every item blocking first, each with its status word and a Fix link (Open when
  done) to the page that sets it.
- **Console:** a Readiness page (platform admin only): the events that start within 14 days (or whose start passed without going
  live), not ended, soonest first, 100 at most, as equal cards with the organizer, the start, the three counts and the items
  still open.

## The two reads

`readiness_facts(event)` (internal, no grant): one jsonb of flags and counts from rows other pages write: event times, the
activation request, quests (total, playable, operator-only, device-only), rewards (active, in stock, item, experience), the desk
place, operators, paired devices by kind, the join method and guest list, rules text, the big screen add-on and switch, the
rehearsal (the card's own `first_play_at`, or a rehearsal quest entry while the event can still rehearse), the accent, the guided
setup. `event_readiness(event)` for the event's team (AN404 otherwise), `readiness_soon()` for an admin (RD404 otherwise). Every
lookup is by `event_id` on an indexed column; the ledger is read only while the event can rehearse, through the partial
`ledger_entry_rehearsal_idx`. Nothing is cached.

## Personal data

None: flags, counts, the event's name and times, the organizer's name. The console list is not audited (as the usage view).

## Tests

DB suite `test/db/event-readiness.int.test.ts` (every fact, both doors, refusals, an editor's limit); HTTP suite
`test/readiness/routes.int.test.ts`; shared unit tests for every item; web unit tests for the links, words and order; outsider,
cross-tenant, route-map and community gate entries; browser spec `readiness.spec.ts` (Overview in both languages, the setup's last
step, the console list, a non-admin); `readiness` in `LAYOUT_PAGES` for the console page.
