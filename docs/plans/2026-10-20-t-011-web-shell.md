# T-011 — Web app shell: staff sign-in, responsive, Arabic and English

Task: `docs/TASKS.md` T-011 (FR-1746). Done when the dashboard sign-in works on a desktop and on a phone browser in
both languages. Depends on T-006 (staff sign-in API) and T-008 (translations).

## Scope
In: the Next.js app in `apps/web`; the same-origin `/v1` forwarder to the API; the two-step staff sign-in (password,
then the emailed code, resend); a signed-in home placeholder (who you are, your organizers, sign out); language in
the URL with a switch; responsive layout from phone width up; security headers; shared design tokens; tests; a
Dockerfile and runbook lines for staging.
Out: any dashboard feature (T-101 onward), the event page, station and big-screen pages, the console, password reset
(T-020), translation-store overrides on the web (shipped texts only for now; overrides join with the first organizer
screens, T-101), the staging deploy itself if the Gmail app password is still missing (the build is ready; the live
check waits on that secret).

## Stack
- Next.js 16.4.x (16.4.1 was a security release; take the newest 16.4 patch at install), App Router, React 19,
  TypeScript strict as the rest of the repo. `poweredByHeader: false`; `images.unoptimized: true` (no image
  optimiser, so no `sharp` on the server; nothing needs it yet).
- Styling: CSS Modules plus CSS variables generated from the shared tokens. No UI library (a dependency each is not
  justified for two screens; revisit with the dashboard's tables in T-101).
- Fonts: `next/font/google` for Baloo Bhaijaan 2 and Rubik (ADR-017). Files are fetched at build time and served from
  our own origin; the browser never calls Google.
- Cache Components left off for now: every page here is per-request (session) and the shell gains nothing from it.

## Design
### Language and direction (FR-1506, ADR-018)
- Every page lives under `/{lang}/…` with `lang` in `ar | en`. The root layout for `[lang]` renders
  `<html lang dir>` on the server, so the first paint is already right to left in Arabic.
- `/` redirects (in `proxy.ts`) to the saved language (`qs_lang` cookie, a preference only), else the first `ar`/`en`
  in `Accept-Language`, else English (the same rule as the app). Any other `lang` value is a 404.
- A language switch links to the same page in the other language and saves `qs_lang`.
- Layout uses logical CSS properties only (`margin-inline-start`, `text-align: start`), so the `dir` attribute
  mirrors everything. Numbers stay Western digits.
- Texts come from `MESSAGES` in `packages/shared` (new keys for the sign-in screens, both languages, Arabic written
  first with the ux-araby skill).

### Same-origin forwarder (`app/v1/[...path]/route.ts`)
The browser only talks to the web origin, so the `__Host-` session cookie and `SameSite=Strict` work and there is no
CORS. One route handler forwards every method to `API_ORIGIN` + the same path and query:
- Request headers on an allow-list: `content-type`, `cookie`, `origin`, `idempotency-key`, `if-none-match`,
  `accept-language`, `user-agent`, `x-forwarded-for` (passed through unchanged, see below). Everything else is
  dropped (no `host`, no `x-*` from the client).
- Body: read as bytes with a 1 MB cap (413 above it, before forwarding).
- Response headers on an allow-list: `content-type`, every `set-cookie`, `cache-control`, `etag`, `retry-after`,
  `x-request-id`, the rate-limit headers. Status and body pass through.
- Timeout 15 s (`AbortSignal.timeout`); no retry (sign-in steps are not safe to repeat). On timeout or a network
  error the answer is 502 with the shared error envelope (`api_unavailable`), never a stack.
- Client address: a route handler cannot see its own peer, so the forwarder passes `X-Forwarded-For` through
  unchanged. Behind CranL's edge the last entry is the one the edge added (the real client). The API trusts exactly
  one hop (`TRUST_PROXY_HOPS=1`), the same value as for the app calling the API directly through the edge. The staging
  check proves it: a spoofed `X-Forwarded-For` from the browser does not change the address the API throttles.
  (This replaces the T-006 note's "edge, dashboard proxy, API" count, which assumed the forwarder appends.)

### Screens
- `/{lang}/sign-in`: step 1 email and password; step 2 the six-digit code (numeric keyboard, one-time-code
  autocomplete, paste), resend with a countdown from `retryAfterSeconds`, "use a different account". Each API error
  code maps to a message key (wrong details, too many attempts with the wait, code wrong with attempts left, code
  expired, email unavailable, busy). Client components post JSON to `/v1/staff/auth/*`; the browser sets `Origin`.
- `/{lang}` (signed-in home): a server component calls the API's `/v1/staff/me` with the incoming cookie (server to
  server, direct to `API_ORIGIN`, same timeout and the incoming `X-Forwarded-For`). 401 redirects to sign-in; any
  other failure shows the error state with retry. Shows the email, the organizers the person belongs to, sign out.
  Every response is `no-store`.
- A sign-in page visited with a live session goes to the home.
- States: loading (button busy, inputs locked), every error above, network down (retry), empty organizers ("Ask an
  owner to invite you").

### Security headers (all pages, from `proxy.ts`)
CSP with a per-request nonce (`default-src 'self'; script-src 'self' 'nonce-…' 'strict-dynamic'; style-src 'self'
'unsafe-inline'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none';
form-action 'self'`), HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`,
`Permissions-Policy` with everything off. Pages are `no-store`.

### Shared design tokens
Move the platform-free tokens (palette, colours, spacing, radius) from `apps/app/src/theme/tokens.ts` into
`packages/shared/src/design/tokens.ts`; the app re-exports them (no behaviour change, its contrast test moves with
them). The web turns them into CSS variables once, at build time, in the root layout.

### Configuration
`API_ORIGIN` (required, fails fast with a clear message). The API's `DASHBOARD_ORIGIN` becomes the web app's
origin. No secrets in the web app.

## Tests
- Unit (vitest): language negotiation (`/` redirect rule), the error-code-to-message map (every API sign-in error has a
  key in both languages), the forwarder against a real local HTTP server (allow-lists both ways, several
  `set-cookie`s kept, 1 MB cap, timeout gives 502 with the envelope, `x-*` from the client dropped, path and query
  kept, a non-`/v1` path impossible).
- End to end (Playwright, chromium desktop plus a phone profile, and WebKit phone): a test harness starts the real API
  in-process against a throw-away database with a recording email sender that writes codes to a temp file (test code
  only, no test endpoint in the product); the web app runs against it. Sign in fully in Arabic and in English, wrong
  password, wrong code, resend, sign out; check `dir="rtl"` and that nothing scrolls sideways at 360 px.
- CI cost: the e2e job runs only when `apps/web/**`, `apps/api/src/auth/**` or `packages/shared/**` change (path
  filter in the one CI job), chromium only in CI; WebKit runs locally in `ci:full`.

## Phases
1. Tokens to shared; Next.js app skeleton (`[lang]` layout, fonts, tokens as CSS variables, `proxy.ts` redirect and
   headers); forwarder with unit tests.
2. Sign-in screens, home, sign out, language switch; messages; unit tests.
3. Playwright harness and e2e; CI path-filtered step; Dockerfile; RUNBOOK (`ci:changed`/`ci:full` updated); docs.

## Judgment calls
1. Language in the path rather than a cookie only: the server renders the right `dir` on first paint and links can be
   shared; the event page (later) needs per-language URLs for link previews anyway.
2. Our own forwarder instead of a `next.config` rewrite: the headers it passes and the timeout are explicit and
   tested; the rewrite's header handling is not documented.
3. Pass `X-Forwarded-For` through instead of appending (the handler cannot see its peer); one trusted hop everywhere.
4. Shipped texts only on the web for now; overrides arrive with the first organizer screen.

## Revisions after the CTO plan review (84/100, no blocker)
**M1, client address.** `API_ORIGIN` is CranL's internal address of the API, never the public URL. Checked on
2026-10-20 from inside the staging container: `http://questify-api-staging-3ez01s:3000/healthz` answers through the
project's private network (Docker DNS; the internal name is the app's public subdomain label), the same way
`questify-db-oj68ag` is reached. The web config refuses an `API_ORIGIN` that is `https://` or ends in `.cranl.net`, with
an error that says to use the internal name. The staging check covers both paths: a spoofed `X-Forwarded-For` through
the web forwarder and one sent straight to the API's public host must both be throttled under the real client's
address. Whether CranL's edge appends to `X-Forwarded-For` (rather than passing the client's value through) is
checked in that same step; if it does not append, neither path has a trustworthy address and we ask CranL for its
client-address header before launch (recorded in OPEN_QUESTIONS). Proposed ADR-113 records the one-hop decision; the
T-006 note, `API.md` and the API's `TRUST_PROXY_HOPS` error text are updated.

**M2, TypeScript 7.** First step of phase 1: prove `next build` with the repo's TypeScript 7 and
`typescript.ignoreBuildErrors: true` (types stay gated by `pnpm typecheck`). If Next's setup check still needs the
TypeScript JS API, pin TypeScript 5.x as an `apps/web` dev dependency for Next only. The outcome goes into
TECH_STACK. The web tsconfig adds `jsx` and the DOM libs.

**M3, CI.** The one CI job builds the web app (`next build`, `.next/cache` cached) when `apps/web/**`,
`packages/shared/**`, `pnpm-lock.yaml` or the workflow change. The e2e step runs on the built app (`next start`)
when any of those or `apps/api/src/**` or `apps/api/migrations/**` change. Filtering is a small `git diff --name-only`
script, no new action; the Playwright chromium install is cached by version.

**M4, phone browser.** No WebKit in the harness: chromium desktop plus a chromium phone profile (360 px). The phone
part of "Done when" is proven on a real iPhone (Safari) and a real Android phone against staging, so **T-011 stays
unticked until that staging check** (with a status note like T-006's).

**Also adopted:** CSP nonce set on the request and the response headers, `object-src 'none'`, a dev-only branch for
`unsafe-eval` and `ws:` with a test that production has neither, and a `proxy.ts` matcher that skips `/v1`, `_next`
and static files. The forwarder never logs a body or the `cookie` header (a test checks a failure's log line). The
upstream path comes from the raw pathname and must still start with `/v1/` after URL parsing (encoded `..` and `%2F`
tested). A live session means `/me` answered 200; a 401 or 5xx on the sign-in page shows the form; an ended session
shows "Your session ended, sign in again". Accessibility: real labels, errors in `role="alert"` tied by
`aria-describedby`, focus to the code field, `autocomplete` email / current-password / one-time-code, and one
keyboard-only e2e sign-in. Fonts come from the same files the app ships, through `next/font/local`, so the build
calls no outside service. The challenge token lives only in component memory (never the URL or storage). `qs_lang`
is `Path=/; SameSite=Lax; Secure; Max-Age=1 year`. Each e2e test sends its own `X-Forwarded-For` so throttles do not
cross. Tokens move to shared without `fontFamily` and `typography`, which stay with the app.
