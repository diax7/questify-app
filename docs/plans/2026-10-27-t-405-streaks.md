# T-405 — Streaks: the event day streak (with or without bonus), the Questify daily streak, the platform switch

**Plan written 2026-10-27; awaiting the independent CTO plan review.** Delivers FR-417, FR-418, FR-419, FR-420 (the
switch's effect; its console control is T-703's switches page), FR-421, FR-1615, and the streak half of FR-1715 and
FR-731 (the daily challenge itself is T-406). Depends on T-401 (XP ledger, `xp_apply`, levels), T-403/T-404
(`questify_sync`, its unlocked pre-check, gems), T-216 (`event_day`, `event_multi_day`), T-313 (the nearest pattern: a
system bonus paid inside the completion transaction), all built. Never push, deploy, run EAS or run local mutation
testing. Choices are **Proposed ADR-294 to ADR-300 / Q-259 to Q-265**. `docs/STORE_COMPLIANCE.md` is a gate (below).

**CORE:** the event streak bonus writes the points ledger (`ledger_entry`, a new kind, inside every completion
transaction) and the daily streak writes the XP ledger (`xp_entry`, a new source). Neither writes the gem ledger:
`gem_entry` gets no streak source (FR-421, TASKS note from T-404).

## Store compliance gate (ADR-300, Q-265)

`STORE_COMPLIANCE.md` has no streak rule; checked against 1.6 (Apple 3.1.1: nothing sold), 1.12/2.9 (no chance, no cash
value), 1.14 (age rating), PD-15 (not a Games category), PD-19 (13+), PD-22 (no purchase UI) and
`research/GAMIFICATION_PATTERNS.md` ("streak anxiety: no guilt-trip copy"):

- **Nothing is sold.** No freeze, repair, restore or "keep your streak" offer exists, paid or free; no IAP arises.
- **No loss pressure.** Copy never threatens a loss ("Don't lose your 12-day streak!"), never guilt-trips, shows no
  countdown to the day's end and no red alert badge. A broken streak reads "Start a new streak today", neutral. A closed
  event day reads "The event is closed today. Your streak is safe."
- **No chance, no cash value.** Event bonuses are fixed event points (prizes stay effort-based, 3.4); daily rewards are
  fixed XP. Age rating unchanged.
- **A kill switch without a release.** The platform switch (FR-420) hides and stops the daily streak at once
  (configuration, not code; 2.5.2 unaffected).
- **No new data type.** Day records are derived from quest completions already collected and declared; the daily streak
  is shown only to its owner. Privacy labels unchanged.
- STORE_COMPLIANCE §6 gains a PD row at build: "Streaks: no purchase, no loss or guilt copy, no countdowns; a platform
  switch turns the daily streak off" (ADR-300).

## T-405 (CORE) — migration 0068

All new tables: ENABLE and FORCE RLS, REVOKE ALL FROM PUBLIC and `questify_app`, no grant (written and read only by
definers). Definers `SET search_path = public, pg_temp`, PUBLIC EXECUTE revoked in the same statement group; only the
doors named here get `questify_app` EXECUTE. Deployed migrations untouched (CranL runs through 0056); 0057 to 0067 are
undeployed but stay untouched too: 0068 restates what it changes.

### Locks (the T-404 MAJOR-1 lesson)

Under `SET LOCAL lock_timeout = '10s'`, every table 0068 touches is locked up front, in live-path order, at the strongest
mode any later statement needs (no upgrade mid-migration):

1. `enrollment` **EXCLUSIVE**: every payer row-locks an enrollment before it writes a completion or a ledger entry, so
   this drains the completions in flight and holds new ones before they touch anything 0068 changes (EXCLUSIVE
   conflicts with their ROW SHARE; plain reads still pass). Also the FK target of `event_streak_day`.
2. `event` SHARE ROW EXCLUSIVE: FK target; compatible with the KEY SHARE a payer waiting behind (1) already holds.
3. `quest_completion` SHARE ROW EXCLUSIVE: FK target.
4. `xp_entry` ACCESS EXCLUSIVE: new column and shape CHECK. Before `player_xp`, because the sync's unlocked pre-check
   reads `xp_entry` before it locks `player_xp`.
5. `ledger_entry` ACCESS EXCLUSIVE: kind CHECKs, the shape CHECK, a partial unique index, the new trigger.
6. `player_xp` SHARE ROW EXCLUSIVE: FK target of `questify_streak_reward`.

**Never** `platform_setting` (a scan reads it before `player_xp`; 0068 adds no row, the switch defaults on when absent)
and never `player`. Residual windows of the ADR-291 kind (a sync whose pre-check read `ledger_entry` waiting for its
player lock while the migration wants `ledger_entry`) abort one side with 40P01; nothing is half-written, and T-022's
retry removes the rerun. The upgrade test below runs a scan and a sync across the migration.

### The event streak (ADR-295, ADR-296, Q-260, Q-261)

| Object | Shape | Notes |
|---|---|---|
| `event_streak` | `event_id` PK, `organizer_id`, composite FK (event_id, organizer_id) → `event` ON DELETE CASCADE, `enabled boolean NOT NULL DEFAULT false`, `bonus_points integer NULL CHECK (1–100000)` (NULL: without bonus), `closed_weekdays smallint[] NOT NULL DEFAULT '{}'` (ISO 1–7, CHECK `<@ '{1,…,7}'` and cardinality ≤ 6), `closed_days date[] NOT NULL DEFAULT '{}'` (CHECK cardinality ≤ 366), `updated_at` | The organizer's settings, one row or none (none: off, no closed days). Not in `event.config`: the bonus pays points, so SQL validates and audits it (ADR-299) |
| `event_streak_day` | `enrollment_id`, `day date`, `organizer_id`, `event_id`, `days integer CHECK ≥ 1`, `completion_id bigint NOT NULL` → `quest_completion` RESTRICT, `entry_id bigint UNIQUE NULL` → `ledger_entry` RESTRICT, `created_at`; PK (enrollment_id, day); composite FKs (enrollment_id, event_id) → `enrollment`, (event_id, organizer_id) → `event` | One row per open event day a player completed a quest. `days` is the streak length that day; `entry_id` the bonus paid with it. Append-only (UPDATE/DELETE/TRUNCATE refused, ENABLE ALWAYS). Its FKs name only rows the quest entry's own insert already key-locks (the entry's enrollment and event, the completion and the entry, all in the same transaction), so it adds no lock |

**Event days and closed days.** A day is an **event day** when it lies between `event_day(starts_at)` and
`event_day(ends_at − 1 µs)` (FR-1714's day start, `event_multi_day`). It is **closed** when its ISO weekday is in
`closed_weekdays` or the date is in `closed_days`. A closed day neither counts nor breaks (FR-1615); a completion on a
closed day writes no day row and pays no bonus. `prev_open_day(ev, settings, day)` (internal) walks back over closed
days to the previous open event day, or NULL before the first day (at most 366 steps; at most 6 closed weekdays, so a
week always has an open day).

**The writer.** A new trigger `ledger_streak` AFTER INSERT ON `ledger_entry` FOR EACH ROW WHEN (NEW.kind = 'quest'),
calling `streak_record(NEW)` (internal, definer). Triggers of one kind fire in name order, so it runs after
`apply_ledger_entry` (the quest's points are on the enrollment) and **before `ledger_xp`** (so it never runs after the
`player_xp` lock in its own transaction). It covers every door that writes a quest entry (scan, typed code, location,
NFC, screen QR, kiosk, my-QR, vote, live poll, survey, share, passport, submission approval, quiz finish, game result,
meet both sides, the team's quest award), as `ledger_xp` does (T-401), so no payer is restated and `PAYER_MAP` is
unchanged. It returns at once (no write) when `NEW.rehearsal` (rehearsals write no streak: nothing to wipe). An operator's practice scan
runs inside an undone block (ADR-249), so whatever it writes is rolled back with it (tested). For the event part:

1. Read the event (already key-locked by the entry) and `event_streak` (a plain primary-key read, no lock). Skip unless
   `event_multi_day(ev)` and `now()` lies in the event window and its day is open.
2. `SELECT 1` on (enrollment, day): present → done (every later completion of the day costs one index probe).
3. `days` := the previous open day's row `days + 1`, or 1. INSERT … ON CONFLICT DO NOTHING RETURNING (the payer holds
   the enrollment `FOR NO KEY UPDATE`, so two completions of one enrollment never race; the ON CONFLICT is a backstop).
4. **The bonus** (FR-418, FR-1615), only when the row was inserted, `enabled`, `bonus_points` set and `days ≥ 2`: a
   ledger entry of kind **`streak`**, `score_delta = bonus_points`, `balance_delta` 0 while `shop_state` is closed, else
   the same (the T-313 rule), `completion_id`/`quest_id` of the paying entry, `actor = 'system'`; then the row's
   `entry_id`. The nested insert fires `apply_ledger_entry` (score, rank marks) and not `ledger_xp` (kind filter), so
   the payer's final score read includes the bonus.

Day rows are written for **every multi-day event, on or off** (ADR-295): switching the streak on mid-event shows true
streaks with no backfill (a backfill would race completions in flight), and METRICS' "players who return on another day"
gets its data. The bonus is paid only while on. A single-day event writes nothing.

**Ledger kind `streak`.** `ledger_entry_kind_check` and `ledger_entry_system_returns_only` widened (restated from 0062);
new CHECK `ledger_entry_streak_shape`: `completion_id` and `quest_id` set, `score_delta > 0`, `balance_delta IN (0,
score_delta)`, `category_id`, `community_step_id`, `redemption_id`, `boost_id` NULL, `actor = 'system'`; backstop UNIQUE
`(completion_id) WHERE kind = 'streak'` (the day row's UNIQUE `entry_id` makes it one per enrollment and day).
**Never boosted** (ADR-232's Never list gains it), **no XP** (XP follows `quest` entries only). The ranking, today's
ranking (`ranked_day` sums `score_delta`) and the score triggers are kind-blind and count it. **Removal:** `remove_award`
(restated) accepts `streak`; the bonus is its own line, removed on its own (as the category and first-N bonuses);
removing the quest line leaves the day row and the bonus, and removing the bonus never unpicks the day (the day was
played; ADR-152's "a removed quest stays used"). **Readers that list kinds** restated with `streak` beside
`first_bonus`: `ledger_operator_play_guard`, `community_read_slice` (a points goal counts it), `member_ledger` and
`member_activity` (the row carries `days` for the label "Streak bonus, day N"). `rehearsal_card`/`wipe_rehearsal` need no
change (never written for rehearsals; a test pins it). **Build check (T-313's):** every SQL and `apps/api/src` query
joining `ledger_entry` by `completion_id` without a kind filter now may find a third line; the build lists each with its
fix or why it is right.

**The settings door** `set_event_streak(target_event, enabled, bonus_points, closed_weekdays, closed_days, request)`
(definer, granted): the caller is the event organizer's **owner** (`app_is_owner`) within event scope, else `AN404`
(another tenant's event is indistinguishable from a missing one); refused once results are final or the event is
archived (the builder's codes); `SK409 single_day` unless multi-day; `SK409 day_started {day}` when the change adds or
removes a closed day or weekday that would alter a day that has already started (today included), so stored `days`
and paid bonuses never disagree with the settings (ADR-295); `SK422 {field}` for a date outside the event's days. Locks
only the `event_streak` row (`FOR UPDATE` or the insert) after reading the event: never an enrollment, a completion or
an XP row, so it cannot cross a payer. An amount or on/off change applies to bonuses paid after it commits. Replay by
`request`; audit `event.streak_set` (before/after). `event_streak_settings(target_event)` (definer, granted): owners
and editors in scope read `{enabled, bonusPoints, closedWeekdays, closedDays, multiDay, today}`. The class `SK` is
checked free at build.

**The player read** `own_event_streak(target_event)` (definer, granted): an active member only, else no row; `{on,
days, playedToday, closedToday, bonusPoints}` with `on = enabled AND multi_day AND live`; `days` = today's row, else the
previous open day's row (still alive: play today), else 0. `own_streak_bonus(completion)` (definer, granted): the
caller's own completion only, `{points, days}` or nothing (same on a replay).

| `questify_streak_day` | `player_id uuid NOT NULL`, `day date`, `created_at`; PK (player_id, day) | One row per Questify day with activity. | `questify_streak_milestone` | `days smallint PK CHECK 2–1000`, `xp integer CHECK 1–1000` | Seeded 3→50, 7→100, 14→150, 30→250, 60→300, 100→400, 200→500, 365→750 (a quest pays 100). Data, edited by migration until T-703/T-709 |

**What counts (FR-419).** Any non-rehearsal quest completion in any event the player plays (repeats included: it is
play), written by the same `ledger_streak` trigger: one `SELECT 1` probe on (player, `questify_day(now())`), then
`INSERT … ON CONFLICT DO NOTHING` on the first completion of the day. **Only while the platform switch is on**
(`daily_streak_on()`: `platform_setting` key `features` → `dailyStreak.enabled`, true when absent; the same read
`flash_on` does, before any lock): days while off are never counted, so a streak restarts after a switch back on
(FR-731). A Questify quest award is earned by event play, so its day is already counted; T-406's daily challenge and
word insert the same row through their own doors (TASKS note). The only wait it can add: two first-of-the-day
completions of one player in two events at the same moment; the second waits on the first's unique entry, then skips
(it takes no `player_xp` lock first: the trigger fires before `ledger_xp`). Tested crossed, below.

**Length (read time, never stored).** `daily_streak_length(who)`: the run of consecutive rows ending today, else ending
yesterday (alive until today ends), else 0, from the primary-key index. Stored lengths are not needed: nothing pays per
day, and an older day arriving late (a completion committing across 04:00) still joins the run.

**Rewards (FR-421).** XP only, at milestones, each paid **once ever** per player, by `questify_sync` (replaced), never in
the completion transaction (ADR-274): after the Questify quest awards and before the gem step, under the same locks
(player FOR KEY SHARE → `player_xp` FOR UPDATE), for every milestone `days ≤ length` with no reward row: insert
`questify_streak_reward` (ON CONFLICT DO NOTHING RETURNING), an `xp_entry (streak)`, `xp_apply` (levels and level items
follow as for any XP). The unlocked pre-check gains `streak_due(who)` (switch on and a milestone at or under the length
unpaid), so a sync with nothing due still takes no lock. Switch off: nothing paid, nothing shown. **Gems:** no gem entry
is ever written for a streak reward (no source exists); a level crossed by streak XP pays its level gems like any level
(T-404's step runs after it in the same call). This is the reading of FR-421 recorded in Q-263.

The sync answer gains `dailyStreak: {days, today, rewards: [{days, xp}]} | null` (null when off) and its `levelUp`
covers streak XP entries. `own_daily_streak()` (definer, granted): `{days, today, next: {days, xp} | null}` or nothing
when off. Shown to its owner only: not on the public profile, rankings or any organizer read (a cross-event activity
fact).

### The switches (ADR-299, Q-264)

- **Platform:** `FEATURES.dailyStreak = {gated: false, level: "platform"}` in `packages/shared/src/config/registry.ts`
  (on by default), so the composed `/v1/config` ships it, the app hides the daily streak when off, and T-703's generic
  switches page offers it. SQL honours the same key (`daily_streak_on()`). Until T-703, a Questify admin flips it through
  the existing `savePlatformSettings` service (a route test drives it).
- **Event:** the streak's on/off lives in `event_streak.enabled` behind the owner-only settings door, not in
  `event.config.features` (whose switches default on, are not checked in SQL, and do not carry an amount). The
  dashboard shows it among the event's switches (FR-1009's "streak"), as one more owner-only control.

## Tests (test first)

**T-405 DB** (`test/db/event-streak.int.test.ts`, `daily-streak.int.test.ts`):
- **Event streak counting (Done when):** play days 1, 2, 3 → 3; miss open day 2 → day 3 is 1 (FR-1615's second
  Given); a closed weekday between (Friday) → 4 (the first Given); a closed date likewise; a completion on a closed day
  writes nothing; the day boundary at `day_start_hour` (03:59 counts for the day before, 04:00 for the new one, in the
  event's zone); before the start and after the end nothing; a single-day event writes nothing; repeats on one day
  leave one row; rows are written while the streak is off and the length is right when it is switched on mid-event.
- **Bonus (FR-418):** off → none; on without bonus → none; on with bonus: day 1 none, days 2 and 3 one each, flat;
  paid with the day's first completion only, through a door table (QR, typed code, kiosk, my-QR, submission approval,
  quiz finish, game result, passport, meet both sides, the team's quest award); never boosted under a running boost;
  no XP row; balance 0 with the shop closed; the returned score holds it; today's ranking counts it; a community points
  goal counts it; the shape CHECK refuses forged rows; rehearsal and practice write nothing; an amount change applies to
  later days only.
- **Removal:** the bonus line removed alone; the quest line's removal leaves the day and the bonus; a removed bonus
  is never paid again for that day; replay.
- **Settings door:** owner sets; an editor refused (`AN404`-style, nothing written); another tenant `AN404`; single-day,
  results final, archived; a closed day or weekday touching a started day refused, a future one accepted; dates outside
  the event refused; replay; audit rows.
- **Concurrency:** two completions of one enrollment on one day on two connections: one row, one bonus; a meet of A and
  B crossing B's own scan in another quest, both orders: no deadlock; two first-of-the-day completions of one player in
  two events at once, both also first-time quest XP, both orders: one daily row, no deadlock; `erase_player` crossing a
  completion that writes both day rows, both orders: no deadlock, nothing written after the erasure commits; the
  settings door crossing a burst of completions: no wait on either side beyond its own row.
- **Daily streak:** any event's completion counts the day (two events, one day: one row); rehearsal does not; the 04:00
  Riyadh boundary; consecutive days 3 → 3, a gap → 1, yesterday-only still alive, two days ago → 0; switch off → no
  row, `own_daily_streak` and the sync answer null, nothing paid; switch back on → the streak restarts; milestones
  3 and 7 paid once each at the sync, a later run reaching 3 again pays nothing (once ever); two concurrent syncs pay
  once; streak XP raises the level and grants the level item; with nothing due the pre-check takes no row lock.
- **FR-421:** a milestone pays XP only: no `ledger_entry` and no `gem_entry` from it; a catalog query asserts
  `gem_entry`'s writers are still only `questify_sync`'s gem step and `gem_buy`, and its source CHECK has no streak
  value; a level crossed by streak XP pays the level's gems through the level source (Q-263's reading, pinned).
- **Integrity:** ledger invariant (`enrollment.score = sum(score_delta)`) and XP invariant (`player_xp.xp =
  sum(xp_entry.delta)`) after each file's sequence; UPDATE/DELETE/TRUNCATE refused on the four new append-only tables.
- **Migration** (the `gems-upgrade.int` style): 0068 applied while a scan transaction is in flight (it holds its
  enrollment and has written its entry) and while a sync is in flight: each waits and completes, no deadlock; the lock
  list matches the tables the SQL alters or references.

**Security** (`apps/api/test/security/*`): outsider: the new tables closed to `anon`, `PUBLIC` and the API role; every

## Proposed decisions and questions

- **ADR-294 / Q-259** the split: T-405 core (migration 0068, API, shared), T-405b standard (app, dashboard, strings).
- **ADR-295 / Q-260** event streak days: per enrollment over open event days (FR-1714's day start, inside the event
  window); closed days are the organizer's closed weekdays and dates, which neither count nor break; day rows written for
  every multi-day event whether on or not; days that have started cannot change.
- **ADR-296 / Q-261** the event bonus: a flat organizer amount (1–100,000, or none), paid by the system with the day's
  first quest completion from streak day 2, ledger kind `streak`, written by a trigger on the quest entry so every door
  pays it; never boosted, no XP, balance 0 while the shop is closed, removable alone, never unpicking the day.
- **ADR-297 / Q-262** the daily streak: the Questify day is 04:00 to 04:00 Riyadh time; any non-rehearsal quest
  completion counts (T-406 adds the daily challenge and word); counted only while the platform switch is on; length
  read, not stored; shown to its owner only.
- **ADR-298 / Q-263** daily rewards: XP only at seeded milestones (3 to 365 days), each once ever, paid by
  `questify_sync`; no items yet; never points or gems; a level crossed by streak XP pays its level gems as any level.
- **ADR-299 / Q-264** the switches: platform `dailyStreak` in the feature registry (on by default; T-703's page flips
  it); the event streak in its own table behind an owner-only door, not `event.config`.
- **ADR-300 / Q-265** no pressure: nothing sold (no freeze or repair), no loss or guilt copy, no countdown or red
  badge, neutral reset copy; T-501's reminders follow the same rule.
