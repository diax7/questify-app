# T-211 — Rehearsal mode

Delivers FR-1721, FR-1722 and FR-1737's rehearsal exception (ADR-080). **Max bar:** it touches the points ledger,
prize handover and tenant isolation (QUALITY_BASELINE). Migration **0032**. Depends on T-210 (activation), and
changes the writers of T-203 (codes), T-206 (desk), T-207 (awards) and T-209 (flags), whose TASKS notes it closes.

Dhia is away: every open choice below is my recommendation, written as a **Proposed** ADR (157 to 160) and a question
(Q-122 to Q-125) he can overturn.

## The core question: rehearsal data against an append-only ledger (ADR-157)

NFR-019 and rule 6 say points entries are never edited or erased; FR-1722 says every rehearsal point is wiped at
go-live. Four ways to hold both:

| Option | How | Verdict |
|---|---|---|
| A. **Stamp and erase** | Each ledger row carries an immutable `rehearsal` flag set at insert. At go-live one definer deletes the event's rehearsal rows (and the completions, reservations, flags hanging off them). The append-only trigger gains one narrow exception: DELETE of a row with `rehearsal = true`, inside that definer only. | **Recommended** |
| B. Keep and reverse | Rehearsal rows stay; go-live appends reversing entries; every read and rule filters `NOT rehearsal` | Rejected: once-per-player quests (`UNIQUE (enrollment, quest, occurrence)`), per-player reward limits, daily award caps, burst counts, member activity, analytics and the ranking rebuild would each need a filter forever; one missed filter leaks rehearsal into the live game. The staff who rehearsed could not complete a one-time quest live. |
| C. Separate tables | `rehearsal_ledger_entry` and twins of every writer | Rejected: doubles the core engine; the twins drift. |
| D. Shadow event | Rehearse on a clone, drop it at go-live | Rejected: the printed QR codes carry the real quest ids (ADR-080's point is to test the real prints). |

Why A keeps the rule's intent: NFR-019 protects the record of real players' points. Rehearsal rows belong to no real
player (only rehearsal accounts write them, below), exist only before go-live, and the user decided they are erased
(ADR-080, Accepted). The audit log is untouched: every rehearsal action and the erase itself (with counts) stay there.
NFR-019 gains one sentence (Proposed): "Rehearsal records (ADR-080) are not part of the record: they are erased at
go-live, and the erase is audited with counts."

**The exception, exactly:** `ledger_append_only()` lets a DELETE through only when `OLD.rehearsal` **and**
`current_setting('questify.rehearsal_wipe', true) = OLD.event_id::text` (set `LOCAL` by the wipe definer). UPDATE and
TRUNCATE stay refused for every row. The API role still has no DELETE grant on `ledger_entry`, so the setting alone
opens nothing; the owner role could always drop the trigger, so the trigger guards against mistakes, as today. Tests:
a live row is refused with the setting on; a rehearsal row is refused without it, or with another event's id; the API
role cannot delete at all; UPDATE of a rehearsal row is refused.

`rehearsal` is set by a `BEFORE INSERT` trigger on `ledger_entry` from the enrollment (`joined_via = 'rehearsal'`),
never by a writer and never granted; a `BEFORE UPDATE` is already refused. A guard trigger on `enrollment` keeps
`joined_via = 'rehearsal'` fixed both ways (a rehearsal row never becomes a real one, or the reverse; `enroll_operator`
and the join paths cannot flip it).

## Who rehearses (ADR-158)

- **Rehearsal accounts are separate enrollments.** A team member joins with the event's **rehearsal code**; the
  enrollment gets `joined_via = 'rehearsal'`. Everything that account does is rehearsal. At go-live the enrollment is
  deleted with its data; team roles (owner, editor, operator assignments) are untouched ("stay joined as team
  members" in the UX means the team, not the test account). To play live, a member joins the normal way.
- A player who already holds a **real** enrollment in the event (pre-joined a Scheduled event) cannot rehearse with
  that account: outcome `already_player` ("You joined this event as a player, so this account can't rehearse.").
  Keeps the rule "rehearsal rows hang only off rehearsal enrollments" free of exceptions. Joining the real way while
  holding a rehearsal enrollment answers `rehearsing` ("You're rehearsing this event. Join again after it starts.").
- **The code:** shown on the event Overview to the owner and editors in scope (UX: "Rehearsal code: SPRING-7Q").
  Shape `XXXX-XXXX` (31 unambiguous capitals and digits); join codes are letters and digits only, so the two never
  collide and the app keeps **one** code box: the join endpoint routes a hyphenated code to `join_rehearsal`. Created
  on first view; owner or editor can **rotate** it (the old one stops). Same join throttle as join by code.
- **Who is "the team":** whoever the owner or an editor gives the code to. Staff accounts have only an email, so the
  database cannot tie a phone to a team member; a standing code is what the UX designed. Two limits stop a leaked code
  turning into a free unpaid event (F-265): **at most 25 rehearsal accounts per event** (constant until T-703's
  settings; `RJ409 full`), and **Erase rehearsal** (below) removes every rehearsal account. Q-122 asks whether Dhia
  prefers single-use passes per member.
- Rehearsal works on **Draft and Scheduled** events, activated or not (FR-1737's exception), never once live, ended
  or archived. Rehearsal accounts skip access type, guest list, email domain, join fields, welcome points and the
  player limit (they take no seat: the `enrollment_player_limit` trigger skips them).
- **Operators** need no rehearsal account to work: station scans, awards and the desk act on rehearsal players in
  rehearsal (below). An operator who wants to play-test joins with the code like anyone (FR-906's `can_play` does not
  apply to a rehearsal account; it governs the live game).

## Rehearsal plays like live (ADR-159)

One helper replaces each writer's `status_now <> 'live'` check: `play_phase(ev event, enrolled enrollment) RETURNS
text` → `'live'`, `'rehearsal'`, or a refusal (the writer's existing not-live error).

- `'rehearsal'` when the event is draft or scheduled by `event_status_now` **and** the enrollment is a rehearsal one;
  a real enrollment before go-live is refused exactly as today.
- In rehearsal the event counts as live for play: quests complete, the **shop is open** (`shop_state` treated as
  `open`), the **desk ignores its hours**, awards (operator, staff, bulk) and removals work, flags are raised, spending
  lowers rank when the event's option is on. Per-quest and per-reward rules (limits, stock, opens/closes times,
  cooldowns, caps) apply as written, so the team sees what players will see (Q-125).
- A bulk award in rehearsal targets rehearsal accounts only; the staff award and the desk refuse a real player before
  go-live as today.
- **Digital rewards** (T-203 note): a rehearsal reservation of a digital reward never touches the code pool or
  `units_out`; it shows a test code `TEST-XXXX-XXXX` (random, not stored as a pool code) with the strip "Test code:
  rehearsal". No real code is ever shown in rehearsal, so none is lost (Q-123).
- Item and experience rewards reserve real units in rehearsal (the team tests "sold out"); the erase gives them back.
- Writers to change (latest bodies, `CREATE OR REPLACE` with only the phase check moved): `record_completion` (0030),
  `reserve_reward` (0031), `end_reservation` (0029), `finish_handover` (0031) and `start_collect` / desk functions
  for hours, `grant_manual_award`, `staff_award`, `operator_award`, `bulk_award` / `quest_bulk_targets`,
  `remove_award` (0030), `event_shop` / `my_redemptions` (shop state), and the member reads a rehearsal account needs
  on a draft event (event home, `member_event_quests`, operator station lists). A DB test lists every function that
  calls `event_status_now(...) <> 'live'` and asserts each went through `play_phase` or is on an allow-list with a
  reason (no writer is missed now or later).

## The go-live moment and the erase (ADR-160)

Live is computed (`event_status_now`); the tick only stores it. So the erase cannot wait for one transaction.

- **`event_rehearsal`** `(event_id PK, organizer_id, code UNIQUE, code_set_at, first_play_at, erased_at, erase_counts
  jsonb, live_wiped_at)`: forced RLS, read by the event's team in scope and admins, **no write grant**.
- **`wipe_rehearsal(event, reason 'go_live'|'erase')`** (internal, no grant), under `SELECT … FOR UPDATE` on the
  `event_rehearsal` row, deletes in FK order: `ledger_note` and `manual_award_key` of rehearsal entries →
  removals → other rehearsal `ledger_entry` rows → `reward_code` links (none expected, asserted) → `redemption` →
  `quest_completion` → `flag` (FKs are RESTRICT: flags before enrollments, T-209 note) → `bulk_award` rows left with
  no notes → `join_answer` → the rehearsal `enrollment` rows. Then: `units_out` minus the rehearsal reservations that
  held a unit (reserved and handed over; T-206 note: handover entries go with them), `mark_ranking_repair(event)`,
  counts into `erase_counts`, one audit entry `event.rehearsal_erased` with the counts and reason. `redeem_paused_at`
  needs no clearing: only rehearsal enrollments can have it before go-live, and they are deleted (asserted).
- **At go-live:** the tick's `advance_event_lifecycle` calls the wipe for every event it moves to live; and the first
  live write to an event whose `event_rehearsal` row has `live_wiped_at IS NULL` runs the wipe inline (inside
  `play_phase`, before the writer locks the enrollment). Whichever comes first wins; the other finds `live_wiped_at`
  set and does nothing. An event that never rehearsed has no row: the hot path is one primary-key read, no lock.
- **Races:**
  - A rehearsal writer takes `FOR SHARE` on the `event_rehearsal` row **before** any enrollment lock, then re-checks
    `live_wiped_at IS NULL` and `starts_at > clock_timestamp()` (not `now()`, which is frozen at the transaction's
    start). If go-live happened while it waited: `RE409 started` ("The event just started. Rehearsal has ended.").
    So a scan that began a moment before the start either commits before the wipe (and is wiped) or is refused.
  - The wipe takes `FOR UPDATE` on the same row, so it waits for rehearsal writers in flight and its DELETEs (new
    snapshots in READ COMMITTED) see their rows. Lock order everywhere: `event_rehearsal` → `enrollment` → `reward`.
  - DB tests: a rehearsal scan and the wipe in two connections both ways round; a live scan arriving at the start
    while rehearsal data exists (wiped inline first, then scored from zero); two live scans racing the inline wipe.
- **Erase rehearsal** (owner or editor, Draft or Scheduled): the same wipe with reason `erase`, so a second rehearsal
  starts clean and a leaked code's accounts are gone. Idempotency key; audited.
- A DB test reads `pg_constraint` for every foreign key to `enrollment`, `ledger_entry`, `redemption` and
  `quest_completion` and fails when a table is not handled by the wipe (a future table cannot silently block go-live).

## API

- `POST /v1/events/join` with a hyphenated code → `join_rehearsal(code)`: outcomes `joined`, `already`,
  `already_player`, `full`, `closed` (live, ended, archived, or no such code: one answer, nothing to probe).
- Organizer: `GET …/events/{id}/rehearsal` (member in scope) → `{code, players, counts: {completions, points,
  reservations, flags}, firstPlayAt, erasedAt}`; `POST …/rehearsal/code` rotate (owner, editor) → `{code}`;
  `POST …/rehearsal/erase` (owner, editor; Idempotency-Key) → the counts.
- Player and operator reads carry `rehearsal: true` on the event so the app shows the strip.
- New errors, Arabic and English: `rehearsal_full`, `rehearsal_started`, `already_player`, `rehearsing`.
- Core module for mutation testing: `src/rehearsal/rehearsal.ts` (code shape and routing, outcome mapping, the view).

## Plan review (CTO, 86 → about 93 with the fixes)

Folded in; these override the sections above where they differ.

1. **Two helpers, not one (MAJOR).** `play_phase(ev, enrolled)` is STABLE and only classifies (`live`, `rehearsal`,
   or NULL for refused), so the STABLE reads (`event_shop`, `my_redemptions`, home, `member_event_quests`) can call
   it. `ensure_rehearsal_wiped(event)` is VOLATILE: it runs the go-live wipe when due and, for a rehearsal writer,
   takes the shared lock and re-checks the start. Every writer and every join path calls it first. The coverage test
   asserts that every VOLATILE SECURITY DEFINER calling `event_status_now` calls it (or is on a reasoned allow-list)
   and that no STABLE function does; it matches functions, not the text `<> 'live'`.
2. **Join paths (MAJOR).** `join_event`, `join_invited`, `join_rehearsal` and `enroll_operator` call
   `ensure_rehearsal_wiped` first, so between the start and the tick nobody gets a stale `rehearsing` reply.
   `enroll_operator` and `join_core` answer `rehearsing` for a rehearsal enrollment **before** their INSERT and
   before the branch that rewrites `joined_via` (which the guard would otherwise raise on). An operator who already
   joined the event as a player cannot rehearse with that account (the same `already_player` rule as any player).
3. **Lock order and the tick (MAJOR).** One order everywhere: `event` → `event_rehearsal` → `enrollment` → `reward`.
   The tick's wipe is its own step, `wipe_due_rehearsals()` listing due events and wiping **one event per
   transaction** (as the reservation returns do in `src/events/tick.ts`), not inside `advance_event_lifecycle`.
   A two-connection test runs `join_rehearsal` against the wipe.
4. `units_out` is **recomputed** from the remaining redemptions that hold a unit, and a test asserts it equals them.
5. The digital test code is derived from the redemption id: `'TEST-' || upper(substr(md5(id::text), 1, 8))`, the
   same on every view; no column.
6. (See 1.) The coverage test reads `pg_proc`, not the text.
7. The clock re-check applies only when the stored status is `scheduled`. A **Draft** never goes live by time
   (only activation makes it scheduled), so a draft whose start has passed can still rehearse; documented here.
8. `join_rehearsal` takes `event FOR SHARE`, then `event_rehearsal FOR UPDATE`, then counts, so two joins cannot
   both take the 25th place; a two-connection test covers it.
9. Ranking: verified during the build; if the repair scan's live-only read leaves rehearsal without a ranking, it
   becomes a T-504 note rather than a change to the ranking tick.
10. A quest or reward with rehearsal rows cannot be deleted (RESTRICT keys): the API answers 409
    `rehearsal_data` ("Erase rehearsal first.") in both languages.
11. After the wipe the app's rehearsal account finds no enrollment: the event screen says "Rehearsal ended. Join to
    play." with the join box, not a dead end.
- Nits: the wipe resets `questify.rehearsal_wipe` to `''` at its end; the stamp trigger is named
  `ledger_a_stamp_rehearsal` so it sorts before `ledger_operator_play_guard` (it sets a column the guard does not
  read, so order does not matter, but the name makes it plain); Q-122 records the free-event risk.

## As built (differences from the plan above)

- The player's side has its own routes, `GET /v1/rehearsals/{code}` and `POST /v1/rehearsals/join`, instead of a
  hyphenated code inside `POST /v1/join`; the app still has one code box (a hyphenated code opens the rehearsal join).
  The code check lives in the shared package (`parseRehearsalCode`), used by the app and the API.
- The alphabet has 32 characters (capitals and digits without I, O, 0 and 1).
- Erase takes no Idempotency-Key: a second erase removes nothing and answers zero counts.
- A rehearsal scan arriving after the start is not refused with a new error: the wipe has removed its account, so it
  gets the engine's usual "not found", and the app shows "Rehearsal ended. Join to play." when Home answers 404.
- `first_play_at` is filled by the wipe (the first rehearsal quest entry) and read live by the card before that, so no
  writer updates the rehearsal row (no lock upgrade between two rehearsal scans).
- The strip shows on the player's Home, the rehearsal join screen, and operator Home, Desk, Tools and the station
  scanner (a Draft or Scheduled event in operator mode is a rehearsal, OPERATOR_MODE §2.4).
- The Players page badges a rehearsal account (`event_players` gains `rehearsal`).
