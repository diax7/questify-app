## Decisions

### The store (ADR-343)

One **notice** per thing that happened (one announcement, one flash launch, one join decision). One **notification**
row per recipient: **the center's row is the record of every message** (FR-1104, FR-1824): every push points at one,
a refused permission or a muted topic still gets one, and the history screen lists them. One **push_send** row per
notification and device: the outbox. Devices are tied to the **sign-in** (the refresh family of T-107), so sign-out,
the 10-family limit and a reused refresh token stop pushes with no change to sign-in code. Kinds are **seeded rows**
(`notice_kind`), so each later slice adds its kinds by inserting rows, not by widening CHECKs. A producer writes only
the notice; every center row and send is written by the worker (§ Review 2).

### Sending (ADR-345)

- **An in-process worker loop, not pg-boss** (ADR-109's "workers inside the API container"; the T-306b/T-409 tick and
  lease pattern, already tested): while work exists it loops (fan-out step, then a claim round), and sleeps 1 s
  (jittered ±20%) when idle; settle every 10 minutes, switch on or off. pg-boss would add a dependency and a second job
  store for what one indexed table with leases already does; it is not introduced. Several API instances share the
  outbox through `SKIP LOCKED`. **The worker has its own small pool** (built from `poolOptions`, at most 3 connections),
  so a large fan-out never takes the API's connections, and the T-306b idle-transaction limit holds for it.
- **Fan-out:** `audience='player'` notices first (one row each, about a second after the producer commits), then event
  notices, 2,000 enrollments a call in enrollment id order with a cursor on the notice, inside the 5 s statement limit.
  A batch that fails (a statement timeout, a deadlock with a registration, a lock timeout) is undone alone and counted
  on the notice, which then **waits out a back-off** before its next try: `retry_after = now() + least(1 min ·
  4^(n−1), 1 h)` (1, 4, 16 minutes, then hourly), so it never holds up the notices behind it and a passing error never
  stops it for good; the alert `push.notice_parked` fires at the third failure in a row; a success clears the count;
  the RUNBOOK's release (clear `retry_after`) is the manual override. A failing personal batch of 500 is undone and its
  oldest due notice tried alone, so a poisoned one is found and backed off the same way (T-501 code review minor 4,
  re-review 1 and 3).
- **Claim rounds, waves and leases:** § Review 3 (at most 200 rows a round, at most 100 from one notice, priority
  personal 0, event 1, promotional 2, then id; sends in waves of 50 per provider; ack after each wave).
- **At most once across leases (as T-409):** a claim sets `sending` with a 60 s lease and a fresh lease token; lease
  expiry (in the claim and in settle) sets `unknown` and clears the token; ack changes a row only when it is still
  `sending` with the same token; `unknown` is never resent.
- **Safe retry:** every attempt of one message carries the **same collapse id** (`apns-collapse-id`, Android
  `notification.tag`, both `n<notification id>`), so a duplicate that did arrive replaces the first on the phone. The
  retry and requeue rules are § Review 3.
- **Expiry:** every kind has a time to live and a producer may give an earlier end (`until`, capped by the TTL); a row
  still queued at its `expires_at` becomes `expired` and is never sent (a flash push an hour late is noise); the
  provider gets the remaining time (`apns-expiration`, Android `ttl`). The center row stays.
- **Holds** are per provider target (`apns:production`, `apns:sandbox`, `fcm`), in memory per worker: an account or
  quota refusal (T-501b's tables) or a tripped breaker holds that target, requeues the affected rows with no attempt
  counted, logs `push.provider_hold {target, code}` at error level, and the claim leaves that target out until the hold
  ends. No account problem ever fails a message.
- **Fallback:** the center. Nothing a player needs exists only in a push.

### Providers (ADR-344)

APNs and FCM are called **directly** (INTEGRATIONS: no relay sees the text), behind one interface:

```ts
type PushTarget = "apns:production" | "apns:sandbox" | "fcm";
type PushMessage = Readonly<{
  token: string; collapseId: string; priority: "high" | "normal"; expiresAt: Date;
  title: string; body: string; channel: string; threadId: string; data: Readonly<Record<string, string>>;
}>;
type PushResult =
  | Readonly<{ kind: "sent" }>
  | Readonly<{ kind: "unknown"; code: string }>        // timeout or reset after the request was written
  | Readonly<{ kind: "requeue"; code: string; retryAfterMs?: number }> // a definite 5xx, or never written
  | Readonly<{ kind: "failed"; code: string }>         // definitely refused for this message, token kept
  | Readonly<{ kind: "invalid_token"; code: string; ambiguous: boolean }> // § Review 4
  | Readonly<{ kind: "hold"; code: string; holdMs: number }>; // account or quota: hold the target, requeue
type PushProvider = Readonly<{
  target: PushTarget; send: (m: PushMessage, deadline: Date) => Promise<PushResult>; close: () => Promise<void>;
}>;
```

- **No new server dependency:** `node:http2` for APNs, `fetch` for FCM, `node:crypto` for ES256 and RS256 (the Gmail
  sender's service-account token code, ADR-112, moves to `apps/api/src/auth/google-token.ts` and serves both).
- **Configuration (all-or-none per provider, like Msegat):** `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_PRIVATE_KEY` (the
  `.p8` PEM, or its base64), `APNS_TOPIC` (the bundle id, no default); `FCM_SERVICE_ACCOUNT` (the JSON or its base64:
  `project_id`, `client_email`, `private_key`, `token_uri`). A partial or malformed set **refuses to start** (the key
  must parse as an EC P-256 private key; the account's key as RSA). **None set: the server starts**, builds no provider
  and logs `push.provider_missing {platform}` at warn level once per start in production; nothing is ever sent for that
  platform (its rows expire into the center only).
- **Startup check:** the APNs provider token is signed once at start (a bad key fails before the first send); the FCM
  OAuth token is fetched in the background at start, and a failure holds `fcm` and logs `push.fcm_auth_failed`.
- **The APNs environment** is the device's, read by the app at registration (§ Review 5).
- **Fake provider** (`apps/api/src/push/fake.ts`) for unit, DB and e2e tests: records messages, scripted results and
  latency. The e2e API uses it.

### Push text and payload (ADR-346)

- **Fixed templates per kind**, title and body, in `packages/shared/src/push/templates.ts` with the strings in
  `messages.ts` (`push.<kind>.title/body`, both languages, ux-araby, gender-neutral phrasing, Western digits, the
  event's terminology tokens such as `{questOne}` resolved from the event's config). No organizer or player text except
  where a later slice says so (T-502's announcement). A kind with no template renders the generic center text ("You
  have a new message" / «لديك رسالة جديدة») and is never pushed, never a 500.
- **Placeholders are an allowlist:** `event`, `quest`, `category`, `reward` (organizer-written public names, frozen on
  the notice at creation in both languages, cut in SQL with `left(name, 40)`) and `date`/`time` (in the event's zone).
  Never a player's name, username, phone or email; never points, gems, balances, ranks as numbers or any amount; never
  an answer, a ticket's text, a submission or a review reason. A unit test enumerates every template and fails on any
  other placeholder.
- **Names:** cut again to 40 UTF-16 units without splitting a pair at render (`trimName`, T-409), and run through the
  T-409 name rule (`invitationNameIssue`): a name that fails it is left out and the template's **nameless variant** is
  used. The title is the event's name when it passes, else "Questify".
- **Language:** a push is rendered in the device's language (registered by the app, the app's chosen language); the
  center renders in the request's language. One renderer for both.
- **Payload: ids only.** APNs: `aps.alert {title, body}`, `sound: "default"`, `thread-id` = event id or `questify`,
  plus `q: {n, k, e, r}` (notification id, kind, event id, the kind's reference ids). FCM: `notification {title, body}`,
  `data {n, k, e, r}` (strings; `r` as compact JSON), `android {priority, ttl, notification {tag, channel_id}}`. Both
  under 4 KB, proven for the longest names in both scripts. No URL ever comes from the server: the app maps kind and
  ids to its own routes (T-501c), so a payload can never open an arbitrary link.

### Who receives (ADR-347)

- Every recipient's **player is `active`** (not banned, not deleted), checked at fan-out and again at the claim.
- **Event-scoped kinds** follow the kind's `membership` rule: `active` (the default: an `active` enrollment, not
  `excluded_from_event`), `decided` (join decision: `active` or `declined`), `none` (help-desk answers: the request is
  the player's own). Pending, left, removed, banned and declined enrollments get no event push (FR-1703, T-208 note).
  A player who leaves between fan-out and the claim gets no push (`skipped`, `not_member`); the center row stays.
- **The event's status** decides the audience (§ Review 1), and **what the member can see** decides whether a quest or
  category may be named to them (§ Review 7).
- **Erasure** deletes the player's notices, notifications, sends, devices and mutes at once (§ Review 6); the claim's
  player check covers a send already in flight.
- **Promotional kinds** need `marketing_state` push opted in now (through `promo_pool('push', ...)`, the one consent
  rule), at fan-out and again at the claim; the OS permission alone never counts. **Without that consent there is no
  center row either** (developer's decision at the T-501 code review, ADR-350 (11)): nothing promotional appears in the
  center without the opt-in; a consent withdrawn after the fan-out skips the push and keeps the row. A promotional center row carries an
  opt-out action to Settings → Offers and notifications (FR-1114, Apple 4.5.4); a tap on a promotional push opens that
  center row (T-501f decides the screen).
- **No quiet hours and no daily cap for any push** (ADR-065, FR-1103; Q-287 answered by Dhia: promotional push too).
  Promotional sends still call `promoSendTime('push', at)`, which returns `at`: `CHANNELS_WITH_WINDOW` stays the one
  place to change it. No per-event brake: a runaway sender is the producing door's own rate limit (T-502).

### Topics and mute (ADR-347)

- Four mutable topics (FR-1115): `announcements` (organizer announcements, flash quests, boosts, polls, a category
  opening, the hidden-category hint), `rank` (top-10 alerts), `community` (community milestones), `reminders` (event
  starting soon, streak, shop closing, session reminders). **The topic belongs to the kind:** a kind with no topic
  cannot be muted in the app (decisions, answers, prizes; the phone's own setting still can), and a personal kind may
  carry a topic (T-503's top-10 push is personal with `rank`; the streak reminder is personal with `reminders`).
  Promotional kinds follow consent, not topics.
- **Mute stops the push, not the message:** a muted topic still gets its center row, unread (the center holds every
  message). Muting after planning skips the queued push at the claim.
- Mutes are **per player, all events** (FR-1115). T-510 adds the event's defaults (FR-1836) as an event-level layer
  under the player's own choice.

### Retention (ADR-343)

Center rows 180 days; outbox rows 7 days after their final state; a notice is deleted once it has no center row and is
over 180 days old; a device row is deleted 7 days after it was marked invalid, when not seen for 60 days, or when its
sign-in family is no longer live; center rows of a deleted player at once (§ Review 6). All in settle, bounded per call.
**Purges walk the primary key from the oldest id** and stop at the first row inside the window (ids grow with time), so
no `created_at` index is needed.

### The app (ADR-349, T-501c)

- **Permission after joining, never at launch (FR-1105):** after a successful join (active or pending), when the OS
  permission is undetermined, the app shows its explainer ("Get told when flash quests drop", with Turn on and Not now);
  only Turn on shows the system prompt. Not now: not again for 30 days, and never again once the OS has answered.
  Android: the channels are created before the prompt and before the token (Android 13 shows no prompt without one):
  one per topic, `personal` and `offers`; `personal` and `offers` use `lockscreenVisibility: PRIVATE`.
- **Never rewarded, nothing blocked (FR-1106):** no code path reads the permission or the device table to pay or open
  anything (a source-scan guard and a DB test).
- **When push is refused:** the center, the bell and every screen work as before; Settings shows "Notifications are
  off on this phone" with "Open phone settings"; the topic switches stay usable (they apply when push is on); no nag.
- **The center is P16** at `/notifications`; the offers screen of T-407b moves to `/settings/notifications` and gains
  the topic switches and the push status. The bell with an unread dot sits on Questify Home and Event Home; Profile →
  Notifications opens the center (FR-1824's history, T-312b).
- **Taps and deep links:** the shared `notificationRoute(kind, eventId, refs)` maps a kind to an app route from a fixed
  table; ids are validated; an unknown kind (an older app) and every promotional kind open the center row. A tap marks
  that one row read. Cold start reads the last response. In the foreground the banner shows and the unread count
  refreshes.
- **Registration:** at launch when permission is granted and on a token change; otherwise at most once a day (the
  server's bucket is 20 an hour). iOS tokens are sent lower-case. The APNs environment comes from the build itself
  (§ Review 5).
- **Sign-out** calls `DELETE /v1/me/push-device` before revoking (best effort; the server stops pushes to a dead
  family anyway).

## The eight review findings, as rules and named tests

### Review 1: the event's status decides the audience (MAJOR 1)

`notice_member_ok` reads `event_status_now(status, starts_at, ends_at)`:

| Status now | Event notices reach | `before_start` kinds (event starting soon) |
|---|---|---|
| `draft`, `scheduled` | rehearsal enrollments only (`joined_via = 'rehearsal'`), `active` | `active` enrollments, rehearsal ones excluded |
| `live`, `ended` | every `active` enrollment | nothing (the start has passed) |
| `archived` | nothing (fan-out writes no center row; the claim skips `archived`) | nothing |

Personal kinds follow their `membership` rule whatever the status, except `archived` events, where event-scoped
personal kinds are not sent either (the center row is still written). Named DB tests (`push-store.int`): **"ended
event: a shop-closing-shaped notice reaches every active member, not only rehearsal accounts"**; "draft and scheduled:
rehearsal enrollments only"; "`before_start` in scheduled: real members, no rehearsal account"; "archived: no center
row, no send"; "an event that ends between fan-out and the claim still sends".

### Review 2: a producer writes one notice and nothing else (MAJOR 2)

- `notice_create(kind, organizer, event, player, refs, params, dedupe, until) → bigint`, internal, is exactly one
  statement: `INSERT INTO notice (...) SELECT ... FROM notice_kind k WHERE k.kind = $kind ON CONFLICT (dedupe) DO
  NOTHING RETURNING id`. An unknown kind inserts nothing and returns NULL. `expires_at = least(coalesce(until, now() +
  k.ttl), now() + k.ttl)`, so a past `until` gives a notice that is already expired, not an error. The table has no
  CHECK a producer's data can fail: `refs` and `params` are built in SQL by the producer from its own rows
  (`jsonb_build_object` of ids; names as `left(name, 40)`), `dedupe` from ids. It reads no device, mute, consent or
  refresh row and writes no center row or send.
- **The worker** fans out `audience='player'` notices first (the center row and its sends about a second later), then
  event notices. All planning reads happen there.
- **Producers are set-based** (T-501d onward): a door that changes many rows in one statement gets a **statement-level
  trigger with transition tables** writing all its notices in one `INSERT ... SELECT` (the reveal's places, a bulk
  community reach). Exception, recorded (confirmed by the second review): `enrollment` (accept-all of up to 5,000 pendings) keeps
  a **row-level** `AFTER UPDATE OF status` trigger with `WHEN (OLD.status IN ('pending', 'declined') AND NEW.status IN
  ('active', 'declined') AND NEW.status <> OLD.status AND coalesce(NEW.joined_via, '') NOT IN ('operator',
  'rehearsal'))`, because Postgres refuses transition tables on a trigger with a column list and a statement trigger
  on `enrollment` would materialize every completion's score update; each firing is one insert. The filter covers a
  later accept of a declined request (`decide_join_request`, 0036) and leaves out a member made an operator
  (`enroll_operator`, pending → active with `joined_via = 'operator'`) and rehearsal accounts. **No per-row `EXCEPTION` block anywhere** (more than 64
  subtransactions in one transaction overflow the subxid cache).
- **Named tests:** T-501 (`push-store.int`): "notice_create with an unknown kind writes nothing and raises nothing";
  "twice with one dedupe: one notice"; "a past `until`: one expired notice, no error"; "a personal notice: no center row
  until the worker runs, then one". Each producer slice: **"a broken kind cannot roll back the door"** (its kind row
  missing: the door commits, no notice) and, for enrollment, **"accept-all of 5,000 pendings stays under 5 s with the
  trigger"**, **"declined → active gives one accepted notice"** and **"made an operator (pending → active, `operator`)
  gives none"** (a rehearsal join gives none either).

### Review 3: sends never outlive their lease, and an outage requeues (MAJOR 3, minors 1 and 2)

- **Claim:** up to 200 rows per round for the targets the worker can send, priority then id, **at most 100 from one
  notice** (a small event's flash push is not stuck behind another tenant's 50,000-row announcement). No sort over the
  queue: the index `(target, priority, notice_id, id) WHERE state = 'queued'` gives the notices with queued rows (a
  loose index scan, a recursive CTE), and a per-notice `LATERAL (... ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED)`
  picks their rows, in priority then notice order, until 200. The claim's timing is taken with a 65,000-row queue
  present. A picked row past its
  `expires_at` becomes `expired` in the same statement instead of being leased; **settle** expires the rest through
  `(expires_at) WHERE state = 'queued'`. The claim never scans the whole queue.
- **Waves:** each target's rows go in waves of at most 50 in flight; **each wave is acked as it ends** (one bulk ack per
  wave), not once a round.
- **Deadline:** the worker reads its monotonic clock (`performance.now()`) **before** sending the claim, so its
  deadline, that moment plus 60 s (the lease) minus 2 s, falls before the database's `lease_until`; the API host's
  clock is never compared with the database's. An attempt starts only when it can end (its 10 s timeout) before the
  deadline; otherwise the row is acked `requeue` without that attempt. This leaves room for three attempts at most; a
  later wave whose rows cannot start in time is requeued whole. **In-lease tries are capped at `8 − attempts`** (the
  claim returns `attempts`), and the ack writes `least(n, 8)`, so a row can never break its wave's ack.
- **Outcomes:**

| What happened | Row becomes | `attempts` |
|---|---|---|
| 200 | `sent` | +1 |
| a definite 500 or 503 answer (after the in-lease retries, 1 s then 2 s, or `Retry-After` when it fits the deadline) | `requeue` → `queued`, sent again by a later claim until `expires_at` | +1 each |
| the connection failed before the request was written | `requeue` | +0 |
| a timeout or a reset **after** the request was written | `unknown` (never resent) | +1 |
| `hold` (account, quota, breaker) | `requeue` | +0 |
| refused for this message | `failed` | +1 |
| 8 attempts reached (written as `least(n, 8)`) | `failed` (`attempts`) | 8 |

- **Breaker:** per target, 10 consecutive 5xx answers or timeouts hold it for 30 s, doubling on each consecutive trip up
  to 15 minutes; one success resets it. A provider outage therefore requeues messages until they expire, never turns
  the queue `unknown` (INTEGRATIONS: "a failed batch is retried with backoff").
- **`push_send.attempts`** (smallint, default 0) counts requests written, so "no attempt counted" is checkable.
- **Named tests:** worker unit: "a 33 s slow provider: no attempt starts after `lease_until − 12 s`, those rows are
  requeued, none becomes `unknown`"; "four waves of 50: four acks"; "500 then 500 then 500: `requeue`, attempts 3";
  "timeout after write: `unknown`"; "connect refused: `requeue`, attempts 0"; "10 consecutive 503: target held 30 s,
  then 60 s, capped at 15 min; a 200 resets"; DB: "a 50,000-row notice then a 10-row notice: the first claim takes 100
  and 10"; "a picked expired row becomes `expired`, not leased"; "8 attempts: `failed`"; **"a row claimed at 7 attempts gets one
  try and is acked `failed` at 8, and the other 49 rows of its wave are acked as usual"**; "a database clock 30 s
  ahead of the host changes no deadline".

### Review 4: uninstalls clean up, ambiguous answers hold (MAJOR 4)

- APNs 410 `Unregistered` and FCM 404 `UNREGISTERED` **always** mark the device invalid (unless it re-registered
  after the claim) and are **not counted** by the guard: a push after an event can find most apps uninstalled.
- The guard counts only the **ambiguous** codes: APNs 400 `BadDeviceToken` and `DeviceTokenNotForTopic`, FCM 403
  `SENDER_ID_MISMATCH` and token-named `INVALID_ARGUMENT`. In one round, 20 or more answers from one target of which
  more than half are ambiguous → that target is held (15 min), those rows requeued, **none of the ambiguous ones
  invalidated**, `push.mass_invalid {target}` logged at error level. Below that, an ambiguous answer invalidates.
- Holds are per target, so a sandbox fault never stops production pushes.
- **Named tests:** "120 answers, 100 `Unregistered`: 100 devices invalid, no hold"; "40 answers, 25 `BadDeviceToken`:
  held, nothing invalid, 25 requeued"; "`apns:sandbox` held: `apns:production` still claimed".

### Review 5: the APNs environment is read from the build (MAJOR 5)

`eas.json`'s `development` and `preview` are `distribution: internal` (ad hoc signing, production APNs), so the build
profile is not the environment. The app reads `getIosPushNotificationServiceEnvironmentAsync()` from `expo-application`

### Review 6: erasure leaves nothing behind (MAJOR 6)

`erase_rows` gains **five** deletes: `notice WHERE player_id = me` (personal notices; cascades to their center rows and

removes the orphan center rows and their sends"; "a producer's personal notice committed after an erasure: settle
removes it"; "a player deleted 25 hours ago is not scanned".

### Review 7: a hidden or targeted quest or category is never named to someone who cannot see it (MAJOR 7)

Generic in T-501, at fan-out and again at the claim. **Event notices:** when `refs` carry `category`, the member must

who cannot see what a notice names gets **no center row and no send** for it. Named tests: "a hidden category's notice reaches only members who

### Lock order (the build adds it to `docs/rules.md`)

**The push store's lock order (T-501, ADR-345).** A producer inserts one notice **after** every lock its own door takes
and reads nothing of the push store, so the notice comes last in every producer's order. The fan-out: notice `FOR
UPDATE SKIP LOCKED` → center rows (insert) → sends (insert); enrollments, players, categories, mutes, devices and consent
are read without locks. The claim, lease expiry and purges: sends `FOR UPDATE SKIP LOCKED`, nothing else locked. Ack:
sends by id; devices `FOR UPDATE` in id order when marking invalid. Register: the device row by family, then the other
row holding the token. No push door locks a player, an enrollment, a consent row or a ledger row. No outside call runs
inside a transaction. The notice carries no counters (no hot row): delivery numbers are aggregated from `push_send` when
a later screen needs them.

## T-501b: the provider clients

**As built (2026-10-28):** ADR-351 / Q-320 record where the build filled this in: FCM over the same HTTP/2 transport
as APNs (not `fetch`), never-processed answers requeued uncounted, a 4-minute idle close, every status mapped, no FCM
`collapse_key`, Google's token endpoint failing to answer requeues while only a refusal holds.

**APNs** (`apps/api/src/push/apns.ts`): one HTTP/2 session per host (`api.push.apple.com` for `apns:production`,
`api.sandbox.push.apple.com` for `apns:sandbox`), opened on first use, reopened after `GOAWAY` or an error, closed on
stop; at most 50 streams in flight (and never above the server's `maxConcurrentStreams`). Provider token: ES256 JWT
(`kid`, `iss` team, `iat`), `dsaEncoding: "ieee-p1363"`, reused and re-signed every 40 minutes (Apple: not more often
than every 20, never older than 60). Headers: `apns-push-type: alert`, `apns-topic`, `apns-priority` 10 (personal,
event) or 5 (promo), `apns-expiration`, `apns-collapse-id`. 10 s per request; `send` honours the deadline it is given,
which the worker sets 500 ms before its own timer (`PROVIDER_MARGIN_MS`, T-501 code review minor 6): a client that gives
up at its deadline must answer "never written" (`requeue`, `written: false`) by then, or the worker's timer counts the
attempt as `unknown`. T-501b's done-when includes the all-or-none provider settings check (a partial or malformed set
refuses to start).

| APNs answer | Result |
|---|---|
| 200 | `sent` |
| 410 `Unregistered`, 410 `ExpiredToken` | `invalid_token`, not ambiguous |
| 400 `BadDeviceToken`, 400 `DeviceTokenNotForTopic` | `invalid_token`, ambiguous (§ Review 4) |
| 403 `ExpiredProviderToken` | re-sign once and resend; a second one → `hold` 15 min |
| 403 `InvalidProviderToken`, `MissingProviderToken`, `Forbidden`, `BadEnvironmentKeyIdInToken`, `UnrelatedKeyIdInToken`; 400 `BadTopic`, `TopicDisallowed`, `MissingTopic`; 429 `TooManyProviderTokenUpdates` | `hold` 15 min (that target) |
| 413 `PayloadTooLarge`, other 400 (`BadCollapseId`, `BadExpirationDate`, `BadPriority`, `PayloadEmpty`, …) | `failed` (our bug; error log) |
| never processed: `REFUSED_STREAM`, a stream above a `GOAWAY`'s last stream id, 503 `Shutdown`, 400 `IdleTimeout` | `requeue` at once (no in-lease retry on that session); the session is reopened |
| 429 `TooManyRequests` (this device) | `failed` |
| 500, other 503 | retry within the deadline, then `requeue` (§ Review 3) |
| timeout or reset after the request was written | `unknown` |
| connection failed before writing | `requeue` |

**FCM** (`apps/api/src/push/fcm.ts`): `POST https://fcm.googleapis.com/v1/projects/{project}/messages:send` with a bearer
from the service account (scope `https://www.googleapis.com/auth/firebase.messaging`), cached until 5 minutes before
expiry, refreshed once on a 401. 10 s per request and per token fetch.

| FCM answer | Result |
|---|---|
| 200 | `sent` |
| 404 `UNREGISTERED` | `invalid_token`, not ambiguous |
| 403 `SENDER_ID_MISMATCH` | `invalid_token`, ambiguous |
| 400 `INVALID_ARGUMENT` | `invalid_token`, ambiguous, only when the details name the token (`BadRequest` field `message.token`, or the FCM error "not a valid FCM registration token"); otherwise `failed` |
| 401 after one refresh; 403 `PERMISSION_DENIED` | `hold` 15 min |
| 429 `QUOTA_EXCEEDED` | `hold` for `Retry-After`, at least 60 s |
| 500, 503 | retry within the deadline honouring `Retry-After`, then `requeue` |
| timeout or reset after writing | `unknown` |

The breaker (§ Review 3) and the guard (§ Review 4) live in the worker, per target, over these results.

## Risks for the plan review

1. **Retry vs at most once.** A definite 5xx is requeued and sent again under the same collapse id; a timeout after the
   write is `unknown` and never resent. A device that ignores the collapse id could show a requeued message twice.
2. **Invalid-token cleanup:** only `Unregistered`/`UNREGISTERED` invalidate unconditionally; the ambiguous codes are
   guarded per target (§ Review 4).
3. **Fan-out cost and the foreign keys.** 50,000 center rows and about 65,000 sends per announcement; no FK on
   `notification.player_id` (settle cleans orphans), FKs kept on `push_send`. Gate: under 30 s on the laptop.
4. **Session-derived device binding.** The door trusts the session hash the API passes; a token registered by another
   player moves to them (a shared phone), which also lets someone who knows a stranger's token take its pushes away.
5. **Triggers as producers (T-501d on):** one insert each, after the door's locks; the `enrollment` exception to
   statement-level triggers is measured (§ Review 2).
6. **Mute keeps the center row unread.** A muted topic still raises the bell's count.
7. **Names in push text.** Organizer names go to Apple and Google; the name rule is a filter, not a gate (as T-409).
8. **Visibility at fan-out time.** A member who reveals a hidden category after its notice was fanned out never gets
   that row (§ Review 7).
