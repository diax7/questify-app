in T-501d to T-501f; FR-1824's history screen moves here from T-312b). Depends on T-107 (sessions and refresh

testing. CranL runs migrations through 0056; T-501 is **0076** (new file).

outside calls); T-501c (the app) is Standard. Each core slice gets a plan review (this plan covers T-501 and T-501b in
full; T-501d to T-501g get a short plan of their own on top of § Owed pushes) and a code review.

**What Dhia must provide before a real push leaves (nothing else waits on it):** the Apple Developer account's APNs
auth key (`.p8`, key id, team id) and a Firebase project for Android (service account JSON for the server,

## Decisions

### The store (ADR-343)

One **notice** per thing that happened (one announcement, one flash launch, one join decision). One **notification**
row per recipient: **the center's row is the record of every message** (FR-1104, FR-1824): every push points at one,
a refused permission or a muted topic still gets one, and the history screen lists them. One **push_send** row per
notification and device: the outbox. Devices are tied to the **sign-in** (the refresh family of T-107), so sign-out,
the 10-family limit and a reused refresh token stop pushes with no change to sign-in code. Kinds are **seeded rows**
(`notice_kind`), so each later slice adds its kinds by inserting rows, not by widening CHECKs.

### Sending (ADR-345)

- **An in-process worker loop, not pg-boss** (ADR-109's "workers inside the API container"; the T-306b/T-409 tick and
  lease pattern, already tested): while work exists it loops (fan-out step, then a claim round), and sleeps 1 s
  (jittered ±20%) when idle; settle every 10 minutes, switch on or off. pg-boss would add a dependency and a second job
  store for what one indexed table with leases already does; it is not introduced. Several API instances share the
  outbox through `SKIP LOCKED`. A later split into its own process starts the same image with only this loop and builds
  its pool from `poolOptions` (T-306b note: `idle_in_transaction_session_timeout`).
- **Fan-out** of an event notice: 2,000 enrollments a call, in enrollment id order with a cursor on the notice, inside
  the API's 5 s statement limit. Personal notices (one recipient) are fanned out in the producer's own transaction.
- **Claim rounds:** up to 200 rows a round for the platforms the worker can send (providers configured, not held, the
  `pushNotifications` switch on), ordered by priority (personal 0, event 1, promotional 2) then id, so a join decision
  never waits behind a 50,000-player announcement. Sends run at most 50 at a time per provider; one bulk ack per round.
- **At most once across leases (as T-409):** a claim sets `sending` with a 60 s lease and a fresh lease token; lease
  expiry (in the claim and in settle) sets `unknown` and clears the token; ack changes a row only when it is still
  `sending` with the same token; `unknown` is never resent.
- **Bounded retry inside one lease (departs from T-409, ADR-345 (3)):** a timeout, a reset connection, 500 or 503 is
  retried at most twice within the lease (1 s then 2 s, or `Retry-After` when it fits), each attempt with the **same
  collapse id** (`apns-collapse-id`, Android `notification.tag`, both `n<notification id>`), so a duplicate that did
  arrive replaces the first on the phone instead of showing twice. This is rule 5's safe retry; SMS could not have it.
- **Expiry:** every kind has a time to live (§ Kinds); a row still queued at its `expires_at` becomes `expired` and is
  never sent (a flash push an hour late is noise); the provider gets the remaining time (`apns-expiration`, Android
  `ttl`). The center row stays.
- **Holds per provider (in memory, per worker):** an account-level refusal (T-501b's table) holds that provider for 15
  minutes (FCM `QUOTA_EXCEEDED`: `Retry-After`, at least 60 s), puts the round's affected rows back to `queued` with no
  attempt counted, logs `push.provider_hold {provider, code}` at error level, and the claim leaves that platform out
  until the hold ends. No account problem ever fails a message.
- **Fallback:** the center. Nothing a player needs exists only in a push.

### Providers (ADR-344)

APNs and FCM are called **directly** (INTEGRATIONS: no relay sees the text), behind one interface:

```ts
type PushPlatform = "ios" | "android";
type PushMessage = Readonly<{
  token: string; environment: "sandbox" | "production" | null; collapseId: string; priority: "high" | "normal";
  expiresAt: Date; title: string; body: string; channel: string; threadId: string; data: Readonly<Record<string, string>>;
}>;
type PushResult =
  | Readonly<{ kind: "sent" }>
  | Readonly<{ kind: "unknown"; code: string }>        // may have arrived (timeout after the retries)
  | Readonly<{ kind: "failed"; code: string }>         // definitely not delivered, token kept
  | Readonly<{ kind: "invalid_token"; code: string }>  // remove the token
  | Readonly<{ kind: "hold"; code: string; holdMs: number }>; // account or quota: hold the provider, requeue
type PushProvider = Readonly<{ platform: PushPlatform; send: (m: PushMessage) => Promise<PushResult>; close: () => Promise<void> }>;
```

- **No new server dependency:** `node:http2` for APNs, `fetch` for FCM, `node:crypto` for ES256 and RS256 (the Gmail
  sender's service-account token code, ADR-112, moves to `apps/api/src/auth/google-token.ts` and serves both).
- **Configuration (all-or-none per provider, like Msegat):** `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_PRIVATE_KEY` (the
  `.p8` PEM, or its base64), `APNS_TOPIC` (the bundle id, no default); `FCM_SERVICE_ACCOUNT` (the JSON or its base64:
  `project_id`, `client_email`, `private_key`, `token_uri`). A partial or malformed set **refuses to start** (the key
  must parse as an EC P-256 private key; the account's key as RSA). **None set: the server starts**, builds no provider
  and logs `push.provider_missing {platform}` at warn level once per start in production; nothing is ever sent for that
  platform (its rows expire into the center only).
- **Startup check:** the APNs provider token is signed once at start (a bad key fails before the first send); the FCM
  OAuth token is fetched in the background at start, and a failure holds FCM and logs `push.fcm_auth_failed`.
- **Fake provider** (`apps/api/src/push/fake.ts`) for unit, DB and e2e tests: records messages, scripted results and
  latency. The e2e API uses it.

### Push text and payload (ADR-346)

- **Fixed templates per kind**, title and body, in `packages/shared/src/push/templates.ts` with the strings in
  `messages.ts` (`push.<kind>.title/body`, both languages, ux-araby, Western digits, the event's terminology tokens such
  as `{questOne}` resolved from the event's config). No organizer or player text except where a later slice says so
  (T-502's announcement).
- **Placeholders are an allowlist:** `event`, `quest`, `category`, `reward` (organizer-written public names, frozen on
  the notice at creation in both languages) and `date`/`time` (in the event's zone). Never a player's name, username,
  phone or email; never points, gems, balances, ranks as numbers or any amount; never an answer, a ticket's text, a
  submission or a review reason. A unit test enumerates every template and fails on any other placeholder.
- **Names:** cut to 40 UTF-16 units without splitting a pair (`trimName`, T-409), and run through the T-409 name rule
  (`invitationNameIssue`, NFKC, control and format characters, addresses, 9+ digit runs): a name that fails it is left
  out and the template's **nameless variant** is used ("A flash quest just dropped" without the quest's name). The title
  is the event's name when it passes, else "Questify".
- **Language:** a push is rendered in the device's language (registered by the app, the app's chosen language); the
  center renders in the request's language. One renderer for both.
- **Payload: ids only.** APNs: `aps.alert {title, body}`, `sound: "default"`, `thread-id` = event id or `questify`,
  plus `q: {n, k, e, r}` (notification id, kind, event id, the kind's reference ids). FCM: `notification {title, body}`,
  `data {n, k, e, r}` (strings; `r` as compact JSON), `android {priority, ttl, notification {tag, channel_id}}`. Both
  under 4 KB, proven for the longest names in both scripts. No URL ever comes from the server: the app maps kind and
  ids to its own routes (T-501c), so a payload can never open an arbitrary link.

### Who receives (ADR-347)

- Every recipient's **player is `active`** (not banned, not deleted), checked at fan-out and again at the claim.
- **Event-scoped kinds** follow the kind's `membership` rule: `active` (the default: an `active` enrollment, not
  `excluded_from_event`), `decided` (join decision: `active` or `declined`), `none` (help-desk answers: the request is
  the player's own). Pending, left, removed, banned and declined enrollments get no event push (FR-1703, T-208 note).
  A player who leaves between fan-out and the claim gets no push (`skipped`, `not_member`); the center row stays.
- **Rehearsal:** while the event is not live, event notices fan out to rehearsal enrollments (`joined_via =
  'rehearsal'`) only, except kinds marked `before_start` (event starting soon), which skip rehearsal enrollments. A
  rehearsal account's center keeps its rows (the team's own phones); no wipe change.
- **Erasure** deletes the player's notifications, sends, devices and mutes at once (`erase_rows` restated); the claim's
  player check covers a send already in flight.
- **Promotional kinds** need `marketing_state` push opted in now (through `promo_pool('push', ...)`, the one consent
  rule), at fan-out and again at the claim; the OS permission alone never counts. A promotional center row carries an
  opt-out action to Settings → Offers and notifications (FR-1114, Apple 4.5.4).
- **No quiet hours and no daily cap for any push** (ADR-065, FR-1103; Q-287 answered by Dhia: promotional push too).
  Promotional sends still call `promoSendTime('push', at)`, which returns `at`: `CHANNELS_WITH_WINDOW` stays the one
  place to change it. No per-event brake: a runaway sender is the producing door's own rate limit (T-502).

### Topics and mute (ADR-347)

- Four mutable topics (FR-1115): `announcements` (organizer announcements, flash quests, boosts, polls, a category
  opening, the hidden-category hint), `rank` (top-10 alerts), `community` (community milestones), `reminders` (event
  starting soon, streak, shop closing, session reminders). **Personal** kinds (decisions, answers, prizes) have no topic
  and cannot be muted in the app (the phone's own setting still can); promotional kinds follow consent, not topics.
- **Mute stops the push, not the message:** a muted topic still gets its center row, unread (the center holds every
  message). Muting after planning skips the queued push at the claim.
- Mutes are **per player, all events** (FR-1115). T-510 adds the event's defaults (FR-1836) as an event-level layer
  under the player's own choice.

### Retention (ADR-343)

Center rows 180 days; outbox rows 7 days after their final state; a notice is deleted once it has no center row and is
over 180 days old; a device row is deleted 7 days after it was marked invalid, when not seen for 60 days, or when its
sign-in family is no longer live. All in settle, bounded per call.

### The app (ADR-349, T-501c)

- **Permission after joining, never at launch (FR-1105):** after a successful join (active or pending), when the OS
  permission is undetermined, the app shows its explainer ("Get told when flash quests drop", with Turn on and Not now);
  only Turn on shows the system prompt. Not now: not again for 30 days, and never again once the OS has answered.
  Android: the channels are created before the prompt and before the token (Android 13 shows no prompt without one).
- **Never rewarded, nothing blocked (FR-1106):** no code path reads the permission or the device table to pay or open
  anything (a source-scan guard and a DB test).
- **When push is refused:** the center, the bell and every screen work as before; Settings shows "Notifications are
  off on this phone" with "Open phone settings"; the topic switches stay usable (they apply when push is on); no nag.
- **The center is P16** at `/notifications`; the offers screen of T-407b moves to `/settings/notifications` and gains
  the topic switches and the push status. The bell with an unread dot sits on Questify Home and Event Home; Profile →
  Notifications opens the center (FR-1824's history, T-312b).
- **Taps and deep links:** the shared `notificationRoute(kind, eventId, refs)` maps a kind to an app route from a fixed
  table; ids are validated; an unknown kind (an older app) opens the center. A tap marks that one row read. Cold start
  reads the last response. In the foreground the banner shows and the unread count refreshes.
- **APNs environment** comes from the build profile (`extra.apnsEnvironment`: development builds `sandbox`, release
  builds `production`; Expo sets the entitlement to development and a release archive turns it into production).
- **Sign-out** calls `DELETE /v1/me/push-device` before revoking (best effort; the server stops pushes to a dead
  family anyway).

## Migration 0076 (new file)

`SET LOCAL lock_timeout = '10s'`; `player`, `event`, `player_refresh` in `SHARE ROW EXCLUSIVE` only where a foreign key
needs it. Never `ledger_entry`, `enrollment` (read only), `xp_entry` or `platform_setting`. Deny by default: every new
table RLS enabled and forced, `REVOKE ALL FROM PUBLIC, questify_app`, no policy; definers `SECURITY DEFINER SET
search_path = public, pg_temp`; every function `REVOKE ALL ... FROM PUBLIC` in its own statement; only doors granted to
`questify_app`. SQL codes `PN***`.

```
notice_kind(                                   -- seeded by each slice's migration; read only at run time
  kind text PK CHECK (kind ~ '^[a-z][a-z_]*$'),
  class text IN (personal, event, promo),
  topic text NULL IN (announcements, rank, community, reminders),   -- NULL = not mutable
  membership text IN (active, decided, none),  before_start boolean DEFAULT false,
  priority smallint (0 personal, 1 event, 2 promo), ttl interval (1 minute .. 7 days))
  CHECK (class = 'promo' ⇒ topic IS NULL)
  -- 0076 seeds no production kind; tests insert theirs as the owner

notice(
  id bigint identity PK, kind → notice_kind,
  organizer_id uuid NULL, event_id uuid NULL, FK (event_id, organizer_id) → event ON DELETE CASCADE,
  player_id uuid NULL,                          -- the one recipient of a personal notice
  audience text IN (player, event), CHECK ((audience = 'player') = (player_id IS NOT NULL)),
  CHECK (audience = 'player' OR event_id IS NOT NULL),
  refs jsonb NOT NULL DEFAULT '{}' (object of id strings only, < 1 KB),
  params jsonb NOT NULL DEFAULT '{}' (frozen public names {ar, en} and dates, < 4 KB),
  dedupe text NOT NULL UNIQUE (1..200),         -- the once-only marker
  fan_cursor uuid NULL, fanned_at timestamptz NULL, expires_at timestamptz NOT NULL, created_at)
INDEX (id) WHERE fanned_at IS NULL

notification(                                  -- the center: one row per recipient per notice
  id bigint identity PK, notice_id → notice ON DELETE CASCADE,
  player_id uuid NOT NULL,                      -- no FK: fan-out must not lock players (lock order); erasure deletes
  event_id uuid NULL, created_at, read_at NULL,
  UNIQUE (notice_id, player_id))
INDEX (player_id, id DESC);  INDEX (player_id) WHERE read_at IS NULL;  INDEX (created_at)

push_device(                                   -- one per sign-in on a phone
  id uuid PK, player_id → player, family uuid NOT NULL UNIQUE,      -- player_refresh.family
  platform text IN (ios, android), token text NOT NULL,
  environment text NULL IN (sandbox, production), CHECK ((platform = 'ios') = (environment IS NOT NULL)),
  CHECK (ios: token ~ '^[0-9a-f]{64,200}$'; android: token ~ '^[A-Za-z0-9_:-]{20,4096}$'),
  language text IN (ar, en), app_version text (≤ 20),
  token_set_at, seen_at, invalid_at NULL, invalid_code text NULL,
  UNIQUE (platform, token))

push_topic_mute(player_id → player, topic text IN (announcements, rank, community, reminders), muted_at,
  PK (player_id, topic))

push_send(                                     -- the outbox
  id bigint identity PK, notification_id → notification ON DELETE CASCADE, device_id → push_device ON DELETE CASCADE,
  platform text, priority smallint, expires_at timestamptz,
  state text IN (queued, sending, sent, unknown, failed, expired, skipped),
  lease_token uuid NULL, lease_until NULL, code text NULL (provider code or skip reason only),
  created_at, sent_at, finished_at,
  UNIQUE (notification_id, device_id), CHECK ((state = 'sending') = (lease_token IS NOT NULL)))
INDEX (platform, priority, id) WHERE state = 'queued';  INDEX (lease_until) WHERE state = 'sending';
INDEX (finished_at) WHERE state NOT IN ('queued', 'sending')
```

The foreign keys on `push_send` stay unless the fan-out gate below is missed (then ADR-334 (3)'s trade applies and is
recorded). A device is **pushable** when `invalid_at IS NULL`, `seen_at > now() - 60 days`, and its family has a live
refresh row (`revoked_at IS NULL AND used_at IS NULL AND expires_at > now()`, the build pins this against
`rotate_player_refresh`).

**Internal (no grant):** `push_system_only()` (`ranking_system()`, no device, READ COMMITTED; PN403 `system_only`);
`notice_member_ok(kind_row, event, player)`; `push_pushable(device)`; `push_plan(notification ids)` (inserts a queued
send per pushable device unless the topic is muted or, for promo, the consent is off); `notice_create(kind, organizer,

### Lock order (the build adds it to `docs/rules.md`)

**The push store's lock order (T-501, ADR-345).** A producer inserts its notice (and, for one recipient, the center
row and its sends) **after** every lock its own door takes, so the notice comes last in every producer's order. The
fan-out: notice `FOR UPDATE SKIP LOCKED` → center rows (insert) → sends (insert); enrollments, players, mutes, devices
and consent are read without locks. The claim, lease expiry and purge: sends `FOR UPDATE SKIP LOCKED`, nothing else
locked. Ack: sends by id; devices `FOR UPDATE` in id order when marking invalid. Register: the device row by family,
then the other row holding the token. No push door locks a player, an enrollment, a consent row or a ledger row. No
outside call runs inside a transaction. The notice carries no counters (no hot row): delivery numbers are aggregated
from `push_send` when a later screen needs them.

## T-501b: the provider clients

**APNs** (`apps/api/src/push/apns.ts`): one HTTP/2 session per host (`api.push.apple.com` for `production`,
`api.sandbox.push.apple.com` for `sandbox`), opened on first use, reopened after `GOAWAY` or an error, closed on stop;
at most 50 streams in flight (and never above the server's `maxConcurrentStreams`). Provider token: ES256 JWT (`kid`,
`iss` team, `iat`), `dsaEncoding: "ieee-p1363"`, reused and re-signed every 40 minutes (Apple: not more often than every
20, never older than 60). Headers: `apns-push-type: alert`, `apns-topic`, `apns-priority` 10 (personal, event) or 5
(promo), `apns-expiration`, `apns-collapse-id`. 10 s per request.

| APNs answer | Result |
|---|---|
| 200 | `sent` |
| 410 `Unregistered`, 400 `BadDeviceToken`, 400 `DeviceTokenNotForTopic` | `invalid_token` |
| 403 `ExpiredProviderToken` | re-sign once and resend; a second one → `hold` 15 min |
| 403 `InvalidProviderToken`, `MissingProviderToken`, `Forbidden`; 400 `BadTopic`, `TopicDisallowed`, `MissingTopic`; 429 `TooManyProviderTokenUpdates` | `hold` 15 min |
| 413 `PayloadTooLarge`, other 400 (`BadCollapseId`, `BadExpirationDate`, `BadPriority`, `PayloadEmpty`, …) | `failed` (our bug; error log) |
| 429 `TooManyRequests` (this device) | `failed` |
| 500, 503, timeout, reset | retry within the lease (§ Sending), then `unknown` |

**FCM** (`apps/api/src/push/fcm.ts`): `POST https://fcm.googleapis.com/v1/projects/{project}/messages:send` with a bearer
from the service account (scope `https://www.googleapis.com/auth/firebase.messaging`), cached until 5 minutes before
expiry, refreshed once on a 401. 10 s per request and per token fetch.

| FCM answer | Result |
|---|---|
| 200 | `sent` |
| 404 `UNREGISTERED`; 403 `SENDER_ID_MISMATCH` | `invalid_token` |
| 400 `INVALID_ARGUMENT` | `failed`; `invalid_token` only when the details name the token (`BadRequest` field `message.token`, or the FCM error "not a valid FCM registration token") |
| 401 after one refresh; 403 `PERMISSION_DENIED` | `hold` 15 min |
| 429 `QUOTA_EXCEEDED` | `hold` for `Retry-After`, at least 60 s |
| 500, 503, timeout | retry within the lease, honouring `Retry-After`, then `unknown` |

**Mass-invalid guard:** in one round, 20 or more answers from one provider of which more than half are
`invalid_token` mean a configuration fault (wrong environment, wrong project, a payload bug read as a token error):
hold that provider, requeue those rows, invalidate nothing, log `push.mass_invalid` at error level.

## Risks for the plan review

1. **Bounded retry vs at most once.** A retry after a timeout can deliver twice; the claim leans on the collapse id and
   tag to merge them on the phone. Is that safe enough on both platforms, and is the lease (60 s) long enough for two
   retries at 10 s each?
2. **Invalid-token cleanup wiping good tokens.** FCM's `INVALID_ARGUMENT` is shared with payload bugs and APNs'
   `BadDeviceToken` with environment mix-ups; the guard is "only the token-named shapes" plus the mass-invalid hold.
3. **Fan-out cost and the foreign keys.** 50,000 center rows and about 65,000 sends per announcement; no FK on
   `notification.player_id`, FKs kept on `push_send`. Gate: under 30 s on the laptop.
4. **Session-derived device binding.** The door trusts the session hash the API passes; a token registered by another
   player moves to them (a shared phone), which also lets someone who knows a stranger's token take its pushes away.
5. **Triggers as producers (T-501d on).** AFTER triggers on `enrollment` (status only, `WHEN` clause), `ticket`,
   `submission`, `event_result`, `quest` and `community_reach` add one insert to hot doors and hide a side effect from
   the door's reader; the alternative is restating six core doors.
6. **Mute keeps the center row unread.** A muted topic still raises the bell's count.
7. **Names in push text.** Organizer names go to Apple and Google; the name rule is a filter, not a gate (as T-409).
8. **Rehearsal audience.** Event notices before going live reach rehearsal enrollments only; a scheduled event's real
   early joiners get only `before_start` kinds.
