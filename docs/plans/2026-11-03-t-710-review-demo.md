Delivers FR-1406, FR-1407, FR-1736 and the review half of FR-303 and NFR-017 (ADR-009, Accepted by Dhia 2026-10-16;
STORE_COMPLIANCE §0.8 and §1.3). Depends on T-703 (done). Migration **0144**. ADR-560 to ADR-569 and Q-520 to Q-526
Proposed. Tier A (sign-in, tenant isolation, admin powers): plan review, build, one code review, mutation on GitHub for
the sign-in and confinement code only.

**Split (ADR-569):** **T-710** builds the reviewer sign-in, the demo tenant and event, confinement, reset, the in-app
account deletion with the fixed code, and the console page (sections 2 to 8). **T-710b** builds the demo-only QR picker

## 0. Plan review (score 84) folded in before the build

## 1. What exists and is reused

- **Player sign-in** (`apps/api/src/players/sign-in.ts`, migrations 0013, 0017, 0038, 0120): `requestCode` checks
  acceptances, normalises the contact (`contactOf`, Saudi mobile only), `openChallenge` takes the send windows and the
  platform SMS budget under a contact lock (`takeSend`) and calls `start_player_challenge` (latest: 0038, 9 args), then

  `keys.playerCodeHash(challenge, typed)`, finds the owner through `player_contact`, issues tokens. Limits:
  `PLAYER_SIGN_IN_LIMITS` (`apps/api/src/auth/limits.ts`): 3 tries a code, 10 wrong a contact per 15 minutes, 30 a day,
  100 per address per 15 minutes, 5 and 10 codes a contact per hour and day.
- **Keys** (`apps/api/src/auth/keys.ts`): one secret, one derived key per purpose.
- **Account deletion** (`apps/api/src/deletion/deletion.ts`, migrations 0038, 0129): a deletion code to the account's own
  contact, then `erase_player`; the shared body is `erase_account(me, key, forfeit, challenge)` (0129), which the admin
  path (`admin_erase_player`) already calls with no challenge. `erase_marks` leaves `erased_mark` rows (`welcomed`,
  `banned`) under the contact fingerprints.
- **Console** (`apps/api/src/console/*`, `console_admin()` re-read in every door, QE403; `throttled` from
  `platform-routes.ts`; access kind `admin` under `/v1/admin/`, 404 to anyone else). Feature overrides per organizer
  (T-711, T-711b: `organizer_feature_override`).
- **Event lifecycle** (`apps/api/src/events/tick.ts`, every 30 s: `advance_event_lifecycle`, archive, rehearsal wipe).
  `event_status_now` is a pure function of the times, so a live event stays live only while `ends_at` is ahead.
- **Joins**: `join_event`, `enroll_operator` and the other definers that insert `enrollment` (T-111, T-204, T-218,
  T-409 invitation joins, rehearsal). Operators are players with a `staff_assignment` (0026).
- **Quest codes** (`apps/api/src/quests/qr.ts`, `codes.ts`): Questify-signed, quest-bound codes; the scanner

  NFC tag, meet code). T-710b feeds a picked string into the same handler.

## 2. The model: one platform row, created from the console (ADR-560)

`review_demo` is a single-row table (`id boolean PRIMARY KEY DEFAULT true CHECK (id)`):

| Column | Notes |
|---|---|
| organizer_id, event_id | The demo tenant and its "App Review Demo" event (FKs, `ON DELETE RESTRICT`) |
| contact | The reviewer phone, `+9665XXXXXXXX` (the `player_contact` shape). Questify's own number (Q-520), never logged |
| contact_key, contact_fp | `keys.contactLookupKey(contact)` and `keys.deletionFingerprint(contact)`, as a challenge stores them |
| player_id | The current reviewer account, NULL until provisioned (FK `player`) |
| code_hash | `keys.reviewerCodeHash(code)` of the fixed code, NULL until the first Prepare |
| window_until | The review window's end; NULL or past = closed. At most 30 days ahead (CHECK in the door) |
| prepared_for, prepared_at, prepared_by | The app version the admin typed (text ≤ 20), when, which admin |
| created_by, created_at | |

`review_demo_player(player_id PK → player, role reviewer|fictional, created_at)` marks every account the demo ever
made, tombstones included, so a retired reviewer never ranks anywhere.

Both tables: RLS forced, `REVOKE ALL FROM PUBLIC`, no grant to any role; definers only. Created by the console door
`console_review_demo_create`, never seeded by a migration (production gets it once, staging its own).

**Create (`console_review_demo_create(contact, contact_key, contact_fp, request)`):** refuses a second run (RD409).
Writes the organizer ("Questify Review Demo", fictional brand; the calling admin as owner, the three acceptances in force
recorded as `create_organizer` writes them), its `organizer_feature_override` row **On** for every overridable feature
(T-711, T-711b), the event (`status = 'live'`, `activated_at/by` = now/admin with no activation request,
`player_limit_mode = 'none'`, `access = 'public'`, `join_methods = {code, qr, link}`, `starts_at = now()`,
`ends_at = shop_closes_at = now() + 60 days`, every event switch on, `operator_play` on), 12 fictional players (fixed
usernames from a list in the migration, no contact, so they can never sign in) with seeded points (the internal payer
`bulk_award` uses, reason "Demo", actor system), and the reviewer account (section 4). Audited
`review_demo.create` (ids only).

**Content** (ADR-568; every quest type, rewards, polls, sessions, a meet quest, games) is built by the admin as the demo
organizer's owner in the ordinary dashboard: configuration is data, and the dashboard already makes every type. The
console page shows a **readiness checklist** (section 8) of every quest type and feature in the registries against what
the demo event holds, so FR-1406's "every feature and quest type" is checked, not remembered.

## 3. The fixed code, decided by the database (ADR-561)

- **The code.** Six random digits (the app's code field), made by the server at every **Prepare for review**, shown once
  to the admin to paste into App Store Connect and Play Console, stored only as `keys.reviewerCodeHash(code)` (new
  derived key, purpose `reviewer-code`, so it can never match a sign-in, deletion or contact code). A rotated auth
  secret invalidates it; the admin prepares again (RUNBOOK).
- **Opening a challenge.** `start_player_challenge` (DROP and CREATE, same 9 args, now `RETURNS boolean`) marks the new
  row `reviewer = true` exactly when `review_demo_open(key)` holds: the row exists, `contact_key = key`,
  `window_until > now()`, `code_hash IS NOT NULL`. It returns that flag. TypeScript only reads it: when true it sends
  nothing (no SMS, no Msegat call) and logs `player.reviewer_challenge` (no contact). The send windows and the platform
  budget are taken as for anyone (one budget unit per reviewer sign-in is negligible and keeps `takeSend` unchanged).
  The random code is still generated and hashed into `code_hash` (NOT NULL) and is never sent.
- **Verifying.** `sign_in_player` (DROP and CREATE with a 7th argument `reviewer_code bytea NOT NULL`; the API passes
  `keys.reviewerCodeHash(typed)` on every verify, so there is no TypeScript branch to get wrong):
  - a challenge with `reviewer = false` never reads `reviewer_code` or `review_demo` (the fixed code cannot sign into
    any other account: it is compared to the challenge's own random hash, and fails like any wrong code);
  - a challenge with `reviewer = true` re-checks `review_demo_open(challenge.contact_key)` (a window closed or a code
    rotated since the challenge opened answers `expired`), compares `reviewer_code` with `review_demo.code_hash`
    (wrong: the same attempts and `wrong` outcome as today), and on success signs in **only** `review_demo.player_id`:
    the owner found through `player_contact` must be that id; if the reviewer account is missing or a tombstone,
    `review_demo_provision()` makes a fresh one in the same transaction (section 4) and signs it in. A reviewer
    challenge never answers `new` (no sign-up token is ever minted by the fixed code) and never `banned` (a platform
    mark on Questify's own number is cleared by provisioning).
- **Closed window.** The reviewer number is treated as any number: a real SMS with a random code goes to Questify's own
  SIM (Q-520), and the fixed code is a wrong code.
- **Limits.** The existing per-contact (10 wrong per 15 minutes, 30 a day), per-address and per-install windows apply
  unchanged, plus 3 tries per challenge. With the default 14-day window an attacker gets at most 420 of 1,000,000
  guesses (0.04%), and a hit opens only the demo account (section 5). No auto-close on failures (it would let anyone
  shut a review); a log line `review_demo.code_guessing` fires once a day when the reviewer contact passes 10 wrong
  codes in a day, and the admin can close the window or prepare a new code.
- **Audit.** Every reviewer sign-in writes `review_demo.signed_in` (actor system, target the player, no contact).

## 4. Reviewer account, reset per build, deletion (ADR-562, ADR-564)

- **`review_demo_provision()`** (internal, no grant): if `player_id` is a live account, nothing. Otherwise it creates a
  player (`username` `Reviewer` plus 4 digits, birth year 1990, default avatar), its `player_contact` with the reviewer
  phone (after the old tombstone let go of it), its fingerprint, the acceptances in force (method `sign_in`), a
  `review_demo_player` row (reviewer), a `staff_assignment` as operator of the demo event (FR-1736: an operator allowed
  to play), deletes `erased_mark` rows under `contact_fp` (so the new account gets the event welcome), and sets
  `review_demo.player_id`. The reviewer is **not** enrolled: joining by the code in the review notes is part of the
  walkthrough (join → quest → points → leaderboard → redeem → report/block → delete).
- **Prepare for review (`console_review_demo_prepare(code_hash, days, version, request)`)**, the reset per new build
  (FR-1736, ADR-564): `days` 1 to 30 (default 14), `version` the build being submitted. Under the `review_demo` row lock:
  erase the current reviewer through `erase_account(me, NULL, true, NULL)` (forfeits held prizes), clear its marks,
  `review_demo_provision()`, store the new code hash, `window_until`, `prepared_for/at/by`; audited
  `review_demo.prepare` with the version and window end (never the code). The admin then signs in as the reviewer and
  plays to level 3 (at least 40 gems) per T-806, so the reviewer can get one gem item. The reset is the console's, not
  automatic on the app's `X-App-Version` (Q-522): an automatic reset at the reviewer's first sign-in would wipe that
  pre-play.
- **Close window (`console_review_demo_close(request)`)**: `window_until = NULL`, revokes every session and refresh
  family of the reviewer (`revoke_family`), audited. The lifecycle tick does the same when `window_until` passes
  (`review_demo_tick`, section 6), so a stale reviewer token stops within 30 seconds of the window's end.
- **In-app account deletion** (Apple 5.1.1(v); reviewers test it): `start_deletion_challenge` (restated) marks the
  deletion challenge `reviewer = true` by the same `review_demo_open` rule and the API sends nothing; the deletion code
  check compares `keys.reviewerCodeHash(typed)` with `review_demo.code_hash` for that challenge only (same refusal
  shape as section 3). The erasure is the ordinary one. The next reviewer sign-in provisions a fresh account. The web
  deletion page (FR-127) uses the same functions and so behaves the same.
- **Contact change** (T-108) is refused for any `review_demo_player` (409 `contact_locked`, RD409 in
  `start_contact_change`): it would send a real code to a stranger's number and move the fixed number (Q-523). The app
  shows "This demo account's phone number can't be changed." / «لا يمكن تغيير رقم الجوال لهذا الحساب التجريبي.»

## 5. Confinement, both ways, in the database (ADR-563)

- **Enrollment guard** (trigger `enrollment_review_demo_guard`, BEFORE INSERT OR UPDATE OF `event_id, player_id`, enabled
  ALWAYS): if the event is the demo event, the player must be in `review_demo_player`; if the player is in
  `review_demo_player`, the event must be the demo event. Otherwise `RD404`. One rule covers every join path, present
  and future (`join_event`, `enroll_operator`, invitation joins, guest list, rehearsal, operator invites). The join
  routes map RD404 to the same 404 `event_not_found` an unknown code gets.
- **Staff assignment guard**: the same rule on `staff_assignment` for a demo player (an organizer cannot make the
  reviewer an operator elsewhere; the demo owner cannot assign a real player).
- **Event guard** (trigger `event_review_demo_guard` on `event`, the demo event only): refuses DELETE, a status other
  than `live`, `public_list` in `join_methods`, `access` other than `public`, a player limit, and an `ends_at` or
  `shop_closes_at` earlier than now + 1 day (RD409). `end_event_early` is refused through it. Organizer deletion is
  refused while `review_demo` names the organizer (FK RESTRICT).
- **Never public**: `public_events` (restated from 0114) also excludes the demo event (defence in depth beside the
  `public_list` guard). `public_event(code)` still answers by code (the reviewer's join card needs it; the name is
  fictional) and the join refuses anyone else.
- **Never in Questify-wide lists or sends**: `questify_ranking` and `questify_season_top` leave out
  `review_demo_player` (the reader's place takes them off as it takes off inactive players); `promo_pool`,
  `marketing_audience` and `invitation_candidates` leave them out (no promotional push or SMS ever reaches the demo
  number); the invitation campaign request door refuses the demo event (RD409: a campaign would SMS real players about a
  fake event). Push to the reviewer's own registered phone stays on: it is the reviewer's device, and the review notes
  show notifications working.
- **What reaches outside the tenant**: nothing by SMS or email. Help-desk tickets go to the demo team (the admin
  owner); a report from the reviewer goes to Questify's platform queue like any report (the moderators see the demo
  organizer's name).

## 6. Never ends, never archives, no activation (FR-1736, ADR-567)

- Created live (section 2); no activation request ever exists for it.
- `review_demo_tick()` (definer, system only, called by `events/tick.ts` after the lifecycle step, `FOR UPDATE SKIP
  LOCKED` on the row): keeps `ends_at` and `shop_closes_at` at least 60 days ahead (moved to now + 90 days when under
  60; "live: end may only move later" holds), and closes an expired window (section 4). Even with the tick down for
  59 days the event stays live, and the guard refuses any manual shortening. Archive needs `ended`, so it never runs.
- The Home countdown therefore shows "ends in about 2 to 3 months", a believable live event.

## 7. What the reviewer can and cannot do (ADR-566)

- **Can, in the demo event**: every player feature the binary has (every quest type, rankings with the 12 fictional
  players, shop and rank prizes, the help desk, reports and blocks, polls, community goals, flash quests and boosts,
  mini-games, passport, My QR) and staff mode as an operator allowed to play (Pair a device, Rotating QR, the desk).
  Questify-wide features too: XP and levels, achievements, Questify quests, daily games, streaks, the gem shop
  (cosmetic, earned gems only).
- **Prizes**: fictional rewards ("Demo coffee voucher") with stock; digital ones carry `DEMO-` placeholder codes the
  admin enters, never a real gift card. A reviewer may reserve and, as an operator, hand over at the desk. There are no
  payments in Questify (ADR-002), so nothing to demo or to block.
- **Cannot**: join any other event; be assigned elsewhere; change their phone; appear in the Questify-wide ranking,
  marketing audiences or invitations; trigger any SMS or email to anyone. A guessed fixed code yields exactly this.

## 8. Console page and API (T-710)

`/console/review-demo` ("App Review demo" / «العرض التجريبي لمراجعة المتجر»), admin only:

- **State**: the event (link to its dashboard), the reviewer account (username, signed in last), the window (open until,
  prepared for version), the fictional players count.
- **Readiness checklist**: each quest type in `packages/shared/src/quests/registry.ts` and each event feature in the
  switch registry, with present/missing in the demo event, plus the organizer overrides; the RUNBOOK's review-day items
  (live poll with 1,440 minutes, running community goal with an unlock step, a scheduled flash quest and a boost, an
  NFC quest, a station paired for the screen-QR quest) as present/missing. Read only (`review_demo_readiness()`).
- **Actions**: Create (once; asks for the reviewer phone), Change reviewer number (closes the window, revokes the
  reviewer's sessions, cancels open reviewer challenges), **Prepare for review** (version, days; shows the new code once
  with Copy and the warning "Shown once. Paste it into App Store Connect and Play Console now."), Close window.

Routes (access `admin`, `throttled` bucket `console_review_demo`, 30 writes an hour, 120 reads a minute):
`GET /v1/admin/review-demo`, `POST /v1/admin/review-demo` (create), `PUT /v1/admin/review-demo/contact`,
`POST /v1/admin/review-demo/prepare` → `{code, windowUntil}`, `POST /v1/admin/review-demo/close`. The player routes are
unchanged (`/v1/auth/code`, `/v1/auth/verify`): the reviewer signs in like anyone. Every string in Arabic and English
(`packages/shared/src/i18n/messages.ts`), RTL checked, Western digits.

## 9. T-710b: the demo-only QR picker (FR-303's review half, ADR-565)

- **Door** `review_demo_codes(event)` (definer, API role): answers only when the caller (`app_player_id()`) is
  `review_demo.player_id`, `event` is `review_demo.event_id`, the window is open and the caller is an active member;
  otherwise `RD404`. Returns ids, versions and titles of the event's printable codes: visible scan quests, passport steps,
  hidden categories, NFC tags (their QR alternative). TypeScript signs them with the existing keys (`questCode`,
  `stepCode`, `revealCode`, `tagCode`) into the URLs a printed sticker carries. No new completion path: the app feeds
  the picked string to the scanner's existing handler, and every completion rule (membership, windows, limits, the
  quest's own state) applies unchanged.
- **Meet quests**: `review_demo_meet_code()` issues a meet pass for one fictional player of the demo event, only under
  the same caller rule, so the reviewer can complete a meet quest without a second phone.
- **Not in the picker**: a station's rotating code and the kiosk (the review notes link a paired station page, as
  STORE_COMPLIANCE §1.3 says).
- **Route** `GET /v1/events/{id}/review-codes` (player; 404 to anyone the door refuses, the same answer as an unknown
  event). **Home** (`GET /v1/events/{id}/home`) adds `reviewDemo: true` only under the same rule (absent otherwise).
- **App**: the scanner shows "Pick a code (review only)" / «اختيار رمز (للمراجعة فقط)» when `reviewDemo` is true, also on
  the camera-permission card; a sheet lists the codes by title; picking one runs the scanner's handler. No image picker,
  no gallery access (FR-303 holds for everyone else). `npx expo export` passes; a store build is needed (T-806).

## 11. Tests (test first)

## 13. Risks

- **Restating `sign_in_player` and `start_player_challenge`** (the sign-in core): the builder copies 0120's and 0038's
  bodies unchanged except the reviewer branch, and the existing sign-in suites must pass untouched. Highest review
  attention here.
- **Many restated readers** (section 10.4): each restatement must start from the latest body; a stale copy silently
  undoes a later fix. The builder diffs each against its latest definition in the commit message.
- **Erasing the reviewer on Prepare** forfeits its held prizes and leaves a tombstone per build (a few a year).
- **A leaked fixed code** opens only the demo account and only until the window closes; Close revokes at once.
- **The reviewer number must be Questify's** (Q-520): a real person's number would be denied codes while a window is
  open.
- **Apple and Google review at once on one account** (Q-521): they share progress; harmless, and Prepare resets it.
