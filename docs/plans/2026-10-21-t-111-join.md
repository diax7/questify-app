# T-111 — Join: by code, QR, link and the public list; the join card; browse before sign-in; several events

Delivers the server half of FR-101, 102, 103, 104, 105, 111, 112, 121, 122. The app screens (the scanner, the join
card, the event switcher, the sign-in screens carried from T-107 and T-110) wait for the app shell (T-009) and stay
on this task, unticked parts noted. Depends on T-107, T-102. Core (tenant isolation, sign-in): Max.

## Scope note

- **Found while scoping, the reason this task is core:** the `enrollment_insert` policy (0008) lets any signed-in
  player insert an `active` enrollment for **any** event whose id they know, private ones included, with no code.
  Nothing calls it yet (no join route exists), but the hole is in the database. This task closes it: players join only
  through a definer that checks the code, the access type, the join methods and the event's state.
- **Reuse:** `event` (`join_code` unique case-insensitively, 6 characters from a 31-letter alphabet; `access`
  public|unlisted|private; `join_methods` code|qr|link|public_list, `public_list` only for public events),
  `enrollment` (status pending|active|left|removed|banned, unique per event and player), `event_status_now`, the
  player guard, `auth_throttle` and its buckets, the outsider and cross-tenant suites, the route inventory.
- **Out of scope:** approval of private joins, invited people skipping it, the hard limit and waiting list (T-218);
  join fields and answers (T-212); leaving (T-208); the event web page and store links (T-112); the official rules
  text (T-214); prizes in the browse view (the shop task, T-2xx: no reward table yet); drawing the join QR (ADR-115
  is Proposed).

## Decisions (tactical; for the CTO to challenge)

1. **One join route, by code or from the list.** `POST /v1/join {joinCode, via: code|qr|link, cardVersion}` or
   `{eventId, via: public_list, cardVersion}` (player). The QR and the invite link both carry the code
   (`https://questify.sa/{lang}/e/{CODE}`, T-112 serves it); `via` says which way the person came. **`via` is a UX
   setting, not a security boundary:** the code is what grants access; an organizer who turns `code` off still has
   the code printed in the QR. The server refuses a `via` the event turned off (`join_method_off`), as the screens do.
2. **`join_event(code text, event uuid, via text, card text)` definer** (pinned search path, `REVOKE ALL FROM PUBLIC`,
   `GRANT EXECUTE TO questify_app`), bound to `app_player_id()` (an active player). It finds the event by code
   (case-insensitive) or, for `public_list`, by id **only if** the event is public and lists itself; an unknown code,
   a draft or archived event, or a private event looked up by id all answer the same `not_found`. The event must be
   `scheduled` or `live` now (`event_status_now`); ended is `event_ended`. Outcomes:
   - public or unlisted → `active`; private → `pending` (ADR-105: the owner approves, T-218; a pending player cannot
     score, QC403, and is not ranked);
   - already `active` or `pending` → the same enrollment (idempotent, 200 with `alreadyMember: true`);
   - `left` → back to `active`/`pending` by the same rule (FR-1603's rejoin rules belong to T-208; until then a player
     who left may come back);
   - `removed` or `banned` → `not_allowed` (403), saying nothing more.
   The enrollment row records `card_version` and `joined_via`. **The player's direct INSERT path on `enrollment` is
   dropped** (the policy branch and the INSERT grant for players; organizers keep theirs for later tasks). The player
   UPDATE path stays only for `left` (the guard already limits it).
3. **The join card (FR-121, ADR-089, PD-17):** a shared `JOIN_CARD` with a version (`0.1`) and the list of what the
   organizer receives (username, avatar, points and quest progress in this event, prize handovers; join answers are
   added with T-212 and bump the version). `GET` returns it with the event; `POST /v1/join` must send the version shown
   (`card_version_stale` 422 with the current card, like T-110). The rules line says the official rules open from the
   card (T-214 writes them).
4. **Browse before sign-in (FR-104, 111):** anonymous, read through definers (no grant on `event` or `quest` for
   outsiders; the API role reads with an empty context):
   - `GET /v1/public/events?cursor=` → events that are public **and** list themselves, scheduled or live, soonest
     first, 20 a page: `{id, name, venue, kind, startsAt, endsAt, statusNow, joinCode}`. Never unlisted or private.
   - `GET /v1/public/events/{joinCode}` → the join card's event: `{id, name, venue, kind, startsAt, endsAt, timezone,
     statusNow, access, joinMethods, card}` for any scheduled or live event (private too: the code is the secret,
     FR-105). Draft, archived and unknown codes are the same 404.
   - `GET /v1/public/events/{joinCode}/quests` → categories and quests (name, points, type, hidden categories left
     out) for **public and unlisted** events only; a private event's quests need membership (T-113).
   - Rate limits per address (keyed tag, like sign-in): 60 code lookups a minute (6 characters from 31 letters is
     about 887 million codes; at 60 a minute an address needs centuries to sweep them), the list 120 a minute.
     Throttle rows in `auth_throttle` under new buckets `join_lookup` and `event_list`.
5. **Several events (FR-122):** `GET /v1/me/events` → the player's `active` and `pending` enrollments with the event's
   name, dates, `statusNow`, score and balance, newest join first. The switcher is the app's (T-111 screens).
6. **Join QR recognition (FR-102):** `parseJoinLink(text)` in `packages/shared` accepts `https://questify.sa/{ar|en}/
   e/{CODE}` (and the bare code) and returns the code or "not a Questify join code"; the app's scanner uses it. The
   host is a constant until the domain is live (Q-083 area); staging uses the same parser with its own host list.
7. **Audit:** `player.join` audit entries per join (event, via, the resulting status), organizer-visible as the
   event's history.

## Revision 1 (after CTO plan review 1, 84/100) — overrides the sections above where they differ

- **M1, throttle misses only:** successful lookups write nothing (a venue's attendees share one address at the door).
  One bucket `join_code_miss` counts unknown codes on `GET /v1/public/events/{code}`, `…/quests` and `POST /v1/join`,
  per address, and per player too on the POST: 20 misses per 10 minutes, then 429 with `Retry-After`. The list has no
  throttle (public, indexed, paged); a cap belongs to the proxy. Drawn from the measure that matters: with N live codes
  one guess hits with odds N/887M, so misses, not lookups, are what an attacker spends.
- **M2, no enrollment is ever inserted by the API role directly:** `enrollment_insert` keeps only `app_is_admin()`;
  the organizer branch (any organizer could enroll any player id in their own event, and so read that player's row,
  birth year included) goes with the player branch. There is one role, `questify_app`, so the policy is what changes;
  the column grant stays for the admin seat. T-204 and T-218 add definers when they invite people. Tests: a player
  inserting into any event, and an organizer inserting player B into their own event, are both refused.
- **M3, the decision under a row lock:** `join_event` does `INSERT … ON CONFLICT (event_id, player_id) DO NOTHING`,
  then `SELECT … FOR UPDATE`, then decides (`left` → active/pending; `removed`/`banned` → `not_allowed`), so a rejoin
  cannot race a ban. A join is idempotent by its natural key (event, player), so it takes no Idempotency-Key
  (rules.md #6 is met by the key). Test: two concurrent first joins make one row and both answer 200.
- **m1:** no audit entries for joins (`audit_log` is for admin and staff powers). A rejoin overwrites `card_version`
  and `joined_via` with the card accepted last.
- **m2, the anonymous quest read lists its columns:** quest `id`, `name_ar`, `name_en`, `points`, `type`, `opens_at`,
  `closes_at`, its category's `id` and names; never `type_config` (an `enter_code` quest keeps its answer there).
  Quests with `visible = false` are left out; quests not yet open show as upcoming. Test: an `enter_code` quest's code
  appears in no `/v1/public` body.
- **m3:** `GET /v1/public/events/{code}` returns an ended event with `statusNow: "ended"` (the card says it has ended,
  no Join); draft, archived and unknown stay one 404. The list leaves ended events out.
- **m4:** `GET /v1/me/events` is a plain query under RLS (the player reads their own enrollments and those events);
  definers only where no grant exists: the anonymous reads and `join_event`.
- **m5, join by code only:** `POST /v1/join {joinCode, via: code|qr|link|public_list, cardVersion}`; the list returns
  each event's code. `public_list` is refused unless the event lists itself.
- **m6:** test that `join_event` with an empty context (the anonymous seat) raises.
- **m7:** each `JOIN_CARD` item is a message key with Arabic and English, checked by the messages completeness test;
  `name` and `venue` in every public shape are `{ar, en}` as in `EventRecord`.
- **Nits:** the list's keyset is `(starts_at NULLS LAST, id)`; `GET /v1/me/events` returns each row's `status`
  (`active` | `pending`, so the switcher can say "waiting for approval"); `parseJoinLink`'s hosts are one constant.
- **Notes for later tasks:** T-208 narrows "a player who left may come back".

## Result (2026-10-21)

CTO: plan 84 → 94; phases 93, 92, 93 (GO). Changes found while building, each accepted by the CTO:
- The list's keyset is plain `(starts_at, id)` (a scheduled or live event always has its times), and the cursor is the
  last event's id: the database reads its start time at full precision (a JS timestamp lost the microseconds and
  repeated a row). An id that names no event starts again from the first page.
- The miss budget reserves a miss before the lookup and gives it back for a real code, instead of a lock: a lock
  fails fast for concurrent requests, which is a crowd at one venue address. A burst never passes the budget (tested
  with 80 parallel misses); reservations still in flight count too, so it may stop short.
- Two budgets: 60 misses per address (one person cannot lock a venue's door), 20 per player.
- `join_event` refuses a NULL card: the database guarantees the consent, not only the API.

Mutation on `join/{join,routes}.ts` and `shared/join/*`: 97.8% (the survivors are an unreachable guard, `Math.min` for
`Math.max` when two budgets run out at once, and two equivalent forms).

Known gap recorded, not fixed here: organizers can read every `player` column of their enrolled players through RLS,
`birth_year` included (SECURITY.md, Data protection; T-208 builds the narrow read path).
