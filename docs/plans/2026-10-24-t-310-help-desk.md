# T-310 — Help desk: Ask a question, Report a problem, the operator inbox, private tickets

F-118, F-180: from a quest or from the event, a player sends the event team a **question** or a **problem** report (a
missing or broken QR code is the common one); operators answer it from staff mode's **Inbox**, which lists submissions
to review and help-desk tickets together with one count badge; owners and editors answer from a dashboard page. A
ticket is visible only to the player who sent it and the event team. Delivers FR-337 (text; the optional photo moves
to T-301b), FR-338 (the reply and Solved; the push is T-501's), FR-339, FR-927, and FR-1628 for tickets (owed by T-109).

on GitHub. Migration **0059** (new file; CranL runs through 0056, 0057 and 0058 are undeployed and finished, so the
functions they last stated are restated here, never edited there). Depends on T-205 (staff mode, operators and their
abilities), T-301 (the submissions queue the inbox merges), T-217 (erasure), T-211 (the rehearsal wipe), all done.

## The shape (ADR-246): one ticket table, built so T-312 only widens it

`ticket` holds one request and at most one answer. **Open** waits in a queue; **Closed** has an outcome: `answered`
(the team's one reply) or `solved` (closed with no reply, for example "the QR is back"). A further question is a new
ticket (ADR-105). The player sees the answer signed "The event team", never a person.

| Column | Type | Notes |
|---|---|---|
| `id` | bigint identity PK | |
| `player_id` | uuid NOT NULL → `player` | the sender; the player's reads and erasure key on it (T-312's non-event tickets have no enrollment) |
| `organizer_id`, `event_id`, `enrollment_id` | uuid, nullable | composite FKs `(event_id, organizer_id) → event ON DELETE CASCADE`, `(enrollment_id, event_id) → enrollment ON DELETE CASCADE`; CHECK `queue <> 'event' OR (event_id, organizer_id, enrollment_id all NOT NULL)` |
| `quest_id` | uuid, nullable | `(quest_id, event_id) → quest ON DELETE SET NULL (quest_id)` (PostgreSQL 17: only the quest column is cleared; a deleted quest keeps its tickets) |
| `kind` | text | CHECK `IN ('question', 'problem')` now; T-312 widens it (Q-209) |
| `queue` | text NOT NULL DEFAULT `'event'` | where the ticket waits: CHECK `IN ('event')` now; T-312 adds `'questify'` (escalation, app problems, suggestions) |
| `body` | text NOT NULL | 1–1,000 characters after `clean_submission_text` |
| `marked` | boolean NOT NULL | `text_marked(body)` at sending (FR-1628) |
| `status` | text NOT NULL | `open` \| `closed` |
| `outcome` | text | `answered` \| `solved`; CHECK `(status = 'closed') = (outcome IS NOT NULL)` |
| `reply` | text | 1–1,000 after `clean_submission_text`; CHECK `(outcome = 'answered') = (reply IS NOT NULL)` |
| `answered_by_staff` / `answered_by_operator` | uuid | at most one set (CHECK); set exactly when closed. Shown to the team, never to the player |
| `answer_key` | text | the answerer's idempotency key; unique per (event, answerer) like `submission.review_key` |
| `closed_at` | timestamptz | CHECK with `status` |
| `player_seen_at` | timestamptz | when the player saw the closed ticket (the unread dot and Home's strip) |
| `idempotency_key` | text NOT NULL | unique `(player_id, idempotency_key)` |
| `created_at` | timestamptz NOT NULL DEFAULT now() | |

Indexes: `ticket_open_idx (event_id, created_at, id) WHERE status = 'open' AND queue = 'event'` (the inbox and its
count), `ticket_event_idx (event_id, status, id)` (the dashboard's tabs), `ticket_player_idx (player_id, event_id,
created_at DESC)` (the player's list, the caps), `ticket_quest_idx (quest_id)` (the FK).
RLS **enabled and forced, PUBLIC revoked, no grant and no policy** to `questify_app`:
the definers below are the only doors (the T-301 pattern). A guard is not needed for the status columns: nothing but the
definers can write the table at all, tested from the API role's seat.

## Who sees a ticket (ADR-247)

| Who | Reads | Answers | How |
|---|---|---|---|
| The sender | their own, in any enrollment status (left, banned or removed included), while the account is active | — | `own_tickets`, `player_id = app_player_id()` |
| Another player | nothing, on any screen or route | — | no door returns another player's ticket (FR-339) |
| Owner, editors in scope | every ticket of the event | yes | `award_event_of` (AN404 otherwise) |
| An operator with `help_desk` | open tickets where `quest_id IS NULL OR operator_reviews_quest(event, me, quest_id)` (the function alone answers false for NULL to a limited operator, 0040:464); never their own (a playing operator's); closed ones only where `answered_by_operator = me` | yes, the open ones by the same rule | `help_operator(event)` (OP403 / OA403), `player_id <> me` |
| An operator without `help_desk` | none (the inbox still lists submissions when they have `review`, FR-927) | no | OA403 |
| A Questify admin | **none in T-310** (no console door); T-312 adds escalated tickets only (Q-211) | no | |
| Anyone else, `anon`, `PUBLIC` | nothing | no | no grant |

An operator reads a closed ticket only if they answered it, and the operator reads never say who answered (CTO 4);
the history of closed tickets is the dashboard's. A deleted quest sets its tickets' `quest_id` NULL, so they become
event-wide and visible to every `help_desk` operator (accepted: the text was always the event team's; CTO 3). The
player's reads (`own_tickets`, `/tickets/mine`, `/me/tickets`) carry no `answered_by_*`, username or name (tested;
CTO 5). What the team sees of the player: the @username and avatar (as on scans and the review queue), the quest,
the time and the text; never a contact, a full name or a birth year. The player's reply shows "The event team"; the
dashboard shows who answered (the operator's @username or the staff member's name) for accountability.

## Sending, limits and abuse (ADR-248)

- **Who may send**: an `active` enrollment in an event whose status now is `scheduled`, `live` or `ended` (not draft,
  not archived), with the event switch `helpDesk` on (`HT403 feature_off`). Pending, waitlisted, left, removed and banned
  members get `HT403 not_member`; the app shows a banned player the existing ban screen with the appeal email
  (FR-1417), not the help form. Only **sending** stops: Your requests stays reachable in every one of these states and
  with `helpDesk` off (CTO 2, App below). Sending stops 30 days after the event's end (`HT403 event_closed`), so
  the 90-day sweep never removes a fresh ticket early (CTO 6). A rehearsal account can send in a Scheduled event; the wipe removes its tickets.
- **The quest link** (`questId`, optional): a quest of the same event (`HQ404` otherwise; the composite FK is the
  second wall), not checked for open or visible (a player reporting "this quest is hidden" is a fair report).
- **Text**: `clean_submission_text` (SV422 `empty` / `too_long` / `characters`), then `text_marked`: a hit marks the
  ticket for the team ("Contains words from the watch list"), never blocks it.
- **Caps, in the database under the enrollment lock** (deterministic, no cache): at most **3 open** tickets per player
  per event (`HT409 too_many_open`), at most **10 sent in 24 hours** per player per event (`HT429 too_many_tickets`,
  Retry-After from the oldest of the ten). Replays by key are answered before the caps.
- **Spam and abuse**: the team closes a junk ticket as Solved with no reply; repeated abuse is what bans are for
  (T-208), and a ban stops sending. No separate help-desk mute (not asked for; ADR-248 records it). FR-1415's block
  hides players from each other; tickets are never shown to other players, so there is nothing for it to hide (T-312's
  Report a player is where it meets blocks; note there).
- **The answer**: reply 1–1,000 characters (`clean_submission_text`; team text is not word-list checked), or Solved with
  no text. The ticket row `FOR UPDATE`; only `open` moves; a second answerer gets `HT409 already_closed`; a replay of the
  same answerer's key on the same ticket answers the first outcome, and on a different ticket is `QK422` (CTO 7). An operator answering their own ticket: `HT403 self_answer` (hidden from
  their inbox anyway). Answering works while the event is not archived; the sender's enrollment status does not matter
  (a banned player can still read the answer to a question asked before).

## Functions (migration 0059; each REVOKEd from PUBLIC, entry points granted to `questify_app` only, each new definer calls `ensure_rehearsal_wiped` first)

1. `open_ticket(target_event, ticket_kind, target_quest, body, request_key)` (player) → `(ticket_id, status, created_at,
   replayed)`. In `submit_quest`'s order (0040:301-309; CTO 1): the enrollment `FOR NO KEY UPDATE` first, **then** the
   replay by `(player_id, key)` (same event, kind and quest answers the first ticket, anything else `QK422`), then
   the event, the switch and its 30 days, `active`, the quest, the text, the caps, the insert. Two sends with one key
   at once serialize on the enrollment, so the second is a replay, never a unique violation or a double count. A
   player with no enrollment in the event is refused before any lock (`not_member`).
2. `own_tickets(target_event)` (player): the caller's tickets in that event (NULL reserved for T-312), newest first,
   at most 50, with `unread = status = 'closed' AND player_seen_at IS NULL`; only for an `active` player account; any
   enrollment status; never the `helpDesk` switch. NULL lists every event's tickets (newest first, at most 100, each
   with the event's name) for the profile's Your requests (CTO 2).
   `own_unread_tickets(target_event) → integer` for Home. `mark_tickets_seen(target_event, ids bigint[]) → integer`
   stamps `player_seen_at` on the caller's closed ones.
3. `help_operator(target_event) → uuid` (internal, as `review_operator` with `help_desk`).
4. `answer_core(ev, target, reply, request_key, operator, staff)` (internal): the rules above; audit
   `event.ticket_answered` / `event.ticket_solved` for staff (ids only: `target_type ticket`, `after {outcome}`, never
   the text); operators are recorded on the row (`answered_by_operator`, `closed_at`, `answer_key`), as SECURITY.md
   already says for operator reviews. `staff_answer_ticket(target_event, target, reply, request_key, request)` and
   `operator_answer_ticket(target_event, target, reply, request_key)` are the two granted doors.
5. `event_tickets(target_event, wanted open|closed, wanted_kind, cursor_id, page)` (team): keyset paged (open oldest
   first, closed newest first), each row with the player's @username and avatar, the quest's title, the text, the
   reply, the outcome and who answered.
6. `operator_ticket(target_event, target)` (operator): one open ticket by the visibility rule, or a closed one only
   where `answered_by_operator = me`; never who answered (CTO 4).
7. `operator_inbox(target_event, cursor_at, cursor_kind, cursor_id, page)` (operator): **one list** (FR-927): pending
   submissions (when `review` is on: `queue_rows`' rule, inside the limit, never their own) `UNION ALL` open tickets
   (when `help_desk` is on: the rule above), ordered oldest first by `(created_at, kind, id)`, keyset paged; each row
   `kind submission|ticket, id, created_at, quest title, username, avatar, preview (first 120 characters), marked,
   ticket_kind`. Neither ability → `OA403`. `operator_inbox_count(target_event) → (submissions, tickets)`: the same
   rules, counts only (the badge).
8. `purge_ended_tickets(batch integer) → integer` (granted for the tick, no organizer context): deletes tickets where
   `greatest(event.ends_at, ticket.created_at) + 90 days` has passed (Q-210; with sending closed 30 days after the end,
   every ticket lives at least 60 days), at most `batch` (1,000) a run, oldest first. It joins `event` on its key; no
   all-status `ends_at` index is added (fine at this scale; noted for later). A comment says why
   it reads across organizers (rules.md allows this for retention sweeps).
9. **Erasure**: `erase_rows` restated (from 0050:867) with `DELETE FROM ticket WHERE player_id = me` (every ticket the
   account sent, open or closed, in any event). Tickets an erased operator answered keep the answer; the dashboard's
   "answered by" shows "Deleted account".
10. **Rehearsal wipe**: `wipe_rehearsal` restated (from 0055) deletes the rehearsal accounts' tickets before their
    enrollments and counts them (`tickets`), as it counts submissions.
11. **Event and quest delete**: the event cascade takes tickets; a quest delete clears `quest_id`. `has_completions` is
    not touched (a ticket never blocks a quest delete).

Lock order (rules.md gains the line): `open_ticket` takes the rehearsal row, then the enrollment `FOR NO KEY UPDATE`,
then inserts; the answer takes the rehearsal row, then the ticket `FOR UPDATE`, and never an enrollment; the sweep and
erasure delete ticket rows only. No path takes an enrollment after a ticket, so none cycles.

## API (`apps/api/src/tickets/`; API.md rows)

Player (bearer):
- `POST /v1/events/{eventId}/tickets` `{kind: "question" | "problem", questId?: uuid, text: string}`,
  **Idempotency-Key** → `201 {ticket}` (`200` with the first ticket on a replay). 403 `not_member` / `feature_off`, 404
  `unknown_quest`, 409 `too_many_open`, 422 `invalid_text {problem: empty|too_long|characters}` /
  `idempotency_key_reused`, 429 `too_many_tickets` with Retry-After.
- `GET /v1/events/{eventId}/tickets/mine` → `{tickets: [{id, kind, quest {id, title {ar, en}} | null, text, status,
  outcome, reply, closedAt, createdAt, unread}], open, limit: {open: 3}}`.
- `GET /v1/me/tickets` → `{tickets: [{…as above, event {id, name}}]}` (`own_tickets(NULL)`): every event's, in any
  enrollment status, whatever the switch (CTO 2).
- `POST /v1/events/{eventId}/tickets/seen` `{ids: number[] (1 to 50)}` → `204`.
- `GET /v1/events/{eventId}/home` gains `help: {unread}` (`own_unread_tickets`, never gated by the switch);
  `/v1/config`'s event features carry `helpDesk`, which gates only the send form.

Operator (player bearer, operator of the event):
- `GET /v1/operator/events/{eventId}/inbox?cursor&limit` (default 30, at most 100) → `{items, nextCursor, abilities
  {review, helpDesk}}`; `GET …/inbox/count` → `{submissions, tickets, total}`.
- `GET /v1/operator/events/{eventId}/tickets/{ticketId}` → the detail; `POST …/tickets/{ticketId}/answer` `{reply?:
  string}` (absent: Solved), **Idempotency-Key** → `{ticketId, outcome, replayed}`. 403 `not_operator` / `ability_off` /
  `outside_quests` / `self_answer`, 404, 409 `already_closed` / `event_closed`, 422 `invalid_text`.

Team (staff cookie, owner or editor in scope):
- `GET …/events/{eventId}/tickets?status=open|closed&kind=&cursor` (the dashboard's organizer prefix, as Submissions) → `{tickets, nextCursor, counts {open,
  closed}}`; `POST …/tickets/{ticketId}/answer` as the operator's (audited).

Cursors are opaque base64url of `(created_at, kind, id)`. Every route declares `config.access` and is classified in
`routes.int.test.ts`. **Logs**: `ticket.opened {kind, hasQuest, marked}`, `ticket.answered {outcome, via operator|staff,
replayed}`, `ticket.refused {reason}`; never the text, the reply, a username or a player id. The redaction test gains a
ticket body and a reply.

## How the player learns of an answer before T-501 (ADR-248)

- **Home**: a parchment strip "The event team answered you" while `help.unread > 0` (from `own_unread_tickets`, never
  the switch), opening Get help → Your requests, which is always shown when the player has tickets;
  the strip is part of Home's read, so it shows on every Home load and pull-to-refresh (no new poll).
- **Get help → Your requests**: a gold dot on each unread answer; showing the list sends `seen` for the answers on

## Retention and personal data (Q-075, Q-210)

- A ticket's text and reply are personal data the player wrote (or wrote about them). Stored in Riyadh with the rest;
  never in logs, error reports, audit rows or push text (rule 3; the redaction and audit tests check it).
- **Account deletion** deletes every ticket the account sent, at once (`erase_rows`), open or closed. Rows are not kept
  for counts: nothing in the ledger or the audit log points at them.
- **Retention**: a ticket is deleted 90 days after the later of its event's end and its sending (the lifecycle tick's
  `purge_ended_tickets`, 1,000 a run; sending closes 30 days after the end), long enough for a prize problem after the event (claim deadlines run up to 60 days, T-214) and short for PDPL
  minimization. The privacy policy's help-ticket line (Q-075) states it; counsel confirms (Q-210).
- DATA_MODEL replaces its `ticket(...)` stub line with the table and its **PII** line.
