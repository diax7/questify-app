# API — Questify

> The contract between the clients and the server (not the implementation). Stage 6, 2026-10-17.
> **Surface: internal-only in v1** (the player app, the web app and the wallet providers are the only
> callers), but built as if it could be opened later, because the AI setup wizard (ADR-060) and
> agencies would call an organizer API. Nothing here is a public promise yet. Proposed, ADR-102.

## Conventions

- **Base path and versioning:** `/v1`. A breaking change gets `/v2`; the app keeps working against
  `/v1` until its minimum-supported version is raised in the console. The app sends its version in
  `X-App-Version`, and the server answers `426` with a store link if the build is too old.
- **Format:** JSON, UTF-8, camelCase; times in ISO-8601 UTC; ids are UUIDs; numbers are Western
  digits (ADR-018). User-facing text comes as `{ "ar": "...", "en": "..." }`.
- **Auth schemes:**
  - *Player bearer token:* short-lived access token plus a rotating refresh token, issued after a
    phone or email code (ADR-030). Operators use the same token plus an event role.
  - *Staff session:* cookie `__Host-qs_session` (`HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, no
    `Domain`) after email + password + email code (ADR-078), with inactivity expiry (NFR-030). **The
    dashboard's server reverse-proxies `/v1` to the API**, so the browser sees one origin: no CORS, and the
    cookie works. State-changing requests must carry `Origin` equal to the dashboard origin (else
    `403 csrf_rejected`). The web app's `/v1` forwarder passes `X-Forwarded-For` through
    unchanged and reaches the API over the private network, so the API trusts exactly one hop (CranL's edge) on
    both paths (`TRUST_PROXY_HOPS=1`, ADR-113). Every `/v1/staff/*` answer is `Cache-Control: no-store`.
  - *Screen token:* a signed read-only token in the big-screen and station page links.
  - *Provider callback:* signed requests from SMS, email and wallet services.
  - Roles: `anonymous`, `player`, `operator` (a player with an event assignment), `editor`, `owner`,
    `admin`. Every route lists who may call it; the server re-checks the organizer and event on
    every request (NFR-016).
- **Errors:** one envelope everywhere: `{ "code": "<machine_code>", "message": { "ar", "en" },
  "details": {} }`. Status codes: 400 bad input, 401 not signed in, 403 not allowed or paused, 404,
  409 conflict (e.g. already completed), 422 rule failure, 426 update the app, 429 too many
  requests / busy, 503 maintenance (with the maintenance message).
- **Pagination:** cursor-based (`?cursor=&limit=`); lists return `nextCursor`.
- **Idempotency:** every unsafe action (complete a quest, award points, reserve a prize, send a
  message, redeem) requires an `Idempotency-Key` header. The server keeps the first result for 24
  hours and returns it for a retry.
- **Rate limiting:** `429` with a `Retry-After` header and `details.retryAfterSeconds` (what the app needs to say when to try again).
  Limits are tuning numbers, editable in the console (F-279) once its tuning lands; today they are code constants (`apps/api/src/auth/limits.ts`): login-code requests per phone/email/IP,
  scans per minute per player, uploads, exports.
- **Live updates:** polled (ADR-221, T-306): the app reads `GET /v1/events/{id}/live` every `livePollSeconds`
  (tuning, 10) while an event screen is open and the app is active. The server-sent stream
  (`GET /v1/events/{id}/stream`: ranking changes, announcements, "flash quest started", maintenance) is **not built**;
  it is the growth step if the big screen (T-504) or a load test needs faster updates.
- **Webhooks:** none sent to organizers in v1. Inbound: SMS delivery receipts, email bounces, wallet
  device registrations; all verified by signature.
- **Config:** `GET /v1/config[?event=<id>]` returns the composed configuration with an `ETag` (see
  `CONFIGURABILITY.md`); anyone may read it. The document is `{schemaVersion: 1, features: {<name>: {enabled,
  minAppVersion, message}}, tuning: {<name>: number}, legal: {documents: [{id, version}]}, terms}`, keys sorted.
  `terms` is the event's words, always complete (Questify's own outside an event or for a word it did not set):
  `{currency: {icon, ar: {one, many}, en: {one, many}}, player: {ar, en}, operator: {ar, en}}` (T-117). An app with a
  copy from before `terms` reads it as the defaults, and one bad word falls back to its default.
  `legal` names the player documents in force (`terms_of_use`, `privacy_policy`, `community_guidelines`,
  T-110): the app opens them as the web pages `/{lang}/legal/{id}` and sends these versions back when the
  person accepts. An unchanged document costs one request:
  `If-None-Match` with the tag answers `304`. `Cache-Control: no-cache`, so apps always revalidate. A change
  reaches every app within 15 seconds (the server's cache) plus the time until the app next asks. An event the
  caller cannot see (unlisted, private, or not there) answers `404` exactly alike; a player reads an event they joined
  through `GET /v1/events/{id}/config`. The app keeps the last document that
  passed `parseComposedConfig` (F-282), drops blocks it does not know, and treats a feature as absent when its
  own version is below `minAppVersion`.
- **Texts:** `GET /v1/translations` returns `{ar: {key: text}, en: {key: text}}`: only the texts a Questify
  admin changed. Anyone may read it; it carries an `ETag` (304 when unchanged) and the server keeps it for 15 seconds.
  The app lays it over the texts shipped inside it (`createTranslator`), so a key that is missing, blank, damaged (a
  placeholder gone) or unreachable shows the shipped text (FR-1768). Numbers in any text are shown in Western digits.
- **Deprecation:** since the API is internal, old routes are removed after the minimum app version
  passes them; each change is recorded in `docs/` changelog notes. If the API is ever opened,
  `Deprecation` and `Sunset` headers and a minimum 6 months' notice apply (proposed).
- **OpenAPI:** generated from the shared schemas during the build; until then this file is the
  source of truth.

## Operations (v1 baseline)

Auth shows who may call. "Rate" notes any special limit.

> **Baseline only.** The operations below cover the core loop, rewards, notifications, wallet, the dashboard and the console at group level. Still to be listed when each phase is built: agenda and session registration and check-in; polls, community quests, surveys and ratings; the Questify layer (profile, items, achievements, gems, daily challenge and word, streaks, Questify home, Explore, public events list); guest lists, join fields and rank prizes; reports and blocks; consent, data export and deletion requests; operator invites, station and kiosk pairing; maps and sponsors; big-screen and station feeds. They follow the same conventions.

**Quest items (T-304d, ADR-205).** A quest's and a category's builder bodies take `itemId` (a quest item of this
event; null clears it; a removed or other event's item answers 422 `invalid_item`) and answer it. Every pay answer that
carries `bonus` also carries `item: {name: {ar, en}, outcome: pending | out_of_stock | claim_closed, until: {at,
timeZone} | null} | null` (`until`: a pending item's claim deadline and the event's zone) (the item
this completion gave on the player's first completion of the quest, or missed), and `bonus` gains `item` the same way
(a category's item, once per period) with `points` 0 for an item-only bonus. The quests read gains `item: {ar, en} |
null` per quest (while the player has never completed it and stock is left) and `bonus.item` per category (while stock
is left). The player's redemptions (`GET /v1/events/{id}/shop`), `GET /v1/me/desk-items` and the desk's lookup and
find gain `source: shop | rank | quest`; a quest item has price 0, is collected through the same handover, and its
player cancel answers 409 `rank_prize` ("This prize can't be cancelled in the app"). The award removal
(`POST …/entries/{entryId}/remove`, and the submission removal) answers `item: cancelled | handed_over | null`: a
pending item of that credit is cancelled and its unit returned; a handed-over one stays; a replay answers the item's
current state.

### Devices: stations, kiosks and big screens (T-309)

A browser opens `/{lang}/station`, `/{lang}/kiosk` or `/{lang}/screen` (no ids in the address) and shows a pairing code
until staff claim it (ADR-239). Its credential is the `__Host-qs_device` cookie (HttpOnly, Secure, SameSite=Strict,
Path=/, 400 days; 32 random bytes, stored as its SHA-256), never in a URL, a log, an audit row or an answer body. Every
device answer is `no-store`; device writes need the dashboard's `Origin`. A revoked, ended (24 h after its event ends),
idle (30 days) or unknown device answers **401 `device_unpaired`**, and the page starts over. Access kind `device`
lives only under `/v1/device` (`/v1/devices` is not one); `GET /v1/device`, renew and activate take a pending or not yet
activated device, every other device route a paired and activated one.

**Console routes (T-210):** every `/v1/admin/…` route has the access kind `admin`: the staff session and Origin
checks, then **404 for anyone who is not an active platform admin** (the console is not advertised); the database
checks the account again inside each definer (`app_admin_id()`, migration 0027). Every state-changing call writes to
the audit log (NFR-019).

**Flash quests and boosts in the player reads (T-307, ADR-231 to ADR-233).** `GET /v1/events/{id}/quests`: a flash
quest is listed only inside its window, with `flash: {closesAt}` (null for any other quest); each quest and each
category has `boost: {multiplier, endsAt} | null`, the boost of its category running now for the caller (a rehearsal
boost only for a rehearsal account; a hidden category's only once found). `GET /v1/events/{id}/live` gains `flash:
[{questId, title {ar, en}, closesAt}]` (open now, playable by the caller, not done) and `boosts: [{boostId, categoryId,
category {ar, en}, multiplier, endsAt}]`; the event's "anything live" shortcut stays true only for 15 minutes after a
flash quest opens or a boost starts (CTO 8), so the app takes them as one-time cards and reads what runs from the
quests read. Every completion answer (scan, code, location, vote, survey, share, passport stamp, meet, an auto-approved
